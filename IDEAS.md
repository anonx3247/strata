# Ideas, decisions and open questions

Everything that keeps track of where Strata is going: open questions, ideas, what has been decided (and whether it is built), known gaps and the roadmap. The [README](README.md) and [docs](docs/) describe what is built.

## Open questions (to discuss before building)

- **A field as a `mut` argument** (decided with the user 2026-11-21: allowed, as now). `shift(mut r.lo)` is the same as `mut t := r.lo; shift(mut t); r.lo = t`, and the record's own invariant is checked the same way after the call as after that assignment, so forbidding it would protect nothing. The check after a `mut` call is left out where the checker proves the parameter's type fits the variable's; undecided cases could become proof obligations for `verify`, with the runtime check kept only for what isn't proven.
- **Generating code from a type's shape** (decided 2026-11-21): see the decision "Derived traits, `comptime` and special methods" below.
- **Marking a `mut self` call** (built 2026-11-20, see docs/language.md "Mutation"). `mut queue.claim(2)`, as Hylo's `&x.append(1)`: required when the method takes `mut self`, an error otherwise. The tree is `Expr::Mut(Method(..))`; a `Mut` around anything else is an argument for a `mut` parameter. The parser's `marked` reads a place after `mut`, then marks the first method call on it, and later calls apply to its result (rendered `(mut q.claim(2)).len()`); as an argument the marked call is rendered in parentheses, `call((mut o.pop()), x, y)` (the user's form). Results are not places (user's point): `mut f(x).m()` is a parse error, and a result can't be passed to a `mut` parameter; name it first. Rejected: `(mut queue).claim(2)`, `claim(mut queue, 2)`, and a separate call operator.
- **What iterating a string yields** (decided by the user 2026-11-21; built: the three units, `len` / indexing / slicing on them, and positions as byte offsets; see "Iterators and `FiniteIterator`"). Nothing implicitly: a `String` is not a list and can't be the subject of a `for` (already an error today: "`for` needs a List, Set or Dict"). The unit is always named: `s.bytes()`, `s.code_points()`, `s.graphemes()` (names to settle), each giving an iterator a `for` can run over. `chars` (code points, as a `List[String]`) stays. The same goes for length, indexing and slicing (decided 2026-11-21, built): `len(s)`, `s[i]` and `s[1..3]` are refused on a `String`, naming the units; they are written on the unit, `len(s.bytes())`, `s.graphemes()[1..3]`. Indexing, slicing and `len` need a `FiniteIterator` iterator (see "Iterators and `FiniteIterator`" below); a string's units are finite, so they can be indexed. Settled when building it (user, 2026-11-22): positions are byte offsets (`index_of`, `byte_slice`, `byte_len`).
- **Iterators and `FiniteIterator`** (user, 2026-11-21; built in four steps, below). Two traits: `Iterator` (what a `for` runs over, and what `map` / `filter` / `fold` take as receiver) and `FiniteIterator` (it ends). `List`, `Set`, `Dict`, ranges and a string's units implement both; an unbounded generator implements only `Iterator`. `FiniteIterator` is what indexing, slicing and `len` require, and what lets termination checking say a `for` loop ends (today it knows this only for lists: "only `for` loops"); a `for` over an `Iterator` that isn't `FiniteIterator` is treated like a `while`. Named `FiniteIterator` (user, 2026-11-21: clearer than `Finite`, which means nothing apart from an iterator). Decided (user, 2026-11-21): `FiniteIterator` carries its length, known ahead of time (that is what shows it ends); the length may change where the value is mutable (a `mut` list). `map` keeps the length; `filter` keeps finiteness but returns something with a new length (on a list, a new list). Proposed (Claude, following Rust's `trait ExactSizeIterator: Iterator { fn len(&self) -> usize }`): a supertrait, `trait FiniteIterator: Iterator { fn len(self) -> Natural }`, which Strata already has (`trait Summary: Describe + Priced`). A supertrait is a requirement, not inheritance: implementing `FiniteIterator` requires an `Iterator` impl, but nothing is inherited or overridden and there is no subtyping of values. The user's concern: it looks like a kind of iterator, i.e. inheritance. To settle: that, whether a lazy `filter` returns an eager value (exact length) or a lazy one (only a bound: Rust's `size_hint` upper bound, which is enough for termination but not for indexing), and how `verify` uses `len`. **Step 1 built** (branch `iterators`): `trait Iterator[T] { fn next(mut self) -> Option[T] }` in the prelude (the element type is a trait parameter, as Strata has no associated types), and `for` over any value implementing it. The checker accepts the subject when its type satisfies `Iterator[el]` (`satisfies`, which also infers `el`), and then the loop is rewritten as `{ mut $iter_N := xs; loop { match mut $iter_N.next() { Some(p) => body, None => break } } }` (`types::lower_iterator_fors`) and the program checked again, so the compiler, the prover and termination see an ordinary loop; the second check only happens when a program has such a loop. Lists, sets and dicts keep their built-in loops (they give an iterator through `iter()`, step 4), and `verify` says a `for` over an `Iterator` that isn't a `FiniteIterator` may not end. Decided (user, 2026-11-21): `FiniteIterator` is a supertrait of `Iterator` (`trait FiniteIterator[T]: Iterator[T]`; the inheritance reading is fine). `map` / `filter` are lazy, so a comprehension over an unbounded iterator is itself an iterator (an infinite comprehension). `verify` uses the length for termination first: a `for` over a `FiniteIterator` ends. Invariants over `len` come later. Next: `FiniteIterator` and termination through it, lazy `map` / `filter` / `fold` on any iterator, the built-in collections and ranges as iterators, comprehensions over iterators, a string's units. To settle when building: what a comprehension over a finite iterator gives (a `List`, as today for lists, or a lazy iterator), and where a lazy `filter`'s length comes from (its bound, the source's length, is enough for termination). **Step 2 built** (branch `iterators-2`): `trait FiniteIterator[T]: Iterator[T] { fn len(self) -> Natural }`, and `map` / `filter` / `fold` as default methods of `Iterator` (`map` / `filter` lazy, through the prelude's `Mapped` / `Filtered`). How:
- **The prelude carries code** (`types::PRELUDE_CODE`): definitions with bodies are added to every program when it is resolved (`with_prelude_code`), in the module `std.prelude`, so they are checked and compiled as the program's own and skipped where std is (`verify`, the views, the viewer's type map). Their traits' methods are named `std.prelude.len` and so on, as std's methods are named in their modules, and a program's impls of those traits name their methods the same way: apart from the builtins `len`, `map`, `filter`, `fold`, which lists keep. Calls (`it.len()`) find them through the receiver's traits (`implemented_method`, now for type parameters' bounds and trait-typed values too). Messages show them short (`ListIter.next`, `FiniteIterator::len`).
- **Termination:** a `for` over a `FiniteIterator` holds it in a `$finite_iter_N`; that `loop`, and the `next` call it makes, count as ending. This rests on `len`, which nothing checks yet (with invariants, later).
- **Build tests** (user, 2026-11-21): they no longer compare compiled output with `--interpret`, but with outputs recorded in `tests/data/build/expected` (`STRATA_BLESS=1` records them), recorded from step 1, where both agreed. The trait methods named like builtins had made the interpreter call `Iterator`'s `map` on lists.
**Step 3 built** (branch `iterators-3`; the user's idea: what is passed to `filter` must end, then `filter` and `fold` do):
- `fold` and `to_list` are `FiniteIterator`'s (on an unbounded iterator `fold` never returns: refused, "`fold` needs a `FiniteIterator`"), written as a `for` over `self`, which ends. `Mapped` / `Filtered` are `FiniteIterator`s when their source is (a filtered one's `len` counts, on a copy).
- Lambdas: termination already follows a lambda's calls from the function it is written in, so a call of a function-typed parameter (`f(acc, x)` in `fold`) counts as ending. An impl's call of its own trait method on a field of `self` (`self.inner.len()`) is recursion on a smaller value (values are finite trees), left out of the call graph.
- Comprehensions over iterators: the checker gives `map(it, f)` / `filter` / `fold` on an iterator to its methods, and `set(it)` / `dict(it)` on a finite one to the prelude's `set_of` / `dict_of`. So a comprehension over an iterator is a lazy iterator (finite when its source is), over a list a list as before.
- `verify`'s cross-check: a fault in a function the checked one calls is that function's, not "a bug in the prover".
**Step 4 built** (branch `iterators-4`; user, 2026-11-21: `xs.iter()`, not lists as iterators, which would clash with the list builtins `map` / `filter`): the prelude's `ListIter[T] = { items: List[T], at: Natural }` (an `Iterator` and a `FiniteIterator`), and `trait Iterable[T] { fn iter(self) -> ListIter[T] }` for `List`, `Set` (in order, `to_list`) and `Dict` (entries by key, `items`); ranges are lists. Calls find a built-in type's impls by its receiver too (`implemented_method`). The prelude's code's names (`ListIter`, `Mapped`, ...) are the prelude's: defining one again says so. **A string's units built** (branch `string-units`; user, 2026-11-21: the names `bytes` / `code_points` / `graphemes`, written in Strata over native byte access): `s.bytes()` and `s.code_points()` are the prelude's (`Bytes`, `CodePoints`, trait `TextUnits` for `String`; code points decoded from the UTF-8 bytes, moving past a continuation byte to the next start), over two native builtins, `byte_len(s)` and `byte_at(s, i)` (C runtime and compiler). `s.graphemes()` is `std.unicode`'s (`Graphemes`, trait `GraphemeText`; std is loaded for a program that calls it, as for `matches`): UAX #29's rules GB3 to GB13 with GB9c (Indic_Conjunct_Break, now generated into std.unicode_tables from the UCD's DerivedCoreProperties.txt, `tools/unicode_tables.py`'s second input), its tables decoded at compile time (`comptime`), checked against all 1093 cases of GraphemeBreakTest.txt (`tests/data/grapheme_break_test.st`). Found on the way: precompiling std deadlocked once std had a `comptime` (resolving std ran it, and compiling that waited for the std library being made: `llvm::building_std` now covers the resolve); a lambda's parameters didn't get types from an earlier argument's trait obligation (`it.map(x -> x.m())`: `settle_pending`). `len`, indexing and slicing on a unit **built** (branch `unit-index`): `len` / `at` / `get` / `slice` / `take` / `drop` called on an iterator are its methods (`FiniteIterator`'s `get`, `at` with its precondition, lazy `slice`; `Iterator`'s lazy `take` / `drop`, the prelude's `Taken` / `Dropped`), `join` collects a finite iterator of strings; messages show the prelude's names as written (`types::shown_name`). **Strings by byte offsets, built** (branch `string-bytes`; user, 2026-11-22: positions are byte offsets, Rust's way): `len(s)`, `s[i]`, `get(s, i)` and `s[a..b]` on a `String` are refused, naming the units (`types::string_position`); `index_of` gives a byte offset, `byte_slice(s, a, b)` cuts in constant time, `byte_len(s)`. Decided while building (Claude; the user's option said it faults): `byte_slice` is total, an offset inside a character moving back to its start, so it never faults and needs no proof obligation (a boundary obligation would be unprovable on most strings, and std's `verify --require proven` relies on it). The prover models bytes exactly on ASCII strings and by bounds elsewhere: `utf8_len` (declared in every query) is between `str.len` and 4×, a slice has at most b - a bytes (exactly on ASCII), a match fits in the string; `len(s.code_points())` is `str.len(s)` and `len(s.bytes())` is `utf8_len(s)`, so refinements on them stay provable. Exhaustiveness reads `len(it.code_points())`, `it != ""` and `it == ""` as length conditions on strings; `NonEmptyString` is `it != ""`. Migrated: std (regex, cli, json, http, fs), the compiled prelude's `lines`, examples, test programs, docs. Found on the way: refinements written in types (`zip: String where …`) and `where` conditions in patterns weren't given the checker's method decisions (`ast::decl_exprs_mut_post_typed`); messages printed elaborated names (`printer::shown`). **String builtins in Strata, first batch built** (branch `str-builtins`): `contains`, `starts_with`, `ends_with`, `index_of`, `chars` and `reverse` (on strings) are the compiled prelude's (`llvm/prelude.strata`, `str_*`, over `byte_len` / `byte_at` / `byte_slice`), called in place of the C runtime's; the checker's signatures and the prover's models are unchanged. `index_of` is a naive search (O(n·m), as the C one). `split`, `replace` and `repeat` **are total and in Strata too** (user, 2026-11-22: errors are `Result`s, and these have no error case: an empty separator splits at every character, an empty pattern is found around every character, as Rust's; a count below 1 gives `""`); the prover no longer has obligations for them (`replace` with an empty pattern is left unknown: SMT's `replace_all` differs there). Still in C: `trim`, `to_upper` / `to_lower`, `is_digit` / `is_alpha` / `is_space` (Unicode tables: `std.unicode` has them, but the compiled prelude can't use std), `parse_int` / `parse_float`. Not yet: a nested comprehension whose inner source is an iterator (needs a lazy `flat_map`); a user's own `it.next()` loop isn't shown to end (a call of `next` through the trait may reach `Filtered.next`); `trim`, case mappings, the `is_` tests and number parsing are still C.
- **Regex verification scope** (decided with the user 2026-11-20; not built). By default, regex refinements are proven over ASCII strings only, and the result always says so ("proven for ASCII strings"). Such a proof counts as proven in an ordinary `verify` run. Under a `[verify] proven = [...]` rule it does not, unless the project opts in to accepting ASCII proofs; it is still reported as proven for ASCII either way. Full Unicode proofs are asked for explicitly where they matter (per module in `[verify]`, or per function). Running code stays fully Unicode either way. Pairs with "two solvers": ASCII classes are small enough for Z3 to decide exactly; full-Unicode proofs can go to cvc5, which decides the large classes.
- **Two solvers, each for its strengths** (user, 2026-11-20; direction). Z3 and cvc5 are both wired in (`STRATA_SOLVER`). Use both: route a query by what it contains (cvc5 for strings and large Unicode regex classes, which it decides exactly where Z3 times out; Z3 elsewhere), or run both and take the first definite answer.
- **Complexity / cost.** Separate from termination: a function can terminate and still take exponential time (naive `fib`, Ackermann). The user raised it as "another issue"; nothing is designed yet.
- **Transpilation / interop** with Python (Pydantic, JSON as the boundary), TypeScript and Rust. Later.
- **JSON as a boundary format: a derived `Json` trait** (user, 2026-11-21; built: see "`std.json`: a derived `Json` trait" under Decisions, which supersedes the details below where they differ; kept for the reasoning). Before it, every value had one JSON form (the interpreter's `to_json` / `from_json`, now gone; `to_json` keeps it): variants externally tagged (`"None"`, `{"Some": 3}`, `{"Queued": {...}}`), records as plain objects, integers beyond 64 bits as strings of digits, untagged unions read by trying each member in written order. That is useful for debugging but not for the main use the user sees: JSON from a web front end read straight into a record. Measured problems: with `Int | String`, `"5"` reads back as the `Int` 5; with `String | Int`, a big integer (written `"9223372036854775808"`) reads back as a `String`. The direction:
  - **a derivable trait** (`derivable(Record)` / `derivable(Sum)`, see "Derived traits" below) whose derive succeeds only for types with an unambiguous JSON form, so being `Json` *means* being serializable. Base types implement it built in. Full round-tripping of every value is not the goal; reading any JSON that fits the type is.
  - **`Option[T]` is the value or `null`** (or a missing key, for a field), not `{"Some": x}`. `Option[Option[T]]` can't tell `None` from `Some(None)`, so it isn't `Json`.
  - **a `"type"` key holding the type's name**, as TypeScript's discriminated unions do (user). Proposed: always on a sum's variants (`{"type": "Queued", "name": "a"}`, a variant without data either that or the bare string `"Queued"`); on a plain record written, but optional on input when the expected type is a single record (web forms won't send it). A variant with positional data needs a key for it (`"value"`?, or only record and no-data variants are `Json`). A field named `type` in a `Json` type is an error (or the tag key is configurable).
  - **records and `Dict`s**: reading is driven by the expected type, so they only need telling apart inside a union, where the `"type"` key does it; a `Dict[String, V]` in such a union could have a `"type"` key itself, so that union isn't `Json`. A `Dict` with non-string keys isn't `Json` either (or keeps the `[[k, v], ...]` form).
  - **unions**: `Json` only when the members' JSON kinds can't overlap (number / string / bool / null / array / object with a distinct `"type"`). `Int | String` qualifies once integers are never strings.
  - **integers**: always JSON numbers; a value beyond 64 bits is a fault when written and an error when read (user: "big integers are banned"). Open: JavaScript's numbers are exact only to 2^53, so a web client silently rounds larger ones. Options weighed with the user: write larger ones as strings (any `Int` works, but the JSON's shape then depends on the value: `number | string` for a TypeScript client), or refuse them (a fault when written, an error when read; the shape stays fixed, and with a `SafeInt` alias and `verify` covering derived code the risk is visible). The user leans towards refusing; Claude agrees.
  - **a JavaScript-like `Number`** (user's suggestion): `Float` is already an IEEE double that is never NaN or infinite (docs/language.md), which is exactly what JSON can hold: JSON has no NaN or Infinity (`JSON.stringify(NaN)` is `"null"`). So a `Number` with NaN/Infinity wouldn't go through JSON any better; reading `3` into a `Float` already works. Open: whether `Number` is still wanted for JS interop beyond JSON.
  - **decided since**: values are shown as code everywhere the tools show them (`strata run`, verdicts, traces, messages: "No internal JSON", #191); `data-on-click` became numbered handlers; only the builtin `to_json` keeps the old tagged form.
  - **`Debug` and `Display`, as Python's `repr` and `str`** (user, 2026-11-21; built, branch `runtime-types`: `Display`'s method is `to_string`, `Debug`'s is `debug`, and an `impl` replaces either; see the `std.json` entry under Decisions). `show` (used by `print`, `to_string` and f-strings) was the compact JSON form, except that a top-level string, big integer or variant without data dropped the quotes. Decided instead: two derived traits that every type has by default, overridable like any other trait (`impl Display for T { fn to_string ... }`). `Debug` is the value as written in code: a record with its type name (`Queued { name: "a" }`), strings always quoted (`"hi"`), `Some("hi")`, `[Red, Blue]`, `Dict { "a": 1 }`, `(1, "x")`. `Display` is the readable form: by default the `Debug` form; `String`'s is the one built-in difference (the text without quotes). Collections display their elements with `Debug`, as Python does (`["a b"]` vs `["a", "b"]`). `print`, f-strings and `to_string` use `Display`.
- **Changes are git commits** (built, `git_commit` in main.rs, asked for by the user). After a logged change (`record`: edit / rename / move / add) and at `strata done`, the package's files are committed with the change's message (`git add -A -- .` and `git commit -- .` in the package folder, so other staged work stays out). Nothing during a pending change. Off with `auto_commit = false` in strata.toml or `--no-commit`; skipped outside git and during a merge in progress; a failed commit leaves the change made and says why. Tests that commit by hand after strata commands no longer need to; the log-splitting test uses `--no-commit` to keep several entries in one commit.
- **Editing in an editor** (built, `edit_in_editor` in main.rs). `strata edit [MODULE | SELECTOR]` at a terminal with nothing piped in (or with `--editor`) opens, in `$VISUAL` / `$EDITOR` / git's editor / `vi` (through `sh -c`), the whole package with no argument (one file per module, all given to the editor), a module (`shop`, `main`, or its file `shop/orders.strata`, which may be new; a module's name wins over a definition's, and a definition is named with its module: `shop.total`, `main.main` for the root module's `main`), or the definitions a selector picks (one file per module they are in). Piped, `strata edit shop` puts the definitions into `shop`; there is no `--module` for `edit`. What is saved goes through `apply_edit` like a piped edit; definitions deleted from the buffer are removed. If it doesn't parse or check, the editor reopens with the errors on top (`// ✗ ` lines, dropped when read back); saving unchanged gives up. Errors go on top of the file of the definition they are in.
- **Removing or adding variants in a pending change** (built, `fix_matches` in pending.rs). Patterns can't be holes, so `match`es are fixed first: arms of removed variants are dropped (or only their alternative in an `a | b` pattern; nested ones like `Some(Pending)` too), a `match` on the changed type without a catch-all gets an arm `NewVariant => ?pending_N` (`Lost(_)`, `Lost { .. }`), and a `match` with no arm left becomes a hole. The edit prints what was dropped. Then expression holes as before (the expression walk skips patterns). Not yet: `let` / `for` patterns naming a removed variant still reject the edit.
- **Pending changes** (built, `src/pending.rs`). An `edit` whose own definitions check but that breaks other code isn't rejected: each broken use in the erroring definitions (a call, reference, constructor, method call or `is` test naming a definition whose interface changed, outermost first) becomes `?pending_N`, recorded with what it was and why, and the package enters a pending change (`.strata/pending.json`: the files before, the holes, the renames). Edits, renames and moves during it only write files (`record` in main.rs); `strata status` lists the holes; `strata done` logs the whole change as one entry (from the files before to now, with its renames), refusing while its holes are open unless `--keep-holes` (they become `?todo_N`); `strata abort` restores the files. (`strata ci` used to refuse `?pending_*` holes; it is gone, and every command reports holes.) Not yet: one pending change per package; a use the edit broke compatibly in an erroring definition is also turned into a hole.
- **Storage: hash references, and propagation** (discussed 2026-11-20; direction agreed, not built). The user prefers storing definitions by hash with references by hash and names in a separate table (Unison's model: renames become free, merges of new code can't conflict, several agents can add code at once), over a binary encoding of the same files (the encoding itself is now decided: see the next item). On an edit, dependents follow automatically when they still type-check ("option 1"), and otherwise get a to-do. The user's addition: while a to-do is open, the references to the old version are replaced with typed holes, so the agent sees exactly what to fill in. Before building: settle how a hole keeps what it replaced (the old call, for the agent), and that code with holes still checks but can't run. Status (2026-11-22): the propagation half is built as pending changes (`src/pending.rs`: broken uses become `?pending_N`). The storage half is not: module files hold self-contained, hashed definitions, but references are stored by qualified name, not by hash, there is no names table, and no object per hash (renames still rewrite every reference; two agents adding to one module still touch one file).
- **Storage: the tree, in binary** (decided with the user 2026-11-20; built: packages are stored in it, see below). Code is stored as the syntax tree, not as text: the AST is the language, and the current syntax is one front end among possible others (Nim-, Python-, C-, Haskell-like). The encoding is a compact binary format, not JSON (no serialization round-trips; big integers stored exactly). Ideally a module's `.strata` file *is* that binary, and text is rendered only when needed: `strata edit` already opens a module or definitions as text in the editor and parses what is saved, `render` / `view` print it. Rendered text files, if kept at all, are a read-only view that git ignores. Every change then goes through the tools (`edit`, `rename`, `move`), which check it and answer immediately; with a cache, several agents (the user guesses 3–4) could work in one codebase at once. Before building, settle:
  - ~~the format~~ **built**: our own, not a crate such as `postcard`, because Strata should be able to read and write it itself once bootstrapped (user). `src/binary.rs`, specified in `docs/binary-format.md`. LEB128 integers (zigzag for signed), one tag byte per enum variant, fields in order, strings by index into a table; canonical; corrupt input is an error, never a crash; no compatibility across format versions.
  - **Module files with a header** (built, branch `binary-header`, discussed with the user 2026-11-20: "header files from first principles, but inside the file"). One module file per module (now the `.strata` files themselves), or a bundle of them (`strata pack app.strata`). The header lists each definition's name, kind, `pub`, hash, interface hash, code hash, dependencies and size; each definition is self-contained (its own strings) and stores its interface (bodies as `()`) before its bodies. `store`'s hashes are now those of the binary encoding (no more printing to hash). Measured on `examples/tasks`: all headers 14 µs, all interfaces 82 µs, everything 166 µs (with each definition's hash checked), against 735 µs to parse the text. Files are larger than the first single-file format (27 KB vs 14 KB; 20 KB of source): three 32-byte hashes per definition, and strings repeated per definition. Not done yet: the tools don't use the header (they decode everything, then recompute hashes and the graph); see the next steps.
  - **Next steps, agreed with the user:** (5) read module files in parallel; (6) cache derived results (inferred types, check results) in `.strata/` by hash, and check a module against the interfaces of the modules it uses, re-checking dependents only when an interface hash changes; (7) a long-running process that loads once and reloads only files whose hash changed. Also: interned names in the AST (`Symbol(u32)` instead of `String`), only if profiling shows string handling is the cost.
  - **Binary is the format, `.strata` its extension** (user, 2026-11-20; built, branch `binary-main`). Packages and scripts store only binary module files, named `.strata`; nothing reads text as code any more. Text comes in only through edits: `strata edit` (stdin or the editor; outside a package, `strata --file F edit` writes a script or a folder's module without a log; since branch `script-edit-check` it then checks it, decided with the user: what doesn't check is still written, its errors printed, exit code 1) and `add` of a text file; `render` / `view` / the viewer print it, `render --split` writes `.st` text files that are never read back. `strata upgrade` rewrites each file as the bytes strata writes for it (it replaced `ci --fix`, user 2026-11-22). Git: `.gitattributes` marks `*.strata binary diff=strata merge=strata`; `setup-git` sets `strata render --file` as the textconv, so `git diff` shows text; the merge driver decodes the three sides, merges their text definition by definition and writes a module file, and a conflict leaves the file as text with markers until `strata resolve FILE`. The repository's `std/`, `examples/`, test data and the compiled prelude are binary (decided by the user: GitHub shows no diff for them). The log still carries each change's text (it is history, replayed by parsing). Open:
    - **changing the format** (decided by the user 2026-11-21): no backwards compatibility while the format isn't settled. `VERSION` stays `1`; a change to the tree converts every file in the repository in the same change (render with the old strata, read back with the new: docs/binary-format.md). Version numbers, and perhaps reading older versions, start once the format is settled. Each such change still touches every file, and other branches then conflict on binary files;

  - **Interned names** (built, branch `interned-names`): every identifier in the AST is a `Symbol` (`src/symbol.rs`), a `u32` into one process-wide table of texts; equal names are equal numbers. ## Ideas

### Language

#### Ranges, slices and comprehensions (built 2026-11-20)

Built on the binary-format branch (format version 3: `Expr::Range`, `Expr::Slice`, `Expr::Comp`); see docs/language.md. Decided along the way:

- `a..b` excludes `b`, `a..=b` includes it; a range is an eager `List[Int]` (iterators remain their own feature). Both ends are required, except in a slice.
- Slicing uses ranges, not Python's `:` (one syntax for both): `xs[a..b]`, `xs[..b]`, `xs[a..]`, `xs[..=b]`, on lists and strings, clamped as `slice` was. No negative indices: in a range `-3..0` already means the integers from -3, so `xs[..-1]` meaning "all but the last" would read two ways.
- `xs[i]` is the element, not an `Option`: `at(xs, i)` requires `0 <= i < len(xs)`, a runtime fault otherwise, and an obligation for `verify` like division by zero ("index in range"). `get(xs, i)` stays for the `Option`. Not yet: `d[k]` on dicts (the same, with "key present").
- Comprehensions: `[e for p in xs where c for q in ys where d]`, with `where` as in refinements; patterns allowed (`for (a, b) in ps`).
- The tree keeps them as written (they render back as written); `resolve` rewrites them into `range`, `slice`, `map`, `filter` and `fold` (`src/desugar.rs`), so the checker, prover and LLVM never see them. Error messages show the builtin calls.

Decided by the user 2026-11-21 (not built):
- The builtins behind the range and slice syntax (`range`, `slice`, the step) become special methods (`@range`, `@slice`, `@step`; see "Derived traits, `comptime` and special methods"): overloadable, implemented through std traits, but not called by name. Code uses the syntax.
- `map`, `filter` and `fold` are not special: they are ordinary methods on any iterator (the receiver), taking a lambda, and stay callable by name; comprehensions keep desugaring to them.
- `take` and `drop` stay ordinary functions (they have no syntax of their own; `xs[..n]` / `xs[n..]` remain the slice forms).
- Steps: `0..n by 2` (and `0..=n by 2`), desugared to `@step`. `by` becomes a keyword.

Still open:
- `xs where it > 0` as a filter on a value (it reads like a refinement type).

#### Other syntax nits (noticed 2026-11-20; not decided)

- **Dict and set literals** (built): `Dict { "a": 1 }`, `Set { 1, 2 }`, `Dict[String, Int] {}`, and comprehensions `Dict { w: len(w) for w in words }`, `Set { x % 3 for x in xs }` (`Expr::Dict`, `Expr::Set`, `Comp` with a `CompKind`; desugared to `dict` / `set`). In a `for` / `if` / `match` header they need parentheses, like record literals.
- **`except` inside a `for` header** reads badly: `for _ in 0..opts.times except { 1 } {`. Proposed: the renderer parenthesizes any header expression (`for`, `while`, `if`, `match`) that ends in a `}`: `for _ in 0..(opts.times except { 1 }) {`. The parser accepts both. Done instead (user's choice, 2026-11-21): `or { … }` / `??` for an `Option` (`Expr::Or`) and `except { … }` / `!!` for a `Result` (`Expr::Except`), each only on its own type, so `Result[Option[T], E]` isn't ambiguous. The short forms are what the renderer writes for a single-value, one-line fallback. So `for _ in 0..opts.times ?? 1 {`.
- **`len(xs)` and `xs.len()`** are both accepted, as for every builtin; the renderer could pick one form (method form for chains, say) so code reads the same everywhere.

#### Proven `ensures` narrow the result at the call site (raised by the user 2026-11-22; not decided, not built)

A function's proven `ensures` that ties the result's member to its inputs becomes the result's type where it is called, so a caller that knows something about the arguments gets the narrowed result without a `match` or an unwrap. `verify` already uses a callee's contract at each call site; what is new is the type checker narrowing with it. Since types are sets and refinements are types, `ensures o is Paid ==> it is Shipped` is the result's type at a call with a `Paid`: a return type that depends on the arguments, used by ordinary narrowing, `match` coverage and codegen (no tag check). Dafny, F* and Liquid Haskell let postconditions reach callers as proof facts; TypeScript's overloads and conditional types do the type half without proof; the two together, without type-level programming, is Strata's.

Examples:
- **Lookup after a membership test.** `fn get(self: Dict[K, V], k: K) -> Option[V] ensures it is Some <==> self.contains(k)`; inside `if users.contains(id) { … }`, `users.get(id)` is a `Some(User)`. One total function would do for both `get` and `at` (the `requires` that faults otherwise): callers that can show the key is there get the value, the others match.
- **State transitions (typestate in one type).** `fn ship(o: Order) -> Order ensures o is Paid ==> it is Shipped ensures o is Pending ==> it is Pending`; in a `Paid` arm, `ship(o).tracking` reads without matching again. No `ship(o: Paid) -> Shipped` beside a version for an `Order`.
- **Combinators that keep the variant.** `map_err(r, f) ensures it is Ok <==> r is Ok` (the user's first example, wrapping an error's message): after `r` is matched as `Ok`, a chain `r.map_err(wrap).map(normalize)` is still `Ok`.
- **Validation.** `parse_port(s) -> Result[Port, PortError] ensures all_digits(s) && 1 <= len(s) && len(s) <= 4 ==> it is Ok`: a literal or a checked string needs no error handling.

Proposed shape (Claude):
- Only a **proven** `ensures` narrows ("proven ⇒ no runtime check"): an unproven one would be unsound, or need a runtime check, i.e. a fault.
- **Two levels.** (a) Conditions the checker already decides: `param is T`, refinements, facts from `match` arms; the checker substitutes the arguments into the `ensures` (transitions, combinators). (b) Any condition (`self.contains(k)`, `all_digits(s)`): decided by the SMT backend at the call site, so the narrowing comes from `verify` or a cached proof, not the plain checker (lookup, validation).

Open questions:
- Does `if cond { … }` narrow on a proven condition (needed for the lookup), not just `match` and `is`?
- With `==>` only the `then` side narrows; does an `else` branch need `<==>`, and should the checker suggest it?
- How the narrowed type shows in the viewer and in `render` (hover on the call: `Shipped`, from which `ensures`).
- What a caller's narrowing depends on when the callee's body changes: a callee whose `ensures` stops being proven breaks its callers' types, so the proof is part of its interface (and of the interface hash).

#### Default values for record fields (built 2026-11-20)

`field: T = value` in a record (or a variant's record payload); see docs/language.md, "Records and defaults". Decided: any expression with no variables in scope (not the other fields), checked against the field's type where the type is defined, and evaluated each time it is used. It applies in constructors (`desugar::defaults` fills them in after resolution), JSON input (`std.json`'s derived `decode`), and the command line (a scalar field with a default is an option, `--times 3`; a `List` field's default is used when no arguments are left). Mocks and fuzzing still generate every field. Not done: defaults for other types (`type Port = Int where … = 8080`), which the user set aside; a flag whose default is `true` can't be turned off from the command line yet (`--no-x`).

### Web UIs (direction agreed with the user 2026-11-20; steps 1-4 built, each step's "Not yet" below)

The second place Strata should be useful, after the command line: UIs in the
browser, written without JavaScript. The direction is the Elm architecture,
run on the server, in the way Phoenix LiveView and htmx work:

```rust
use std.web.{App, Html, div, button, text, on_click}

type Model = { count: Int where 0 <= it }

type Msg = | Increment | Decrement | Reset

impl App[Msg] for Model {
  fn update(mut self, msg: Msg) {
    match msg {
      Increment => self.count += 1
      Decrement => if self.count > 0 { self.count -= 1 }
      Reset     => self.count = 0
    }
  }

  fn view(self) -> Html[Msg] {
    div([], [
      button([on_click(Decrement)], [text("-")]),
      text(f"{self.count}"),
      button([on_click(Increment)], [text("+")]),
    ])
  }
}
```

(The syntax is a sketch; traits with a type parameter like `App[Msg]` may
need work.)

`strata serve` keeps each session's `Model` in memory and renders `view` to
HTML. A small, fixed JS file that ships with the runtime catches clicks and
form submits. `on_click(Increment)` puts the message's JSON in an attribute;
the JS posts it back, and the server reads it against `Msg` (refinements
checked, as for command-line options), runs `update` and `view`, and the JS
swaps the new HTML into the page. (As built, step 3 below: three functions instead of a trait, and messages as numbered handlers rather than JSON.)

Why it fits: users write no JS; no async is needed in user code; `update` and
`view` are pure, so they can be tested without a browser and the verifier can
prove invariants across every message (`count >= 0`); an unhandled `Msg` is a
non-exhaustive `match`. The compiler's output is LLVM IR, so a wasm build
could later run the same app in the browser, without changing user code.

Steps:
1. `std.web.Html` (**built**, branch `worktree-web-html`): `Html[M]` (element,
   text) and `Attr[M]` (attribute, flag, event), helpers (`div`, `a`,
   `input`, …, `class`, `href`, `on_click`, …), `render` and `document`.
   Text and attribute values are escaped; names are checked where they are
   written (`element(tag: TagName, …)`, `attr(name: AttrName, …)`; `AttrName`
   excludes `on…` so inline scripts can't be written), not in the type:
   `Html[M] = { node: Node[M] }` and `Attr[M]` wrap private sums, so only
   `std.web` makes them and the verifier has nothing to check in views
   (decided with the user: verifying markup is pointless; what matters is
   the Strata values put into it, which JSX will make explicit); events are `data-on-EVENT` attributes holding the message as JSON
   (new builtin `to_json`). Void elements can't have children (`element`'s
   `requires`). CSS goes in `style_sheet(css)` (not escaped, can't close the
   element) or `style_link(url)`. Everything in `std` is proven, and so is
   `examples/page`. While `Html`'s fields were refined, the prover needed two
   changes in `smt.rs`, kept since they help any recursive or generic type:
   `check_type` stops at the third nested level of the same named type (a
   recursive type like `Html` made it re-check every element of every list,
   level after level: minutes for a small page), with one unknown per (type,
   value) so an assumed result and a later check are the same atom; and
   validity is compared on types whose unrefined type arguments are erased

2. `strata serve` (**built**, branch `worktree-web-serve`): `std.http`

**JSX-like syntax** (user: wanted at some point, for simplicity). Markup

- **Async first, or web first?** (user, 2026-11-20; undecided.) The web design
  above doesn't need concurrency in user code: the runtime handles it, and each

  (an LLM, an HTTP request): it would block the session, and with a sequential

## Design principles (decided)

- **No effects.** Capabilities (database, queue, console, clock) are traits; code takes an implementation as a parameter or holds it in a field. `mock T` generates an implementation that respects the trait's contracts. Iterators and concurrency are their own language features, **not** effects (concurrency: see "Concurrency: structured tasks without coloring"; it needs no capability, since tasks share nothing and `scope`/`spawn`/`await` are deterministic).
- **Immutable by default, mutable when declared**: `let mut`, field assignment, `mut` parameters and `mut self` with write-back to the caller's variable. Procedural code is normal, and there are no shared references.
- **Refinements are structural**; `type X = Y` with no `where` is an error, so use `distinct type` for a nominal type.
- **Modules meet only through their public (`pub`) contracts.** A folder of `.strata` files loads as modules, and `render --split` writes them back.
- **No backward compatibility.** Breaking changes are expected: never add shims so that older stored trees (`.strata/` objects) or old syntax keep working. Re-import from source instead.
- **Rendered code wraps at about 80 columns** by breaking lines, not soft-wrapping.
- **Viewer**: two levels (interface/source), the code view sliced around the selection, a type map as a separate view, and no Flow view.

## Decisions

### Verification: automatic theorem prover (SMT), with layered results
- Use an SMT solver (Z3 or cvc5) as the main verifier. Contracts (refinements, `requires` / `ensures`, trait laws) become proof obligations.
- Report one of four **layered results** per obligation:
  - `proven` (the solver proved it);
  - `fuzzed` (not proven, but no counterexample found);
  - `failed` (with the solver's or fuzzer's counterexample);
  - `assumed` (trusted: outside libraries, I/O).
  A project policy can require `proven` for chosen modules.
- **Loop invariants**: infer them where possible (e.g. bounds and accumulators). Explicit `invariant …` annotations only where they really help; agents may write them and the solver checks them. Plan and syntax: "Loops and invariants: what to build first" below.
- Callers are checked against a callee's **contract**, not its body, which fits modules meeting through contracts. Cache results by content hash, as `verify` already does.
- Suggested order:
  1. integer, length and string-format refinements;
  2. `requires` / `ensures` across calls;
  3. loop invariants;
  4. trait laws.

### Termination and helpers (decided with the user, session 3; built)
- Termination is reported for every function: terminates (with how) / may not terminate (with why) / assumed (`terminates` marker, after the contract). See docs/verification.md. The viewer shows "may not terminate" in orange; diffs show it in the verification word.
- **No `decreases` clauses** for now (user: a `for` loop covers the case where you can name the bound). Instead the bound is inferred. For `while a < b`, the solver tries `b - a` (and the other comparisons). For recursion, a smaller piece of a parameter is detected first. Otherwise candidate measures are tried (`termination::candidate_measures`): integer parameters, `len` of list or string parameters, both differences of each comparison of parameters in the body, then pairs compared in order (Ackermann). Not covered: mutual recursion, measures built from more than a difference (`n * n - k`), recursion through a lambda.
- **Helpers are seen through in contracts** when they terminate and cannot fail (`termination::analyze` → `transparent`): no `requires`, no refined parameters, no `mut`, no division by a non-literal, no `assert`, no hole, no refined constructors, and only such helpers or total builtins called. A helper whose termination is only assumed is still seen through, and the proof lists it. In function bodies, calls are still checked against contracts only.
- Policies: `--require terminates` accepts an explicit `terminates`; `--require no-recursion` rejects any recursion, even structural.

### Proven checks leave the compiled code (decided with the user 2026-11-22; built, branch `proven-checks`)
- **Principle** (user): what is proven at compile time is never checked again at run time; runtime checks stay only for what isn't proven, e.g. assumed code (outside code, capabilities), whose contracts can't be proven. Code that relies on assumptions but is itself proven needs no checks.
- **Where proofs come from**: `verify`'s cache. Then (user, 2026-11-22): `build` verifies first whatever changed since it was last verified (`store::unverified`: each definition's hash at its last verification, `ProofFile::verified`), quietly, with `strata verify`'s caches, and says how it went; a counterexample doesn't stop the build (its checks stay). `run` (the JIT) doesn't verify: it uses the cache; `build --no-verify` likewise. Scripts got a verdict cache too (with their proofs). `verify` writes `proofs.json` (package `.strata/`, or `~/.cache/strata/scripts/<path hash>` for a script): per function, the checks proven (with those true by the types alone, `Vc::given`) and those not (`open`: refuted, unknown, stopped), with the definition's closure hash; `build` / `run` use only entries whose hash is current (`store::current_proofs`).
- **Escape hatch** (user chose): `--all-checks` on `build` / `run`. Fuzzing, replay and the cross-check always compile every check: they are what catches a prover bug (#184's `break`).
- **How a compiled check meets its proof**: by name within the function, the text `verify --checks` prints (`assert e`, `ensures e`, `invariant \`e\` …`, `result of \`f\``, `assigning \`x\``, `` `let` annotated `T` ``, `constructing \`C\``, `index in range`; `llvm::same_check`). A check is left out only when every check of that name in the function is proven (at least one, none open). Sound as long as the prover sees every check site (it evaluates lambda bodies too); an unmatched name keeps the check.
- **Entry checks** (parameters' types, `requires`) are the callers' to prove: left out when every function referring to the callee proved the call, and nothing else refers to it (`llvm::Refs`: references from contracts, types, tests, impls, or a method call of the same short name keep them). `main` keeps its own.
- **`verify` before `build` had to be fast** (user: a first verify of a small program in seconds is unbearable). A script whose `main` ran a 7 s loop took 209 s to verify: the solver needed 0.1 s, the cross-check ran `main` 20 times with a step budget that a list's type check (in the runtime) never counted. Now a function without parameters is fuzzed and cross-checked once (every run is the same), and a list check counts a step per element when compiled for fuzzing: 0.5 s. A list check also shows the failing index only when an element fails (it made a string per element). Found on the examples: proofs were taken by a nested compilation made first (a pattern's matcher; only `Entry::Main` takes them now), and a record constructor's field checks didn't match its proof's name.
- **Measured**: a proven `List[Natural]` result checked on each call: 2.17 s → 0.04 s; a `requires` + `List[Natural]` argument per call: 6.7 s → 0.00 s; a plain bounds check in a hot loop: no difference (a predicted branch).
- **Not yet**: trait methods (their compiled names differ from `verify`'s labels; checks kept), std (precompiled once with its checks; its proofs could be kept with it), checks in the C runtime (division by zero, string indexes), the entry checks of a function `strata run f ARGS` calls (that probe isn't verified; it compiles without proofs).
- **Assumed code, only at the call** (user, 2026-11-22: what is assumed is the foreign code itself, not the code around it; built, branch `assume-foreign`): a function that calls C (`extern c`), lives in a module that declares externs, or takes a capability was reported as assumed as a whole (from the interpreter, which couldn't run C), so nothing in it was proven and its callees kept their entry checks (`fuzzy`'s `closest`). Now only the foreign functions and a capability's own methods (and mocks) are assumed: their contracts are taken at the call (and compiled code checks a C function's `ensures` there); the rest is proven and fuzzed as usual, C included, except that code taking a capability isn't fuzzed (nothing can make one: what the solver leaves is reported as skipped). `fuzzy`'s `main` and `wc`'s `wc` and `main` are proven; their builds leave out every check.

### Loops and invariants: what to build first (decided with the user 2026-11-22)
- **Studied on a real program.** An agent loop (the runner of an agent harness, in TypeScript) states its invariants in a comment: the conversation sent to the model starts with a user message of text only, and every tool result follows the tool use it answers; pruning keeps both. In Strata these are *data* invariants, not loop invariants: `type Conversation = List[Message] where …` (the comment's claim becomes `render`'s result type) and a `History` record refined over its messages and its two pruning indices. A declared type is already checked after every assignment and kept across every pass of a loop, so no loop needs an `invariant` clause. Stating "a tool result answers the message just before it" (local) rather than "some earlier message" makes pruning at a tool use obviously valid. Running the sketch: the fuzzer found that updating the two indices one field at a time breaks the record's refinement in between (assign the record whole); the scan loop's termination is proven; nothing else is, because list positions (`ms[i - 1]` next to `ms[i]`, slices, `any`, `all` over indices) are not modelled, and the fuzzer can't make a `History` (too narrow for random values).
- **Order** (user agreed): 1. a `break` leaves a `while` with its condition still true (unsound before: `ensures it >= 10` was "proven" for a loop that breaks at 3; only the cross-check caught it); built, branch `loop-break`. 2. list positions in the prover; built, branch `list-positions`. Not SMT sequences (they would need records and sums as SMT datatypes): an element of a list of a checked type is a `Template` whose unknowns are SMT functions of the position (`(v6 i)`), and of the outer positions for a list inside an element (`(v6 i j)`); `Shift` (slices, `take`, `drop`, `..rest`), `Concat` (`+`, `push`), `Rev`, literals, `range`, `map` and merged branches translate positions; `filter` / `sort` keep the old "some element" model. `all(xs, p)` known true is also a quantified fact over positions (`forall_positions`; unknowns made inside it are functions of its variable, and what it learns of lists stays inside), and `every` proves "all elements" by position where it can. `any` is `!all(!p)`. Left: a non-empty list as a counterexample (query the element functions), and nested quantified facts with strings (the agent loop's `answers`: Z3 times out on the 57 KB query; hand-picked instantiations at the positions the code takes, instead of MBQI, are the likely fix). 3. a fuzzer that can build values of narrow refinements (`History`); first part built (branch `solver-inputs`, user chose "ask the solver" over compiled generators): when random values can't be made, `Vc::inputs` asks Z3 for up to 20 different models of the parameters' types and `requires` (lists ≤ 6 elements, their first elements made by position, `input_elems`; each model blocked for the next; random seeds), run as one compiled module (`replay_all`). `render` and `shift` of the agent sketch are fuzzed now (were skipped). Few models come back once quantified facts are in the query (3-6 of 20); compiled generators for common patterns (sorted, consecutive, indices within a list) remain an option. Next: use `input_elems` for the solver's own counterexamples (it finds them but can't show a non-empty list). 4. inferred invariants (built, branch `loop-invariants`; `Vc::infer_invariants` for `while`, solved inline: `Vc::solver`; facts the declared types already give are left out; loops with `continue` since `loop-invariant-clause`; not inside a trial pass; examples: `isqrt` and tasks' `core.drain` proven, the agent sketch's scan in `shift` proves its indices, same CPU time): candidates from the loop condition and its non-strict forms, the `ensures` and later `assert`s (with `it` as the returned variable), `requires`, the body's `if`s and each changed variable against its entry value and the parameters; keep those true on entry, then drop those a pass doesn't keep until none is dropped (Houdini), so what remains is proven; reported as "inferred invariant: …", capped (~30 candidates).
- **Written invariants** (built, branch `loop-invariant-clause`): an `invariant e` clause between a loop's header and its body (one per line, like `requires` / `ensures`), for `while`, `for` and `loop`: proven on entry and after every pass and `continue`, assumed at the head (so after the loop with the condition false, not at a `break`), checked at run time at the loop head (on entry, after each pass, on leaving normally). In a `for`, it can't name the loop variable (user: a `for` rarely needs one). Stored as `Stmt::Invariant`, the first statements of the loop's body (a new tag, so no file conversion); `invariant` is a word only there. Inference treats written ones as given (joint induction: both are proven). Also built in the same change: `continue` keeps its state (`Vc::continues`, like `break`s), so loops with `continue` get inferred invariants and termination bounds (checked at every pass end).

### Values made as they are read, in the prover (decided with the user 2026-11-22; built, branch `smt-lazy-shapes`)
- **The problem.** `Vc::shape` made a value's symbolic form whole when it appeared (a parameter, a list element's template, a call's result, a variable after a loop): a record all its fields, a sum a tag plus the payload of *every* constructor, recursively to depth 3. For a wide recursive sum that is ~(fields × variants)^3 terms, cloned at every binding and branch: a loop over `List[Node]` with `Node` of 20 variants of `(Node, Node, Int)` took over 4 GB; `compiler/Expr` (35 variants) made a 30-line `merge_sort` over `List[(Expr, Expr)]` take 32 s and several GB.
- **Lazy parts.** A value's outer level is made at once (a record's fields that are plain values, a sum's tag); a field or payload that is itself structured (a record, sum, tuple or union) is a `Val::Lazy` cell, made the first time code reads it (`Vc::force`: a field read, a pattern looking inside, `is`, a refinement that reads it, a comparison with a made value). Cells are kept in `Vc::cells`, so a part is made once and every copy of the value sees the same terms. Each cell carries `valid`, "this part is a valid value of its type": `true` for a type without refinements, else an unknown defined (`valid = check_type(made part)`) when the part is made. Checking or assuming the validity of a whole value uses its parts' `valid`, so a parameter's guarantees reach a part when it is read, and a check never makes parts. The cost follows what the function reads; the depth cutoff is gone (a pattern five levels deep is proven with the payload's refinement).
- **Contexts.** A part is made in the context it was created in, not where it is read: its fresh unknowns are functions of the same positions (a list element's template: the cell keeps its facts with the placeholders, and each position's copy, `Make::View`, places them), with no path condition (they are facts about the value, true on every path), and its facts and unknowns go where its scope's are: a part of an outer value first read inside a quantified fact (`every`, `forall_positions`) is made as if outside it (`Vc::regions`), so it is not bound by that quantifier.
- **Merges and `==`.** Merging two branches merges made parts as before; two parts, one of them not made yet, become a `Make::Merge` cell (`valid` is `ite`), made when read. Comparing two such parts gives an unknown for their equality, defined (one level: tags equal, and the parts' parts compared the same way) once both are made. Making the other side instead would not end: a tree merged or compared with its own subtree (`if c { t } else { t.left }`, found on `std.regex.translate`, which took over 4 GB that way) pairs each subtree with the one below it. A part compared or merged with a value built by the code is made (one level per level of that value). So `a == b` costs nothing until the code looks inside, and then says exactly what it did before. Inside a template or a position-quantified fact, where such unknowns can't be kept, comparing makes both sides, to a depth of 4. Calls whose arguments have recursive types are now remembered too (the key no longer contains an `Opaque` cutoff).
- **Size budget.** At most `MAX_CELLS` (200,000) lazy parts per function; past it a part is `Opaque` (any value), with the reason. No proof of std or the examples comes near it. Refinements that read through a recursive type stay bounded by the existing contract nesting limit.
- **Counterexamples.** A part the solver's model doesn't cover (never read) is shown as the simplest value of its type (`some_literal`); the replay checks it, as for any model.
- **Termination analysis follows the selection.** `termination::analyze` takes the roots (the functions `verify NAME` checks) and runs the costly loop and measure proofs only for what they reach; others are left unknown (and not transparent). With no selection, all as before.
- **Left**: a refinement that calls a function with a `requires` is evaluated, when a part is made, without its call site's path condition (as a parameter's always was); `refresh` and `havoc` of a generic record still use the record's name without its type arguments.

### Exact rationals as the default number (`Real`; raised by the user 2026-11-22; open, not started)
The user's idea: decimal literals and default arithmetic as exact numbers that grow when they need to, as `Int` grows into a big integer, with `Float` kept as a type of its own, as sized integers (`I8`) are. In practice "real" means exact rationals (`p / q` of big integers): `+`, `-`, `*`, `/` and comparisons are exact (`0.1 + 0.2 == 0.3`); irrational results (`sqrt`, `exp`, `sin`, π) can't be.
- **Why**: the prover would model them exactly as SMT `Real` (linear real arithmetic is decidable and fast; nonlinear is decidable, slower, far better than bit-blasted floats), with division by zero the only fault (checked by `y != 0`, as for `Int`). Number code becomes verifiable as integer code is, and `0.1` means one tenth.
- **`Float` is not a refinement of `Real`**: `I8` is `Int` with a range check because its operations are `Int`'s; a float's are not (each rounds: `0.1` itself isn't a `Float`). So `Float` stays its own type, its operations defined as "the exact result, rounded to the nearest double, a fault past the largest", with an explicit conversion `to_float(r) -> Option[Float]` (`None` out of range); an evaluator could then run float arithmetic as exact arithmetic plus that one conversion.
- **To decide**: irrational functions (only on `Float`; with a precision, `sqrt(x, digits: 20)`; or, as Pyret, which has exact rationals by default, "rough" numbers whose `==` is refused); how `1/3` prints (`print`, f-strings, `{x:.2}`); JSON (exact decimals read exactly), FFI (`double` converted explicitly), the fuzzer's generators.
- **Costs**: small rationals are 10 to 100 times slower than hardware floats, and unlike `Int` they grow in ordinary use (100 compoundings of `x * 1.07`: a 200-digit denominator; Newton's method doubles the digits each step), so numeric code would say `Float`. Effort about that of big `Int`s: the type and literals, rationals over the runtime's big integers (normalized by their GCD) with a small-value fast path, code generation, the prover's mapping (the easy part, and the largest gain), std, examples and recorded outputs migrated.

### Values as SMT datatypes (discussed with the user 2026-11-22; not started, the next step after lazy shapes)
The prover builds values out of plain solver variables, one per field: a record is its fields, a sum is a tag plus the payload of every variant, and since list positions (PR #190) a list element is a template of functions of its position, one per field. Lazy shapes (branch `smt-lazy-shapes`) build those parts only when the code reads them, within a size budget, which fixed the blowup on wide recursive types (`compiler/Expr`: a 30-line loop over `List[(Expr, Expr)]` took 32 s and several GB). The next step, which the user judged cleaner: records, sums and unions as Z3's algebraic datatypes (`declare-datatypes`), so a value is one term, never expanded.
- **What the solver then knows by itself**: constructors (`(Node l v r)`), testers (`((_ is Node) t)`: `match` and `is`), selectors (`(left t)`: field access), structural equality at any depth (`Leaf != Node(..)`, equal values have equal fields) and well-foundedness. The theory is decidable and combines with the integer arithmetic already used. Mutually recursive types (`Expr`, `Stmt`, `Pattern`) are declared together; generic ones are parametric (or one instance per type argument).
- **What it gains over lazy shapes**: complete `==` on structured values (lazy shapes compare only what was built); no size budget (whatever the code reads is one more selector); values that keep their facts through loops and `mut` calls (today they are refreshed, keeping only their type's guarantees); counterexamples as whole values, shown as Strata literals and replayed by the fuzzer's cross-check; query size following the code, not the types; no "not modelled" cases for recursive or generic types; unions and sums one mechanism. With it, list elements of records and sums become single terms `(elem i)` instead of a template per field (what #190 left out: "records and sums would need SMT datatypes to go into SMT sequences"), and lists can then become Z3 sequences.
- **Refinements, asserted per selector**: a term carries no facts, so a type's guarantees must be stated. "`t` is a valid `Tree` of `Positive`" holds at every depth, which said once would be a quantified axiom (`forall t. valid(t) = ...`) or a recursive definition (`define-fun-rec`): outside the decidable fragment, answered by heuristics that may say `unknown` or time out. Instead, each selector the translation introduces gets its level's facts when it is introduced (`(> (val t) 0)` for `(val t)`, and validity for `(left t)` as a new term): a function only ever reaches finitely many sub-values, and facts about a whole recursive value come from contracts (a recursive call is assumed to meet its own). Quantified facts stay only where unavoidable: refinements written as recursive predicates, and `all(...)`, which #190 already makes a quantified fact (with a known Z3 timeout on nested quantified facts with string comparisons, the agent loop's `answers`: smaller queries should help there).
- **Cost**: a rewrite of `smt.rs`'s value model (`Val::Rec`, `Val::Sum`, `Val::Union` become terms; `shape`, `refresh`, `check_type`, patterns, unions, equality, the element templates of lists), datatype declarations per query (grouped for mutual recursion), reading models back for counterexamples. About the size of the original translation. Done when every verdict lazy shapes give is unchanged (std, the examples' functions, the cli tests), then the cases they can't decide.
### Integers and floats (decided, user, session 3)
- **`Int` is a big integer that is a machine integer while it fits** (like Python). Built: `Value::Int(i64)`, and `Value::Big(BigInt)` only for a value that doesn't fit (so equal numbers are equal values); arithmetic switches over on overflow, and a literal too large for 64 bits is `Expr::BigInt(digits)`. Integers beyond 64 bits are written to JSON as strings of digits (serde_json can't write larger numbers without `arbitrary_precision`, which breaks deserialising the internally tagged verdicts); they are read from a number up to 2^64 - 1 or a string. An integer pattern must fit in 64 bits.
- **Sized types live in the standard library as refinements of `Int`**: built in the prelude, `I8` … `I64`, `U8` … `U64`. They are verified like any refinement, and LLVM compiles each to its own width.
- **`Float` is `F64`**; `F32`, `BF16` and similar exist alongside, with their own LLVM representations. (Floats are not modelled by the prover yet; SMT-LIB has a floating-point theory for when they are.)

### Compilation before transpilation
1. **Native compilation through LLVM** to machine code, with a garbage-collected runtime (no borrow checker in Strata). This comes before transpiling.
   - **Step 1 (built, branch `llvm-backend`)**: `strata build` (`src/llvm.rs`) writes LLVM IR as text from the elaborated program and compiles it with `clang` and a C runtime (`src/llvm/runtime.c`); no LLVM library is linked into `strata`. Scalars (`Int` as `i64`, `Float`, `Bool`, `String`, `()`), functions, control flow, `match` on literals / conditions / refinement types, f-strings, a few built-ins; contracts checked at run time with the interpreter's messages. `tests/build.rs` ran each program both ways and compared (now against recorded outputs, `tests/data/build/expected`). See docs/tools.md. Everything below up to "The interpreter deleted" was written while the interpreter existed; it was deleted in #192, so compiled code is the only way code runs.
   - **Parity with the interpreter, so the JIT can replace it** (user, 2026-11-21; one stacked PR per item; all built, and the interpreter is gone): (1) the small refusals; (2) unions beyond records and variants (`Int | String`), and branches whose values are laid out differently; (3) trait-value methods that mention `Self`, have type parameters of their own or a `mut` parameter, generic supertraits, returning a trait-typed value; (4) regexes (`matches`); (5) big integers; (6) `mock`; (7) `strata test` on the JIT (faults that return instead of exiting, captured output, compiled `test` blocks); (8) `strata verify` on the JIT (calling any compiled function with values, through JSON; a step budget). Later: `serve` (needs an FFI and a network library), `derive`'s compile-time evaluation (the same JSON bridge plus a step budget; the specialization is Rust already), a cache of compiled code (the JIT's `-O2` costs ~0.3 s on a medium program).
     - **(1) built** (branch `compile-small-gaps`): a field of a union of records at different places in each member (by the variant; one without it faults as the interpreter does), assigning a field of a union or a tuple (`pair.0 = …`, also added to the interpreter, which faulted `cannot assign`), any pattern in a `for` over a range, `==` on trait values (an equality entry in the table: the same implementation's, else unequal), the `stack:` line of a fault (`strata_enter` / `strata_leave` around the program's functions, not the compiled prelude's or lambdas, as the interpreter's), and running out of stack is `fault (Limit): stack overflow (recursion too deep)` instead of a crash.
     - **(2) built** (branch `compile-unions`): a union with members other than records and variants is a pointer: records' and variants' blocks as they are, any other member in a box `{ tag, value }` with a tag per member type, unique in the program (so a smaller union's values are a larger one's unchanged). Values are boxed where they flow into a union (`coerce`) and unboxed where the checker narrowed them (an arm's matched variable: `expr` reads the node's type). Type patterns and `is`, literal / list / tuple patterns (the member first), `==`, printing, dropping, refinement checks of a union-typed value (`-1 is not a `Positive | String``), and trait methods on a union (by the member; not a `mut self` one, which would write a member back where the union goes). Found in the checker, then fixed (branch `checker-union-fixes`): a declared type is the variable's, not its first value's (`mut u: Int | String = 3` made `u` an `Int`, so `u = "text"` was refused), and `List[Int]` is a type pattern (`CtorPat::Type`, the arguments in brackets, also what `match comptime` writes as `Option[x]`; it was parsed as a constructor's arguments and printed `List(Int)`).
     - **(3) built** (branch `compile-dyn-methods`): methods called on trait values that take or return `Self` as a whole type (the table's wrapper unwraps a `Self` argument, which must be of the same implementation, and wraps a `Self` result into a trait value), that take a `mut` parameter besides `self` (a slot through the table, written back), or that have type parameters of their own (a dispatcher per call's type arguments, switching on the pair's table among every table of the trait; dispatchers are made once the queue is empty, and again while new tables appear); methods of a generic supertrait (`super_sub` reads its arguments from `supers`); functions returning a trait-typed value. Still refused: `Self` inside another type (`List[Self]`, `Option[Self]`), and type parameters together with `Self` or `mut`. A `Self` argument on a trait value is refused by the checker (decided with the user 2026-11-21, branch `dyn-self-args`): `xs[0].bigger(xs[1])` could pass a `Ci` to `Sq`'s `bigger`, so it is an error with a `help:` (declare the parameter as the trait, `other: Shape`, to take any implementation; that is how the two meanings are told apart: `Self` is the receiver's own type, the trait's name any). Allowed: the receiver variable itself, or what methods returning `Self` make of it (`s.bigger(s.scaled(2))`). The table's check at run time stays (a `mock`).
     - **(4) built** (branch `compile-regex`): `matches(s, re)` with a literal pattern is compiled to a DFA when the program is: `regex-automata` (the engine under the interpreter's `regex`) builds `^(?:re)$`, and its states reachable from the start become tables (each byte's class, the next state of each (state, class), dead states, states that match at the end) that `strata_dfa_match` runs; Unicode classes work as in the interpreter. A bad pattern faults with the interpreter's message. Refused: a pattern built at run time (it would need a regex engine in the runtime; with a Rust runtime, `regex` itself), and a pattern whose DFA gives up (Unicode word boundaries) or passes 4M cells. Also: functions shown as values (`"<closure (x) -> …>"`, `"<fn twice>"`, as the interpreter), so `examples/page` compiles.
     - **(5) built** (branch `compile-bigint`): an `Int` in [-2^62, 2^62) is a machine integer as before; any other is a big integer, a pointer kept in the 64-bit values outside that range (above it for positive ones, below for negative ones), so indices, lengths and counts are unchanged, a big index is simply out of range, and comparing a small with a big integer needs no call. `+`, `-`, `*` stay inline when both operands and the result are small (their two top bits equal), else call the runtime; comparisons and `==` call it only for two big integers; `/` and `%` (Euclidean, as the interpreter's), printing, `float` (rounded to nearest, ties even; too large faults as the interpreter does), `floor` / `ceil` / `round` (exact), `parse_int`, literals and `Int` patterns handle big integers. The runtime's arithmetic (32-bit digits, schoolbook multiplication, bit-by-bit division) was checked against Python on 3,000 random cases. Big integers are counted and freed as any other object (decided with the user 2026-11-21, branch `free-bigints`): `counted` is true for `Int`, and each dup / drop of one is `@strata.int_dup` / `@strata.int_drop`, an inline test (`v + 2^62 < 0`) before calling the runtime, so a small one costs a compare and a branch (a loop of small arithmetic: about 3% slower). New `Int`s (arithmetic, `/`, `%`, big literals, `parse_int`, `floor`, generated ones) are temporaries; lists of `Int` copy their big elements as objects (`dup_slots` kind 2); a big integer's block comes from `strata_alloc`. A number literal is a constant (never counted).
     - **(6) built** (branch `compile-mock`): `mock T` is a trait value whose table's methods generate their results, as the interpreter's `mock_call`: `requires` checked (its fault is the interpreter's), then a value of the result's type generated until `ensures` holds (200 tries). A generator per written type and hints (`gen_fn`), as src/generate.rs: integers from the intervals the refinements allow (often their ends, or 0), lengths likewise, strings matching a refinement's regex (32 samples made when compiling, one picked at run time), unions by a member, variants by choice (the one with fewest fields past depth 3), trait types as mocks, and rejection until the refinement holds (300 tries). A mock's table is among its trait's tables, so dispatchers cover it. The random numbers are the runtime's (splitmix64 from 7).
     - **(7) built** (branch `jit-tests`): `strata test` compiles the tests with the JIT by default (`--interpret` to not; `--jit` says why when it can't, and they are then interpreted; `--emit-llvm` prints their IR). Each `test` block is a function (`strata.test.N`, no frame on the call stack); `strata_test` runs one with a trap armed, so a fault `longjmp`s back with its kind, message and stack instead of exiting, and what it prints is kept; each starts as the interpreter's (no stack, the generators' numbers from the start). The report is printed by Rust, the same for both. Found and fixed on the way (the `tasks` example had never been compiled, having no `main`): a parameter of a generic trait type (`mut queue: Queue[P, E]`) wasn't compiled per implementation as a plain trait's is (`is_trait` wanted no arguments), so a `mut` argument went in as the value where the callee wanted a trait value; and a constructor or type pattern on a trait value (`match worker.console { Log { lines } => … }`) compared the table with a tag, so it never matched (it now compares the pair's table with the implementation's, then matches the value). A crash now prints the program's call stack (`crash (signal 11) in:`).
     - **(8) built** (branch `jit-verify`): `strata verify --jit` fuzzes compiled. A driver per function (`compile_fuzz`: free functions, generic ones at `test_instance`, not methods nor what takes a function) generates the arguments with `mock`'s generators, records each as JSON, and calls the function; all drivers are one module, compiled once (`jit::fuzzers`; the engine lives as long as the process), and `fuzz_limited` runs a case through `strata_fuzz` (the test trap, seeded, a step budget) when the function has a driver, under a lock (the runtime's state is global; verify's jobs are threads). The verdicts are `fuzz_limited`'s: an unmet `requires` of the function itself is a discarded case, a generator that can't satisfy a type skips, a hole is incomplete, any other fault a counterexample. Compiled code counts steps only in this mode (each loop iteration and call; 50M without a budget, the cross-check's 200,000 with one). The SMT solver's counterexamples were then still replayed by the interpreter; since `verify-compiled` they are replayed compiled (below). Decided with the user (2026-11-21, branch `verify-jit-default`): compiled is the default (`--interpret` to not, `--jit` says why when it can't; the inputs are the runtime's random numbers, which is fine), and a runaway case stays `too many steps`: `verify` runs code on inputs it made up, so a budget is its own rule, unlike running a program.
     - **No limits on loops and recursion** (decided with the user 2026-11-21, branch `no-limits`): neither the interpreter nor compiled code stops a `while` / `loop` or a `range` at a count (the interpreter's 1,000,000) or a recursion at a depth (its 2000). Like Python's `RecursionError`, but where the memory ends rather than at a set depth: a recursion runs until the stack is nearly out, then faults `fault (Limit): stack overflow (recursion too deep)`. The interpreter checks the stack left at each call (`stacker::remaining_stack`, 256 KB kept; on its 1 GB thread about 95,000 calls deep); compiled code catches the guard page (SIGSEGV or SIGBUS, on the running thread's own stack, so the JIT on strata's 1 GB thread goes about 33M deep and a native binary's 8 MB main thread about 260,000), as `strata_fault`, so a test's trap catches it too. The `stack:` line shows a recursion as one entry: `main -> down (95846 times)` (four or more calls in a row; compiled code keeps runs, not frames). `verify` keeps its step budget (`too many steps`): it runs code it generated inputs for, not the program. Lists are still copied when read. Open: a native binary could run its `main` on a larger stack, as the JIT does, so the depth doesn't depend on how the program is run.

### Foreign functions: `extern LANG` (decided with the user 2026-11-21; `extern c` built, steps 1-3 below; `std` SQLite and other languages not built)
One declaration form for every foreign language, `extern LANG fn ...`, with two mechanisms behind it:
- **`extern c`**: an in-process call through the C ABI. First, because the rest builds on it (SQLite, then the ORM).
- **`extern python` / `extern ts` / `extern rust`**: calls whose values cross as JSON, through the derived `Json` trait (PR #100, branch `json-trait`), not today's tagged debug form. That trait's mapping is what those ecosystems already produce: `Option` as the value or `null` (Pydantic `Optional`, TS `T | null`, serde `Option`), a sum's variants tagged with a `"type"` key (TS discriminated unions, Pydantic `Field(discriminator="type")`, serde `#[serde(tag = "type")]`), records as plain objects. So types and codecs on the other side can be generated (Pydantic models, TS types or zod, serde structs) and match exactly. A type crosses only if it is `Json`, as only FFI-safe types cross `extern c`: the derive is the check. Results are decoded against the declared type, refinements included, so a foreign function that breaks its contract is a fault at the boundary (a NaN from Python is a decode error, as `Float` is never NaN). `extern rust` can be a generated serde shim exported with the C ABI, i.e. `extern c` underneath. Python and TS run first as a subprocess speaking JSON lines (isolated, works without the JIT); embedding libpython / a JS engine later if speed asks for it. Open: large data (a NumPy array copied as JSON is slow): opaque handles to foreign objects (`extern python type Model`), or a binary path later; integers beyond 2^53 for TS (see the `Json` entry).

`extern c`:
- **Declarations, one at a time**: `extern c fn sqlite3_open(path: String, mut db: Sqlite3) -> I32`, `extern c type Sqlite3` (an opaque handle, only passed back). Each is its own definition (hashed, rendered, diffed like any other). Libraries are named in `strata.toml` (`[native] libs = ["sqlite3"]`, perhaps C files of the package to compile in as shims).
- **Types that cross**: the sized integers (`I8` … `U64`, as C's `int8_t` … `uint64_t`; plain `Int` doesn't, its size isn't fixed), `Float` (`double`), `Bool`, `String` (a NUL-terminated copy each way; a NUL inside is a fault), `()` (`void`), `extern c type` handles. A `mut` parameter is an out-pointer (`mut db: Sqlite3` is a `sqlite3**`), which is what `mut` already means: copy in, copy out. Not at first: structs by value, callbacks, buffers.
- **Contracts are assumed**: `requires` is checked before the call, the result's type and `ensures` after it (at run time: foreign code can lie). Never proven, never fuzzed: a function that reaches an extern is reported like one that reaches `host_*` ("it talks to the real system").
- **Capabilities (option b, user's choice)**: externs are called only from inside their own module, a module of extern declarations; that module turns them into a capability (a trait and its real implementation, as `std.fs` does with `Files` over `host_*`), and everything else works through the capability, so a signature still shows what code can touch. How a program gets the real implementation: see "Capabilities given to `main`" (revised with the user 2026-11-21).
- **Capabilities given to `main`** (decided with the user 2026-11-21; step 1 built, branch `capabilities`: `capability trait`, `capability Name { ... }` (expanded by `resolve` into a type with no constructor and an `impl` whose functions get an implicit `self`), `main` and tests asking for them (compiled: a null pointer, never counted; interpreted: an empty record), `verify` reporting their code and what takes one as assumed, the viewer's colour. Step 2 built, branch `capabilities-std`: std's `Console`, `Files`, `Environment` are capability traits and `Terminal`, `Disk`, `Process` capabilities; `main` (and `handle`, `init`, `update`) names `Disk` / `Process` and gets `Console` (the terminal) from the environment; the Rust table and `HOST_TYPES` are gone; a trait's method is found on a value of a type implementing it without the trait imported (`disk.read(path)` with only `Disk` imported). Step 3 built, branch `capabilities-env`: `[run] mode = true` in strata.toml lets `main` and tests ask for `RunMode` (std.process: `Running`, `Testing`, `Tracing`; hidden otherwise, with an error saying how to allow it); a test may ask for `Console` (the terminal, its output the test's own: the runtime's `host_write` keeps it while a test runs, as `print`'s); `--trace` already records the console's calls with their text and what `read_line` returned, so no separate recorder was added. Replaces the "private constructor" idea above.
  - **`capability trait`**: an interface to the outside world (`Console`, `Files`, `Database`). Anything may implement one (fakes for tests do); the marker says what it is for.
  - **A capability** (proposed syntax `pub capability Sqlite { pub fn open(path: String) -> Result[SqliteDb, SqlError] { ... } }`): a named set of functions that reach the outside world, with no data. Only the runtime makes one, only for an entry point; no constructor, no JSON, no `mock`. Its functions are called on the value (`sqlite.open(path)`), never on the name, so holding the value is the permission. It may implement capability traits (`pub capability Disk {}` with `impl Files for Disk`), which covers std's `Terminal`, `Disk`, `Process` and removes the table hard-coded in Rust (`capability()` in src/cmd/run.rs, the compiler's entry).
  - **`main` names concrete capabilities** (`fn main(opts: Options, sqlite: Sqlite, postgres: Postgres)`) and picks among them in ordinary code (an option chooses SQLite or Postgres), handing the rest of the program a capability trait value (`add_todo(mut db: Database, ...)`). The program's signature lists everything it can touch, used or not.
  - **Only `Console` is chosen by the environment**: `fn main(mut console: Console)` gets the terminal under `strata run`, a fixture in tests, a recorder under `--trace`. The run mode is an implicit parameter of `main`, not visible by default; a flag in `strata.toml` (name to settle) lets `main` ask for it to see or override the choice. No `default` implementations otherwise. `Files` and `Environment` are named concretely by `main` (breaking `examples/wc`, `tasks`, ...).
  - **Syntax** (decided with the user 2026-11-21): capabilities are ordinary parameters (`sqlite: Sqlite`), in `main` as anywhere; no effect lists and no separate `with` clause for entry points. The declaration has its own keyword (`capability Sqlite { ... }`), and the viewer colours capability names (and capability traits) differently from types, wherever they appear.
  - **Libraries**: a capability is only *made* at an entry point; a library with no `main` defines capabilities and code that takes them as parameters (`pub fn migrate(sqlite: Sqlite, ...)`), and the program passes its own on. A library's `[native]` C is linked into every program that depends on it (once `[deps]` are fetched). Tests may ask for real capabilities like `main` (decided with the user 2026-11-21): `test "opens a file" (sqlite: Sqlite) { ... }`, for a library's integration tests; a test that doesn't ask uses fakes through capability traits.
- **Only compiled code calls them** (user's choice: no libffi). `strata build` declares them in the IR and links the libraries; the JIT loads the libraries and resolves the symbols. (With the interpreter gone, compiled code is all there is.)
- **In the tree**: `DeclKind::Extern` added as the last tag, so existing files stay readable (no re-encoding).
- **Later**: the `host_*` layer as `extern c` declarations over `runtime.c`, instead of hand-written cases per builtin (`stdlib.rs`, `llvm.rs`, `jit.rs`).
- **Order**: (1) syntax, tree, binary format, checks (FFI-safe types, externs not `pub`, callers in the module only); **built** (branch `ffi`): `DeclKind::Extern`, the checks, and `verify` reporting anything that reaches a native module as assumed (step 3 done early, since generating a handle crashed the fuzzer); (2) compiled calls, `build` and the JIT, libraries from `strata.toml`: **built** (branch `ffi-calls`): `[native] sources / libs`, conversions in `llvm.rs` (`foreign_call`), the JIT compiling the sources into a library with clang and loading it, `Option` of a handle for NULL (needed for out-pointers: a `mut` argument must start as something), `examples/fuzzy`; (3) `verify` (built with (1)); (4) `std` SQLite behind a `Database` capability; (5) `extern python` over JSON, then TS, then Rust.

### Derived traits, `comptime` and special methods (decided with the user 2026-11-21; steps 1-3 built; special methods not built)
Command-line options need code made from a record's fields; so will JSON codecs for compiled programs and the ORM. Instead of a hidden Rust generator (`src/cli.rs` today) or general metaprogramming over syntax trees, a trait can say how each of its methods is derived, as ordinary Strata code specialized per type at compile time (as Zig's `comptime` does). A derive returns a real function, never a syntax tree.

```rust
use std.typing.{Record, Field}

/// A record whose fields are a program's command-line options.
pub derivable(t: Record) trait CommandLine
  requires all(t.fields, f -> is_option_type(f.type)) {

  derived fn from_args(args: List[String]) -> Result[Self, CliError] {
    given := parse(comptime t.fields.map(spec), args)!
    t.try_make(f -> read(f, given))
  }

  derived fn help(program: String) -> String {
    help_text(program, comptime t.doc, comptime t.fields.map(spec))
  }
}

fn read(comptime f: Field, given: Given) -> Result[f.type, CliError] {
  match comptime f.type {
    Bool => Ok(given.has(f.name)),
    Int => parse_number(given.text(f.name)),
    ...
  }
}
```

- **`derivable(t: Kind)`**: parentheses, not brackets: `t` is an argument, a compile-time value describing the type derived for (`Self` is that type, `t` describes it). Its type is a kind from `std.typing` (`Record`, `Sum`, `Choice`: a sum whose variants carry nothing); deriving for another kind of type fails at the `derive` line. `requires` states finer conditions as a contract checked at compile time, naming the offending field.
- **`derived fn`**: a method with an ordinary body, specialized for each type it is derived for. A method without `derived` is a default method, or one the user must write.
- **Using it**: `derive CommandLine for Options`, or `derive CommandLine for Options { fn help(program: String) -> String { ... } }` to write some methods by hand (as overriding a default method). After specialization it is exactly an `impl` with those bodies: no inheritance, no relationship at run time. `impl CommandLine for Options { ... }` with every method written also works: it is an ordinary trait.
- **`std.typing`**: ordinary types describing types, imported when writing a derivable trait (like Python's `typing`): `Record` (`name`, `doc`, `fields`), `Sum` / `Choice` (`variants`), `Field` (`name`, `type`, `doc`, `default`), `Variant`. `t.make(f -> ...)` builds a `Self` from a function giving each field's value (applied once per field, at compile time; each result must have that field's type); `t.try_make(f -> ...)` does it with a `Result`, stopping at the first `Err`. The syntax tree is only read through these descriptions. Self-hosting (user, 2026-11-21): `std.typing` should be the type-declaration part of the eventual syntax-tree module (`std.ast`) the compiler in Strata needs, not a separate model, so the self-hosted frontend reuses `Record`, `Sum`, `Field`, `Variant` and a derive reads the same structures the compiler does.
- **`comptime`**: on expressions (`comptime t.fields.map(spec)`: evaluated at build time, the result put in the program), functions, and parameters (`comptime f: Field`: the function is compiled once per value, so `f.type` is a real type in each copy). `match comptime f.type { ... }` keeps only the matching branch. Compile-time code can't take capabilities (so it is deterministic, which the type system already shows) and must terminate (proven by `verify`, or within a step budget, else the build fails saying so). Not for generics: type parameters already do that.
- **Checking**: a derived body depends on the type, so it is checked when it is specialized, at each `derive ... for T` (as Zig and C++ templates are); errors point at that line and the field. The kind and `requires` catch most mistakes first. Less powerful than generating trees (a derive can't change a signature or add top-level definitions), which keeps derives tame.
- **Special methods, marked `@`**: value-level specials are methods with a reserved `@` name, declared in std traits and implemented like any trait method: `trait Add[Rhs, Out] { fn @add(self, other: Rhs) -> Out  law associative(...) }`, then `a + b` on such a type. Also `@mul`, `@neg`, `@index`, `@call`, `@iter`, ... For a numpy-like library: generic numeric code (`T: Add[T, T] + Mul[T, T]`) and laws `verify` checks. In the tree a special method is a function with a kind (an enum), not a magic name: the checker enforces each kind's shape, `a + b` and a call of `@add` are the same node, and the text is only one rendering of it.
- **Order of work**: (1) the syntax (parser, printer, binary format) and the checks; (2) the specialization: `std.typing`, `comptime` (run while checking: first by the interpreter, now compiled on the JIT), producing ordinary `impl`s that everything after it (checker, compiler, prover) sees unchanged; (3) `CommandLine` written this way in `std/cli.strata`, `main` calling `from_args`, and `src/cli.rs` removed (its messages and `--help` text kept exactly; tests compare the old and new on the same arguments). Then options compile. Special methods and operator overloading after.

### Long-term goal: self-hosting
The compiler should eventually be written in Strata. Gaps to close first:
- **Native compilation** (built: `strata build` through LLVM, and the JIT for everything that runs code; the interpreter, too slow to run a compiler, is gone).
- **Efficient mutation of collections**: in-place updates when a value has a single owner (as in Swift / Koka), instead of copying. Reference counting is built; reuse (Perceus) is not yet.
- **String and byte primitives** (built): a string's units (`s.bytes()`, `s.code_points()`, `s.graphemes()`), positions as byte offsets (`byte_len`, `byte_at`, `byte_slice`), bit operators (see "What iterating a string yields").
- **Early `return`, and `!` / `?`** to propagate errors (built).
- **A small native runtime**: GC (reference counting, built), I/O (the `host_*` layer, built), threads for tasks (built), and binding to the SMT solver (not built: the solver is still a process per query).

Bootstrap plan: write the frontend (lexer, parser, printer) in Strata and test it against the Rust one, then the checker, then compile the Strata compiler with itself and check that its output stops changing (a fixed point).

**`std.regex`: our own regex engine, in Strata** (decided with the user 2026-11-21; built, steps 1-5 below). A self-hosted compiler can't use Rust's regex crates, so regexes get a library written in Strata, used language-wide (programs call it like any std module) and by the compiler. It replaced, one use at a time: `regex` (the interpreter's `matches`), `regex-syntax` (parsing patterns for the prover, the generator and the code generator), `regex-automata` (DFAs for literal patterns in compiled code, and the inclusion / disjointness facts of `regex_relations`) and `rand_regex` (generating matching strings for the fuzzer and `mock`). It also gives compiled code patterns built at run time, which were refused because they needed an engine in the runtime; the runtime stays small (C), since the engine is ordinary compiled Strata.
- **The engine is the definition of Strata regexes**: compiled code, prover and generator all follow it. Rust's crates are only the reference it is tested against (`regex`, `regex-syntax`, `regex-automata` and `rand_regex` are dev-dependencies, used by `tests/regex.rs` only).
- **The full dialect stays**, word boundaries and anchors anywhere included (user: the library is for every program, not only for compiling). Parts that can't do a feature say so, as now: the DFA builder refuses Unicode `\b`, the prover leaves it unknown, the Pike VM runs everything.
- **Design**: a parser into a Strata syntax tree with the Unicode semantics (`\d`, `\w`, `\s`, `\p{..}`, `(?i)` folding); a Thompson NFA run by a Pike VM (linear time, no backtracking; captures, `find` and `replace` possible later, which a DFA can't give); a DFA builder (subset construction over character or byte ranges) for literal patterns and for products of two patterns; a generator; the SMT translation reads our tree instead of the HIR.
- **Unicode tables**: a `std.unicode` module generated once from the Unicode Character Database by a script and checked in, also meant for `to_upper` / `to_lower` / `is_alpha` (still made from Rust's `char`: the compiled prelude can't use std). Compiled programs keep only the tables they use.
- **Speed**: the compiler runs Strata code with the JIT (the interpreter is gone), so building DFAs for large Unicode classes at compile time is compiled code.

### Concurrency: structured tasks without coloring (decided with the user 2026-11-22; built: step 1 `scope`, `spawn`, `await` on OS threads, PR #200; step 2 channels and `select`, PR #203; step 3 `race` and cancellation, PR #229; step 4 supervised tasks, PR #235; step 5 `Clock` and timer arms, branch `tasks-clock`)

Settled before `std.net`, since it decides what a socket read looks like. **No coloring**: there is one kind of function, and any function may block (`net.read(…)` is a plain call). Colored `async`/`await` (Rust, JS, C#) marks functions that may suspend, and the mark spreads to every caller, which splits libraries in two; it exists to allow stackless coroutines (a state machine per `async fn`). Without it, a blocking-looking call is already the final API: it runs on OS threads first, on a scheduler with a small stack per task later (Go, Java's virtual threads), and user code doesn't change. Each task is plain sequential code, so `check`, `verify` and the prover keep reasoning one function at a time. The runtime's state is already per thread (#177).

**Syntax: keywords.**

```
fn fetch_both(net: Net) -> (Page, Page) {
  scope {
    a := spawn fetch(net, url1)
    b := spawn fetch(net, url2)
    await (a, b)
  }
}
```

- `scope { … }` is a block expression that ends only after every task spawned in it has finished, awaited or not.
- `spawn e` (or `spawn { … }`) runs `e` in a new task and gives a handle `Task[T]`. It belongs to the nearest enclosing `scope` in the code; a `spawn` outside one is an error, and a handle can't leave its scope (a helper that wants tasks opens its own `scope`). This is what makes borrowing safe without a borrow checker (below).
- `await h` (prefix, like `spawn`, `mut` and `comptime`) gives the task's result; on a tuple of handles a tuple of results (`await (a, b)`, the types may differ), on a list a list (`await [spawn fetch(net, u) for u in urls]`).
- `select { … }` waits on operations that already exist and commits exactly one, written like `match` with `as` naming the result:
  ```
  loop {
    select {
      commands.recv() as c => handle(c),
      await download as d => { show(d); break },
      clock.after(1.seconds) => flush(),
    }
  }
  ```
  An arm is an operation the runtime can commit atomically (`recv`, `send`, `await`, a timer): a losing `recv` took nothing, a losing `send` sent nothing (the value is still yours), a losing `await` leaves its task running. It starts no tasks.
- `race { … }` (built in step 3, with cancellation) has the same arms, but each arm's left side runs as its own task; the first to finish runs its right side and the others are cancelled. A loser may have done part of its work, which is why it is not `select` (Tokio's `select!` is really a race, and its docs need a section on "cancel safety"). `race` is `scope` + `spawn` + `select` on the handles + cancelling the losers, so `select` is the primitive.

**No `Tasks` capability.** `scope`/`spawn`/`await` are deterministic: tasks share nothing mutable and values cross by copy, so `scope { a := spawn f(); b := spawn g(); await (a, b) }` is exactly `(f(), g())`, and to `verify`, `await spawn e` is `e`. Spawning touches nothing outside the program, so there's nothing for a capability to stand for (a function that spawns is, from outside, like one that uses more memory: every task ends before it returns). Timing would go through a `Clock` capability (`clock.after`, `clock.sleep`; not built: std has no clock yet) and I/O through its capabilities, as now. Which `select` arm wins and the order of messages from several senders is nondeterministic: the prover treats every arm as possible, as with a `match` it can't decide. The runtime picks threads (decided: one worker per core by default; built so far: a thread per task); `strata test` is to run tasks on a deterministic scheduler with a seed, try several orders and replay a failing one (as Rust's loom and shuttle do), chosen by the test runner (`RunMode`, #152), not by a parameter (not built: today a task inherits the seeded generators, so `select` and generated values repeat, but threads interleave as the OS runs them). Rejected: `tasks.scope(s -> …)` with `Tasks` as a capability (the value was never used in the scope); Zig's `io.async`/`future.await` on a passed-in `Io` (uncolored too, but methods instead of keywords).

**Channels** are a std type: `(tx, rx) := channel()` is unbuffered, as Go's `make(chan T)` (a `send` waits for a receiver to take the value), and `channel[T](n)` has room for `n` values waiting (sends block only when it's full). The buffer absorbs bursts and lets the producer run ahead of slow or uneven consumers; the number of consumers is a separate choice (any number of tasks can receive from one channel, buffered or not). Every channel is bounded, so a fast producer is slowed to its consumers' pace (backpressure). An unbounded channel (Rust's `mpsc::channel()`, Erlang's mailboxes: `send` never blocks, the queue grows without limit) would get its own name, `unbounded_channel[T]()`, so the missing backpressure shows in the code; not planned until something needs it. `tx.send(v)` moves `v` in and blocks while the buffer is full; `rx.recv()` gives `Option[T]`, `None` once closed and empty; `for v in rx` is an `Iterator` that ends at close. Endpoints are runtime handles with their own synchronization (the borrowing rules for data don't apply), and can be copied: several senders, several receivers. **`close` is explicit** (`tx.close()`): each copy of a sender closes its own, the channel ends when every copy is closed, and the checker requires a sender to be closed before its scope ends (decided: on every path; built: somewhere in the block and in each `spawn`, see step 2). Rejected: closing at the last sender's last use (invisible in the code: mentioning `tx` once more would hang the program).

**How values cross tasks.** The meaning is fixed: a capture is a copy at `spawn` time, and there are no shared references, so how the copy is made is the implementation's choice and can change without changing a program. What the implementation must keep is "a count of 1 means nothing else can see it" (see "Memory: reference counting with reuse"): the data is immutable, but the count word isn't, so two threads may not change the same count with plain loads and stores.
- **Built (step 1): counts are atomic while a task is alive.** The runtime sets a flag before the first task's thread starts and clears it after the last one is joined (never while another thread could read it); `strata_dup`, `strata_release`, `strata_unique` and the allocation counters use atomic operations while it is set, plain ones otherwise. A spawned closure holds its captures (counted by the parent before the thread starts), so they outlive every use in the task; a count of 1 still means one holder, on one thread. Programs that never spawn pay one well-predicted branch per count change; code running while tasks are alive pays the atomics. Checked with a stress test (16 tasks dup-ing and dropping the same captured strings, 19 million objects, `STRATA_MEMORY=check`): clean on 20 of 20 runs, and with the counts forced non-atomic it crashes on 2 of 5.
- **The borrowing plan had a hole** (found while building step 1): "children borrow, never count; the scope holds one reference" assumed the parent leaves those objects' counts alone, but the parent keeps running during the scope and `dup`s and `drop`s the same objects (passing `xs` to a call, dropping a temporary), racing with nothing in the children only if they never count; children that keep or pass on a part must count too. Borrowing needs the shared objects to be frozen for the scope (no thread counts them: Lean 4's "marked shared" objects, or our constants' count of 0), which takes a walk of what was captured, or a copy of what escapes. Next, measured against step 1's atomic counts: mark what a `spawn` captures as shared (a walk at `spawn`; dup/drop of a marked object counted atomically, everything else plain), or freeze it for the scope; per-task tables of count changes (biased reference counting) stay a later option.
- **A task's result comes back by move; a `send` moves** when the value is uniquely owned all the way down and copies otherwise (as Erlang copies messages), or, with atomic counts, simply moves. None of these choices changes what a program means.

**`mut` across a spawn** can't happen: `spawn` takes an expression whose captures are copies, and closures can't change outer variables, so `spawn f(mut x)` is an error. A `mut` argument passed by reference (see "Mutation at the call site") stays safe inside a task: it lives on one task's stack, which no other task reaches, even while it blocks. Results come back as values (`x = await h`). Not planned unless needed: lending a `mut` to exactly one child of a scope.

**Step 5 as built** (branch `tasks-clock`): a `Clock` capability and timer arms.
- `std.time`: `capability trait Clock { now(self) -> Instant; sleep(self, d: Duration) }`, `capability SystemClock` (the system's monotonic clock; `main` and tests ask for it by name, as for `Disk` / `Process`), `distinct type Duration = Int` (nanoseconds; `nanos`, `micros`, `ms`, `seconds`; `.value`), `distinct type Instant = Int` (from the clock's own start), `elapsed(start, end)`. Native operations `host_now` and `host_sleep` (runtime `strata_host_now`, `strata_host_sleep`: `clock_gettime(CLOCK_MONOTONIC)`).
- **Sleeping is a wait**: under `chan_lock`, on `chan_cond` with a deadline (`pthread_cond_timedwait`, which takes the wall clock: the deadline is recomputed from the monotonic one), so a cancellation wakes it and it gives up; the call is followed by `cancel_point`. `race { work() as r => Some(r), clock.sleep(ms(100)) => None }` is a timeout.
- **`clock.after(d)` in a `select`** (and so in a `race`'s arms): `after` follows the clock it is called on (user's requirement, 2026-11-22). Its deadline is `clock.now() + d`, in that clock's time, taken as the `select` begins. The system clock's (the clock's type in the compiled instance is `SystemClock`; a function taking a `Clock` is compiled per implementation, so passing the system clock as a `Clock` counts) is a timer the runtime waits for itself (arm kind 3 in `strata_select`: its absolute monotonic deadline; the wait is `pthread_cond_timedwait` to the first deadline). Another clock's (a fake, a mock) is asked again: the compiled code calls its `now` and tells `strata_select` whether the deadline has passed (kind 4); when no arm can happen, `strata_select` waits at most 1 ms and gives -2, and the code asks the clock again (slower, but right for any clock). The arm names nothing (`as` is an error), `d` is a `Duration`, and the receiver must implement `Clock`.
- Tests can now use a fake clock they control: any value implementing `Clock` drives both `sleep` (its own method) and `after` arms (see `fake_clocks_drive_after`: a clock that stands still, one 1000 times faster). Still open: std fakes (a `FakeClock` in std.time), and a **virtual clock** whose time advances only when every task waits (deterministic timeouts without real waiting: it needs the runtime to know when all of a test's tasks are blocked, close to deadlock detection); tests get the real `SystemClock` when they ask for one. Also open: dates and wall-clock time (`std.time` has only the monotonic clock); arithmetic on `Duration` (it is `distinct`: write `ms(a.value + b.value)` or a helper).
- Tests: `clocks_time_out` (a `race` as a timeout whose loser waits on a channel deep in a call, a five-second sleep cancelled by a quicker arm, a `select` with an `after` arm, 20 timeouts in a loop; everything freed, native and JIT alike) and `clock_arms_are_checked`. Also `fake_clocks_drive_after`.

**Step 4 as built** (branch `tasks-supervised`): supervised tasks (see "Failures").
- **Syntax** (user's choice, 2026-11-22): `supervised spawn e`; `supervised` is a contextual keyword, only right before `spawn` on the same line (a name anywhere else), and per arm in a `race`: `race { supervised fetch(a) as r => …, … }` (held as `Expr::SupervisedSpawn`, binary tag 39, in `compiler/ast` too). Failure is handled on the `await`, not the spawn: `await h` of a supervised handle is a `Result[T, Panic]`, so `await h except p { cached(url) }` is plain `except`; a handler after `await h` is the awaited result's (`(await h) except …`, `(await h)!`), both parsers stopping the operand's postfix chain at a handler; the printer writes `await (a!)` for a handler inside. Rejected: `spawn supervised e` (the first try), a separate verb (`isolate e`), `spawn? e`, and `except` on the spawn (`spawn e except p { … }`: the handler belongs where the result is used). A supervised *scope* was the first idea; per task is finer, and a scope of supervised tasks is just that.
- **Semantics**: `Panic = { kind, message, stack }` (prelude). A supervised task is a boundary, like a test (`Contained` in runtime.c): its first panic is recorded, everything below it is cancelled (stops at its next wait), its sender copies close, and its result is `Err(Panic { … })` (built by a generated `task.sfail` function from the runtime's strings; `task.srun` wraps a normal result in `Ok`). A panic in an ordinary task below it is the supervised task's. Under `strata test`, a supervised task's panic is its result, as anywhere; an ordinary task's still fails the test.
- **Memory**: the region per task (option (b)) turned out unnecessary for compiled code and unsound alone: freeing a dead task's region would leave every count it took on objects outside (its captures, what it received) too high, so it needs full copying at the edges (captures in, sends and results out: Erlang's process heaps, with a copy function per type). Instead, a panic in compiled code unwinds the same way a cancelled task does: inside a supervised task `strata_panic` records the panic and returns, and the function leaves through its `unwound` block (dropping what its scopes hold; callers follow through `cancel_point`). So a dying task frees what it held, measured with `STRATA_MEMORY=check` (50 panics deep in calls, each frame holding lists: all freed). std's precompiled code is compiled with these checks too (the library is built as a program with tasks), so std called from a supervised task unwinds as well. **Panics found by the runtime's builtins return too** (built, branch `panics-unwind`): a division or remainder by zero, a negative or huge shift, a float that isn't finite, `floor`/`ceil`/`round` of one, an `Int` too large for a `Float`, `sqrt` of a negative number, `ord`, `chr`, `byte_at`, a string index out of range, `split`/`replace`/`repeat`'s bad arguments, a channel misused (`send` after the end, `close` twice, a negative buffer), a C function's NULL string. Inside a supervised task the builtin records the panic (`soft_fault` in runtime.c) and returns a harmless value (0, a constant empty string), and the compiled code checks right after the call (`after_builtin`: the `cancel_point` check, only in programs with a `supervised spawn` and in std's library, so other programs compile as before) and leaves through the `unwound` block, dropping what it held. Outside a supervised task the same panic ends the program at once, as before. Cost: none measured (150 million divisions and remainders: 0.62 s with the checks and without). The runtime's panic messages now consume their pieces (they leaked, harmlessly while a panic always ended the program). Tested: `supervised_tasks_keep_running` (each of those panics deep in calls, every frame holding lists, 50 times: everything freed, native and JIT alike). **Left as a jump** (`siglongjmp` to the task's trap: the task still dies alone with the right `Err`, but what its frames held stays allocated, tested as known): a stack overflow (detected in a signal handler on the guard page: there is no returning into the overflowing frame), running out of memory (an allocation that fails has no harmless value to give, and the code after it would need a check on every allocation), the step budget (`Limit`, tests and fuzzing only), and a panic in code the compiler generates without a way out (drop and show helpers: they continue with the harmless value until the next check). The fix for the first two is the memory budget below: a supervised task allocating from its own budget can be stopped before it runs out (a check at allocation, which already counts), and a deep recursion has a known stack per task.
- Not yet: memory budgets per supervised task (out of memory as that task's panic: needs per-task allocation counting, which the region would give), restart helpers in std (one-for-one, all-for-one, a restart budget: ordinary code over `supervised spawn`).

**Step 3 as built** (branch `tasks-race`): `race` and cancellation; a panic in a task ends the program (user's choices, 2026-11-22: a cancelled task stops at its next wait; a panic anywhere ends the whole program, see "Failures").
- `Expr::Race(Vec<SelectArm>)` (binary tag 38, in `compiler/ast` too; the evaluator refuses it, as `select`): `race { e as x => body, … }`, each `e` checked as a `spawn`'s body (in a scope of the race's own), the bodies as `select`'s arms. Codegen: a task scope, each `e` spawned into it, `strata_select` with an `await` arm per task, `strata_scope_cancel` on the others, the winner's result moved out of its task, the scope's end (waiting for the losers to stop), then the winner's arm. The prover treats it as an unknown value.
- **Cancellation**: a task has a `cancel` flag and its parent; it is cancelled when it or a task above it is. Waits (`send`, `recv`, `select`, `await`) give up when cancelled (`send` drops its value, `recv` takes nothing, `select` does nothing and drops its sends' values: -1, `await` gives NULL). The compiled code then leaves each function as `return` does (`cancel_point` in llvm.rs: after each call that may wait, and after each wait, a load of the global `strata_cancel_any` (cancellations pending) and, only when it isn't 0, a call to `strata_cancelled()`; the way out drops the scopes and returns a zero value through an `unwound` block, which callers check for before using it). A program without `spawn` or `race` gets no checks; with them, fib(35) runs in the same time (the branch is predicted). A cancelled task's result is never dropped (it has none), and its unclosed sender copies are closed without a panic.
- **A panic in a task ends the program** at once (printed with the stack from `main` through each `spawn`: `strata_spawn` keeps the spawning thread's stack), instead of being raised at `await`. Inside `strata_test` (a test, a fuzz case) it fails only that run: the run's threads all count as cancelled (`Contained`), so the test's thread stops at its next wait and the end of the task's scope raises the panic there; a panic in the test's own thread cancels its tasks before waiting for them.
- Checked with `races_cancel_the_losers` (losers stopped deep in calls at a `recv`, at a `send` to a full channel, at an `await` of their own task, in a `select`, in a race of their own, 100 races in a loop: every object freed, 40 runs alike) and `a_task_panic_fails_only_its_test`.
- Not yet: cancelling at blocking I/O (none can block yet: `std.net` will need it), supervised scopes (see "Failures"), `compiler/check` doesn't look inside `select` / `race` (its `_` arm). Precompiled std code calling a closure that is cancelled doesn't check (std's non-generic functions are compiled without checks); generic ones, compiled per program, do.

**Step 2 as built** (branch `tasks-channels`): channels and `select`.
- `channel()` / `channel(n)` (builtins; the element type is inferred: calls take no type arguments, so not `channel[T](n)`), `Sender[T]` / `Receiver[T]` (built-in types), and their methods in the prelude (`Sending`: `send`, `close`; `Receiving`: `recv`; `Iterator` for `Receiver`, so `for v in rx`), over the builtins `channel_send`, `channel_recv`, `channel_close`. Not `select` a keyword: `select {` starts one, so std.web's `select(…)` stays a call.
- **A copy of a sender is one per task** (user's choice, 2026-11-22): the task that made the channel holds one, and so does each `spawn` that captures the sender (counted at `spawn`, only if the spawning task still holds its own). Each closes its own; the channel ends when all have. The checker requires `tx.close()` in the block that makes the channel and in each `spawn` that captures it (anywhere in it: not yet on every path), and refuses a `spawn` capturing a sender inside another value. At run time: a task ending with a copy still open has it closed for it and faults (`a task ended without closing its copy of a sender`); `close` of a copy the task doesn't hold (or twice) faults; `send` on an ended channel faults.
- `Expr::Select(Vec<SelectArm>)` (binary tag 37; `SelectArm { comments, op, name, body }`, in `compiler/ast` too; the evaluator refuses it). Arms: `rx.recv() as x` (`Option`), `tx.send(v)` (no name), `await h as r`. Codegen describes each arm to `strata_select` (kind, channel or task, slot), which commits the first that can happen, looking from a different arm each time (from the thread's generator: no starvation, and a run repeats); a send's value is dropped by the arm that won if it wasn't its own. The prover treats a `select` as an unknown value.
- Runtime: a channel is one counted object (both ends point to it; its last holder drops what is still in it); every channel and task end is under one lock with one condition variable (simple and correct, slow under contention: a lock per channel later). An unbuffered `send` waits until its value is taken; in a `select`, an unbuffered send arm is ready when a receiver is waiting.
- `scope { …; spawn e }` is `()` (its last task's handle isn't its value), since writing that came up at once.
- Not yet: timer arms (`clock.after(…)`: no `Clock` capability exists yet), detecting a deadlock (every task waiting: today a silent hang), `close` on every path in the checker, a lock per channel.

**Step 1 as built** (branch `tasks-scope`): `Expr::Scope`, `Expr::Spawn`, `Expr::Await` (binary tags 34-36, in `compiler/ast` too). `spawn` takes the whole expression after it, as `return` does (`spawn len(xs) + fib(20)` is one task); `await` is prefix and takes what follows like `-` or `!`, so `await hs.fold(…)` awaits the fold's result: write `(await hs).fold(…)`. A scope whose last expression is a `spawn` gives back a handle, which is an error (end it with the value wanted). The checker: `Task[T]` (not writable in types yet); `spawn` outside a `scope` is an error, and so are `return`, `!` and `?` inside one, a closure or `spawn` capturing a handle, a handle in a scope's result, in a task's result, or assigned to a variable declared outside the scope. A lambda inside a `scope` may spawn into it (a comprehension's body is a lambda: `await [spawn f(x) for x in xs]`); a lambda that spawns can't leave the scope while its type mentions the handle, and the runtime faults if one is called after its scope ended (a generic function can hide the handle's type: a gap until `Task` is tracked through generics). The prover: `spawn e`, `await h` and `scope b` are `e`, `h` and `b`. Codegen: the spawned expression is a closure of no parameters; `strata_spawn` (closure, a `task.run` function that calls it and stores the result, a `task.drop` function for the result) starts a thread (64 MB stack) for the thread's innermost open scope; `strata_await` joins and gives a pointer to the result, which the task keeps (so it can be awaited twice) until `strata_scope_end`, which every way out of the scope calls (`return` and `break` too), joins every task, drops results and closures, then raises the first task's fault. A fault in a task (its own trap) is raised by `await` or the end of the scope, with the call stack `main -> spawn -> pick`; caught by a trap (a test), every open scope's tasks finish first. Tasks inherit the generators' state (split per spawn, so a run repeats), output capture (a test's), and the step budget; `print` locks stdout per line. Not yet (after step 3): the shared-marking optimisation above, `Task` in written types.

Open: blocking `extern c` calls on a scheduler (a blocked call holds a whole OS thread: Go hands that thread's other tasks to a new one); stack size and growth per task.

### Error handling, strings and mutation (decided)
- **Done**: `except` blocks (`e except { fallback }`, `e except err { ... }`, the fallback may `return`), `!` / `?` propagation, early `return`, f-strings, and string primitives (`chars`, `index_of`, `replace`, `lines`, `repeat`, `reverse`, case, `is_digit` / `is_alpha` / `is_space`, `ord` / `chr`). Strings are not indexed themselves: a unit is named (`s.bytes()`, `s.code_points()`, `s.graphemes()`), and positions are byte offsets (`byte_slice`). See docs/language.md, "Errors".
- **Mutation of a `mut` value happens in place**, with no copying, whenever nothing else holds the value. The hard part is knowing when that's the case: use the absence of shared references plus ownership or reference counting (as in Koka's Perceus) so updates through a mutable binding are real in-place updates.
- **Errors that say what was probably meant** (the user, 2026-11-21: as Rust's): an error names the problem in the program's terms, then `  help:` lines with what to write instead (`other: Shape` for a `Self` argument on a trait value). New errors should do this; older ones could be gone through.
- **Memory: reference counting with reuse, as in Koka's Perceus and Lean 4** (decided with the user, 2026-11-21; was: Boehm to start). Values never change once built and there are no shared references, so an object only points to older ones: the heap has no cycles and counting frees everything, with no cycle collector. The compiler inserts `dup` (one more owner: count + 1) and `drop` (one owner fewer: count - 1, freed with its contents at 0), moving a value at its last use instead of dup-ing it, and leaving read-only parameters borrowed (the caller keeps ownership; no counting in the callee). An update (`x.f = e`, a `mut` parameter, `push`, `insert`) happens in place when the count is 1 and copies first otherwise (copy-on-write), so copy-in/copy-out stays the meaning and in place is only the implementation. A count of 1 really means nothing else can see the value; while tasks run, counts change atomically to keep it so (see "Concurrency: structured tasks without coloring"). Rejected: Boehm (an outside library, and no in-place updates), precise tracing (stack maps from LLVM, and no in-place updates either). Steps: (1, built, branch `gc`) a count word before every object (so layouts are unchanged), constants with a count of 0 that are never freed (string literals, values of constructors without fields, and, since branch `regex-parse`, list and tuple literals and constructors (records, variants, `Some`, `Ok`) whose elements are all constants (a small `Int`, a `Float` or `Bool` literal, a string, another constant): one global each, equal ones shared, so a table of 1,700 strings is data instead of 1,700 stores, which took LLVM 3 to 8 s to compile; a push or an update copies them, as for any value held elsewhere), the runtime's `strata_dup` / `strata_release` / `strata_free` / `strata_unique`, and `STRATA_MEMORY` to report allocations at exit; (2, built, branch `gc-drop`) a drop function per type (`drop_fn`; a closure block carries its own, a trait value's table has drop and dup entries; the last field is dropped as a tail call, so a million-long chain doesn't overflow the stack), and counting in the code generator: functions borrow their arguments and return what they own, reads borrow, a stored value is moved (a temporary) or held once more, and every scope (block, branch, statement, loop iteration) drops its temporaries and variables, `return` / `break` / `continue` what they leave; a failed pattern drops what it bound; a `mut` argument always goes through a slot of its own (copy in, copy out); an assigned variable's old value is dropped at the end of the statement. `STRATA_MEMORY=check` keeps freed memory aside and stops on any use of it, and the build tests check every program frees everything (a loop of 28 million allocations: 1.4 GB before, 33 MB after). An operand that only borrows is held until the statement ends when a later operand may assign a variable (`f(x, { x = g(); 1 })`: `operands`). Known gaps: every `dup` / `drop` is a call into the runtime (about 15% slower than not freeing: inline the count updates in the IR); (3, not built) reuse when unique, replacing `push`'s in-place write past the end (the `used` trick), which can make a cycle through a recursive type (`Node(xs)` pushed into `xs`); (4) later: iterative drop for long chains, borrow inference, stack allocation of values that don't escape, big integers in `Int` slots, shared (marked) counts for what tasks capture (atomic counts while tasks run are built: see "Concurrency"). No `copy` / `clone` built-in (user, 2026-11-21): `ys := xs` already is a copy, so `copy(xs)` would only move when the work happens, and would suggest that plain assignment aliases. The runtime part (alloc, free, inc, dec) is small and native; most of the work is in the compiler, so it moves to Strata with it when self-hosting.
- **Self-hosting is a long-term goal**, after the language matures. The compiler would be written in Strata, target LLVM, and use the LLVM libraries.

### Failures: no exceptions, panics end the program, assurance levels (decided with the user 2026-11-22; not built)

Errors are values (`Result`, `Option`), passed and matched; nothing is thrown and caught, so no line of code can be left halfway by something it didn't ask for. What is left when an assumption breaks is a **panic**, which is not an exception: it can't be caught or handled, and it ends the whole program at once, whichever task or thread it happens in (not just the task and its siblings). A test that panics fails, and the other tests run. Today's "faults" become panics, and each kind is meant to shrink:
- **Contracts and refinements** (`requires`, `ensures`, refined types, `assert`): proven by `verify` where it can. An unproven one stays as a run-time check, and if it fails the program panics: an assumption we couldn't prove broke, so carrying on is wrong; the panic says which and where, so the cause can be found.
- **Operations that only work on some inputs** (`xs[i]`, `/`, overflow, `sqrt`, `ord`): give them preconditions the prover discharges at each use, as contracts. To do: measure what proving them everywhere costs `verify` (std and the examples); if it is cheap, they become preconditions; if it is expensive, find a way around it (total versions, `Option`-returning ones, cheaper facts).
  - **Measured 2026-11-22** (branch `partial-ops-cost`): `verify` already has these obligations: an index in range (`at` on a list or a string), no division by zero, `chr`, `ord`, `float`, `sqrt` / `floor` / `ceil` / `round`, finite float results, shifts by a non-negative count. `STRATA_PARTIAL_OPS=off` leaves them out, to measure them. **They are cheap: keep them as preconditions everywhere.** In std: 62 of 343 listed checks (34 functions: std.regex 17, std.ast.binary 4, std.unicode 4, ...), and all 887 functions not assumed are proven either way. In the solver they are 62 of 606 queries and 0.70 s of about 5 s of z3 time over all of std (each query timed alone: 11 ms each, against 9 ms for termination and 6 ms for other contracts), while a std `verify` takes 12 to 15 minutes: the time is elsewhere (fuzzing, compiling, cross-checks), not in proving these. Whole runs: 825 s and 878 MB peak with them, 907 s and 598 MB without, so too noisy to compare: other sessions' builds and `verify` runs shared the machine (load average about 35), and the run without them was the slower. On std.regex, std.unicode, std.utf8 and std.ast.binary, three rounds alternating: 154 queries with them against 107, CPU 6 to 8 s either way. The examples: 267 queries against 258 (`builtins` 6 more, `math` 3), and no verdict changes.
  - **Found on the way, fixed**: an index into a list the prover doesn't model as a list (the result of `??`, a closure's result) had no check at all, so `verify` called `(d.get(k) ?? [])[0]` proven and the cross-check reported "a bug in the prover". Every `at` now checks the index against the list's length (`list_len`, which handles unions and unknown lists), and a list read from a field is made before it is indexed (`every_index_is_checked`). It changes no result in std (887 proven, 343 checks, as before; 665 s). Left: such a list gets a new length at each use, so `if len(xs) > 0 { xs[0] }` on a list from a dict isn't proven yet (fuzzed instead); giving an unknown list one length per value would fix it. Also seen: the counterexample input for that dict prints as `[]`.
- **Can't happen once checked** (no match arm, a `let` pattern that doesn't match, no field): impossible by the checker; one that fires is a compiler bug. A refutable `let` must be refused when checking.
- **Running out** (memory, stack, the step budget): a panic; no language makes these values everywhere (every expression may allocate: a `Result` on each would be unusable).

**Assurance levels** (per package or module, like SPARK's levels; names to settle):
1. *Default*: unproven checks run, a broken one panics.
2. *Checked* (the user's idea): a function whose contracts aren't all proven gives its callers a `Result` with a contract error, which they must match, so an unproven assumption shows in the types instead of as a possible panic.
3. *Proven*: the build refuses any unproven contract or partial operation; nothing can panic but running out (SPARK's "silver": absence of run-time errors).
4. *Bounded*: resources proven too: termination (the checker exists), a computed stack depth (no unbounded recursion), memory within a computed bound or a budget given up front. The hard part, near research with immutable values and counting.

**Keeping running** (mission-critical code), as safety-critical systems do it: (1) make failures impossible and prove it (SPARK, Astrée on Airbus flight code; NASA JPL's "Power of Ten" / MISRA: no allocation after start-up, no recursion, bounded loops, so running out can't happen); (2) contain what still fails and restart it from a known state (ARINC 653 partitions with their own memory and time budgets; Erlang's supervisors, "let it crash"; watchdogs); (3) redundancy outside the program (the Shuttle's voting computers; dissimilar software, since Ariane 5's identical backup failed the same way). Strata's tasks share nothing (values are copies; channels are the only link), which is what makes Erlang's restarts sound: a dead task can't leave shared data half-changed. So a **supervised task** (opted into explicitly: `supervised spawn e`, built: see "Concurrency", step 4) contains a panic: the task dies, its channel ends close (its peers see the channel end), and its parent gets an `Err(Panic { … })` from `await` and can restart it. Everywhere else a panic still ends the program. Later: out-of-memory against the task's own budget as that task's panic.

### Memory in high-performance code: proven properties, not a second memory model (direction agreed with the user 2026-11-21; not built)
The user asked whether Strata needs manual memory management, an unsafe mode or a borrow checker for industrial / high-performance code, where both speed and proofs about memory matter (no leaks, memory used correctly). Agreed: no.
- **What the model already guarantees.** Values never change once built and there are no shared references, so the heap has no cycles and reference counting frees everything: no leaks, by construction (stronger than Rust, where an `Rc` cycle or `mem::forget` leaks in safe code). No use after free and no aliased mutation either, since a mutable reference exists only as a `mut` parameter (see "A `mut` argument is passed by reference"). A borrow checker protects against what shared mutable references make possible, and Strata has none; adding them would also make programs harder to verify (Rust's verifiers, Prusti and Creusot, lean on borrow information to cope), against the language's point.
- **Rejected**: a general unsafe mode or manual `free` (the escape hatch is `extern c`, with contracts at the boundary), a borrow checker with lifetimes, and V's autofree (incomplete, falling back to a GC).
- **What such code needs is predictability**: no hidden allocation, no counting in hot loops, bounded memory, in-place updates that are guaranteed rather than hoped for. Each becomes a property the checker or `verify` proves, in this order:
  1. **Fully in-place functions**, as Koka's `fip` / `fbip` (Lorenzen, Leijen, Swierstra, "FP²: Fully in-Place Functional Programming", ICFP 2023): a marked function is checked to run without allocating, each constructor reusing the memory of one its input gave up. Comes nearly for free once reuse (step 3 of "Memory: reference counting with reuse") is built. Marker and syntax not decided.
  2. **Allocation as a capability** (on top of the capabilities already built): a function without an `Alloc` capability provably allocates nothing, which is the real-time / MISRA rule "no allocation after initialization", enforced by types. To settle: whether `Alloc` is implied by default (and only refused where asked), how it interacts with copy-on-write (a copy is an allocation, so a no-`Alloc` function may only update values it can prove unique), and how faults that allocate their message are counted.
  3. **Arenas**: `with arena a { ... }` allocates in a region freed at once when the block ends, with no counting inside. The only check needed is that nothing allocated in `a` escapes the block, the same second-class rule as `mut` references, so no lifetime annotations. Syntax not decided.
  4. **Bounds checks removed by proof**: an index whose refinement `verify` proves within the length needs no check at run time (part of "skipping the runtime check of a contract `verify` proved"). Built (branch `proven-checks`): see "Proven checks leave the compiled code".
- **Self-hosting and the runtime.** Reference counting needs almost no runtime (no collector thread, no stack maps, no pauses: alloc, free, increment, decrement); most of `src/llvm/runtime.c` is printing, strings, faults, random numbers, contract tracing, fuzzing and host I/O, which a borrow checker wouldn't remove. To go without the C runtime, `std` gets a few raw-memory primitives (load, store, pointer offset, size of a type), usable only inside `std` (as Rust's `core`), so the allocator and the counting can be written in Strata over `extern c` `malloc` / `free`, or over `mmap` where there's no libc. Not decided: their names, and how "only inside `std`" is enforced.

### Runtime and standard library (decided)
- **A small native core in Rust** (C is possible for the system-call layer; decide when we get there): the GC, the system-call / OS boundary, and bindings to LLVM and the SMT solver.
- **Most of the standard library in Strata itself**: collections, strings, the ORM, HTTP / web views, CLI helpers, and agent tooling. Only the thin OS / runtime layer is native.

### Sums and unions are one thing (decided with the user 2026-11-21; built, branch `unions-are-sums`)
A sum already is a union of the types its variants declare (`ShapeError` is `Empty | TooBig`), and matching, narrowing and coverage are the union machinery; what was left apart (where members are declared, which can have `impl`s) confused more than it helped. So there is one construct, the union:
- **Members declared inline or named**: `type Shape = Circle | Square { side: Float } | Dot` reuses `Circle` and declares `Square` and `Dot`. Today's sum is the case where every member is inline (`type Option[T] = Some(T) | None`). Declaring a member inline is declaring a type (a record, a tuple-shaped type or an atom), unique in its module as variants are now.
- **Only bare members flatten**: `type S = A | B; type S2 = S | C` is `A | B | C`; `type S3 = D(S) | E` is `D | E`, not `A | B | E`: a constructor wrapping something is a new type, and what it holds stays inside it (`x.0` of a `D` is an `S`).
- **A named union names a set of values, as an alias does**, under the alias rules: a `Circle` fits `Shape` without wrapping; the same set written out (`Circle | Square`) is the same type; a named union can have `impl`s, methods and `derive` (as a sum can today). A union that adds nothing is refused like `type P = List[Int]`: one that normalizes to one type (`type U = Int | Positive`), or a second name in the same module for a set already named (`type Figure = Circle | Square` next to `Shape`): "use `Shape`, or make it `distinct type Figure = ...`". Names are unique per module, not per program: `geo.Shape` and `ui.Figure` may name the same set, told apart by their module (user); which `impl` applies is the static type's (`geo.Shape`'s for a value typed `geo.Shape`); an anonymous union written inline has none of its own.
- **`distinct type Figure = Circle | Square`**: a separate nominal type, as `distinct` is today: built explicitly (`Figure(c)`), `f.value` is the `Circle | Square`, doesn't mix with `Shape` or its members, has its own `impl`s, and is written to JSON as its value.
- **`std.typing`**: `Sum` and `Union` become one kind with `members` (`variants` goes); `Choice` is a union whose members are all atoms. JSON's two paths (sums tagged by `"type"`, unions told apart by their JSON) merge: a member is tagged when it is a record, tuple-shaped or atom type, else told apart by its JSON kind, as unions are now.
- **Refined with the user (2026-11-21)**:
  - *A bare name refers to a type when one exists*, and declares a new one only when nothing has that name; with a payload too: `Some(Int) | None` is the prelude's `Some` (given `Int`) and `None`, i.e. `Option[Int]`, not new types. A member named like an existing type (`Circel` next to `Circle`) is a warning after the `edit` ("did you mean `Circle`?"), not an error: two types may have close names.
  - *Inline and separate are two views of the same thing*: `type Shape = Circle | Square { side: Float } | Dot`, or `type Square = { side: Float }`, `type Dot` and `type Shape = Circle | Square | Dot`, mean the same; `edit` takes either. So an atom can be declared on its own (`type Dot`), and a tuple-shaped type too (`type Moved(Int)`). Which one is shown is a setting of the renderer and viewer; by default a member is shown inline under its union when that is the only union using it, else on its own.
  - *The renderer uses names*: a union written out (`fn f(x: B | C)`) is rendered as its name (`x: A`) when the set has one in scope (the module's own first), and named subsets too when one name alone covers them (`B | C | D` with `A = B | C` is `A | D`); a `distinct` type is never used so. The checker agrees: a union equal to a named set in scope is that type (its `impl`s apply).
  - *The prelude is part of every module* (it is in scope unprefixed): `type Answer = Some(Int) | None` names a set the prelude already names (`Option[Int]`), so it is refused as adding nothing ("use `Option[Int]`, or make it `distinct`"). A module imported with a prefix (`std.json`, `geo`) is another module: naming the same set there is fine.
  - *A `distinct` union* is built and read as any `distinct` type: `distinct type Answer = Option[Int]` (or `= Some(Int) | None`), `Answer(Some(3))`, `Answer(None)`, `a.value` the `Option[Int]`.
  - *Later (viewer)*: holding a key shows hints: a type expanded into its members, the parameters' names at a call, and the like.
- **Built** (branch `unions-are-sums`, stacked on `typing-defs`):
  - *Stored form*: a union whose members are all defined elsewhere is an alias of their union; one declaring some is a `TypeBody::Sum` whose other members are `Payload::Type` (binary tag 3). The parser reads `A | B { .. } | C(Int)` and the bar-first form the same; whether a bare name is an existing type is decided when the code is stored (`resolve::union_members`: the module's types, earlier unions' declared members, the root module, the prelude and built-ins, what it imports; a second version of the same definition, as an edit has, doesn't count), so the decision is in the tree. A member with fields named like a prelude type (`Some(Int)`) is that type. One bare name with no bar is an alias (`type Port = Int where ..`); a union of one atom is `type X = | Dot`, an atom on its own `type Dot`. `Tuple` and `Unit` aren't built-in names for this (`(A, B)` and `()` are written so), which leaves `std.typing.Kind` its `Tuple` and `Unit`.
  - *Checking and running*: before checking, a union with members of both kinds becomes a sum of its own members (`Shape$own`) and the union of that with the others (`desugar::mixed_unions`), so the checker and backends see only sums and unions. A named union isn't nominal: a union type is found by its set (`Checker::union_name`, `Module::union_name`, a sum counting as its variants), and the named union's `impl`s and own methods apply to it, in `satisfies`, method calls, static calls (`Shape.decode_at(..)`, passed by name) and the compiled dispatch (before each member's own). Two modules naming the same set may not both implement a trait for it (`Checker::union_conflicts`, below); otherwise the first name found (by name order) is used.
  - *Rules*: `Checker::union_adds_nothing` (one type once normalized; the same set as an earlier union or sum of the module, the root module or the prelude; the members a union declares, named apart, are fine); `distinct` on a union that only declares members adds nothing; `resolve::near_misses` warns after an edit (one change in a name of up to five letters, two beyond, or case).
  - *Rendering*: `written_form` names a union written out when its module (or the root module) names the set, and named subsets when they don't overlap, keeping the members' order (`resolve::named_unions`; not `distinct`, not generic). `render --members separate | inline` (`resolve::members_view`).
  - *`std.typing`*: `Kind` has no `Sum`, `Type` no `variants`; a union's `members` are as written, a named union one member, except the members a union declares itself, listed each. A named union can derive (`derivable(Record | Union)`); as a field it needs its own `derive`, as a record does. `std.json`: one path for unions, a record, atom or tuple-shaped member tagged by `"type"`, any other told apart by its JSON; messages for a union of tagged members as before.
  - *Default view (user, 2026-11-21)*: a type with a doc is shown on its own, else inside the one union listing it (`render` folds it unless it has a doc, an `impl` or `derive`, or type parameters); `--members separate` shows every member on its own.
  - *Type parameters are wrapped (user, 2026-11-21)*: a generic union's parameter is inside a member it declares (`Some(T)`) or inside a type (`List[T]`), never a member on its own (`T`), and no two members are alike when a parameter is in them (`List[A] | List[B]`): those couldn't be told apart. No `Either[A, B]`: `A | B` is written where it is used. (A bare parameter name in a union is that parameter, not a new atom.) So a union's set, its members paired by what they are and the arguments read off (`Checker::same_set`, `bind_targs` for unions), names one union: a generic one has `impl`s of its own, `Ints = List[Int] | Problem` next to `Many[T] = List[T] | Problem` adds nothing, and `List[Int] | Problem` renders as `Many[Int]` (whole unions only; a parameter only inside a declared member, `Value(T)`, can't be read off a written union). Also fixed: a bare `List =>` arm on a union member compiled to no match.
  - *Two modules naming one set (user, 2026-11-21)*: allowed, but not both implementing a trait (or having a method of one name) for it: `Checker::union_conflicts`, on the later one.
  - *Viewer*: `strata ui` has the setting (*union members: inline (switch)*, kept in the browser): each card carries its code in the other view, and a type the inline view folds has no card there.
### Unions, variants as types, and match patterns (decided 2026-11-19, built)
- **`Option` and `Result` stay as they are**, and so do `!` / `?` propagation. No `T?` / `T ! E` syntax.
- **Unions are sets of values**: `A | B` holds any value of `A` or of `B`. Unions normalize: `Int | Positive` is `Int`; `(Int where p) | (Int where q)` is `Int where p || q`; different bases stay a union. `A` fits `A | B`; `A | B` fits `C` when both do. Type parameters can be members (`T | E` with bounds); if they end up the same type, it collapses, harmlessly.
- **Variants are types.** `type ShapeError = | NonEmptyErr | TooBig { max: Int }` declares the types `NonEmptyErr` and `TooBig`, and `ShapeError` is `NonEmptyErr | TooBig`. So `Result[Circle, NonEmptyErr]` or a parameter of type `TooBig` are allowed.
- **Names are unique in their module** (changed with the user 2026-11-21; was: across the project): no variant may share its name with a type, a trait or another variant of its module. Another module's of the same name is told apart by its module (`geo.Circle`).
- **No automatic wrapping**: always write `Ok(…)`, `Err(…)`, `Some(…)` (`Result[Int, Int]` would be ambiguous otherwise).
- **Patterns are sets of values**: a type name (`Positive =>`, `Square =>`), a variant as today, a literal, a condition (`where 3 <= it && it <= 5 =>`, base type = the scrutinee's), `_`. An arm takes what no earlier arm took. Exhaustive = the scrutinee's (normalized) type is covered by the arms; an arm already covered by earlier ones is an error (unreachable).
- **Narrowing, no new name**: `match x { Positive => { x … } }` narrows `x` itself in the arm. For an expression: `match f(y) as x { … }`. Field paths (`o.status`) narrow too. Narrowing of a `let mut` lasts until it is assigned.
- **Coverage**: integer (and `len(it)`) comparisons with constants, combined with `&&` / `||`, are decided exactly as interval sets. Anything else waits for the SMT solver; until then such an arm needs a later `_`. This also lets a match on `NonEmpty` skip the `[]` arm.
- **Built** (branch `unions`): `Ty::Union` normalized by `Checker::union_of`; subsumption in `fits` (used by `expect`: union members, variants into their sum; type arguments stay invariant); `infer_at` passes the expected type through `if` / `match` / blocks / lists / constructors; `pattern` returns the narrowed type and a value set `P`; exhaustiveness and unreachable arms use atoms (`atoms`, `covers`, `missing`, `useful`) with integer intervals in `types::ints`. The interpreter (since deleted) had `value_in` / `shape_fits` for type patterns and `is`, unions in `check_type` and JSON input, impls on variants; compiled code does the same. Since then (decided with the user): or-patterns; unions inferred for alternatives when no expected type decides; type arguments fit member-wise (values are never shared) except for arguments to `mut` parameters, which must be exact; `!` passes errors into wider error types; length (`len(it)`) and `Float` conditions are decided (`types::reals` tests one point per region); the matched value's written refinement counts (`Coverage.excluded`), taken from variables' declared types (mutable ones too: every assignment and write-back is checked against the declared type), their fields and function results (`Checker::written`). Narrowing in an arm is skipped for a `mut` variable the arm assigns (`Checker::assigns_to`), so loops stay sound. A `mut` argument's declared refinement must contain the parameter's (`refinement_within`); assignments of literals are checked at compile time (`literal_outside`). Not yet: list lengths other than empty / not empty; conditions beyond constant comparisons (see "Match coverage with the SMT solver").

### Match coverage with the SMT solver (assessed 2026-11-19, not started)
The prover (`src/smt.rs`) has the pieces: symbolic values for parameters with their refinements as facts, `Vc::pattern` turning a pattern into an SMT condition on the matched value (type names, `where`, or-patterns included), per-arm path conditions in `Expr::Match`, obligations solved with Z3. To decide coverage of undecidable conditions it still needs: (1) an obligation per `match` that some arm holds (the `or` of the arm conditions, under the facts), and one per arm that it can hold (unreachable when proven impossible); (2) (done since); (3) a policy between `check` and `verify`: `check` would report such a `match` as "needs proof" instead of an error, and `verify` proves it, reports a counterexample, or leaves it runtime-checked (a `no match arm` fault). Floats are not modelled there; the checker's own `reals` covers them.

### Mutation at the call site, references, and unproven checks (decided 2026-11-19)
- **`mut` at the call site (done)**: an argument to a `mut` parameter is written `f(mut x)`; missing it, or writing it for a parameter that is not `mut` (or a builtin, or a closure), is an error. A `mut self` method's call is marked too, `mut queue.claim(2)` (since 2026-11-20; it was unmarked, as in Swift). `Expr::Mut`, checked in `check_mut_args`.
- **References**: immutable values can always be shared (no copying in the compiled form); a mutable reference only exists as a `mut` parameter. References stay second-class (never stored or returned), like Swift `inout` / Hylo, since first-class ones would need a borrow checker; a possible local form is `mut l := mut order.lines[0]`.
- **A `mut` argument is passed by reference, and may not overlap another argument** (decided with the user 2026-11-21; not built: today every `mut` argument goes through a slot of its own, copied in and out). Without threads or async, a `mut` parameter is the only way to the caller's variable while the call runs, and it can't outlive the call, so passing a pointer to the variable is safe with no borrow checker (Swift's "law of exclusivity"). Copy-in/copy-out stays the meaning, which is what the checker and the prover reason with; with a single reference the two can't be told apart. That holds only if the `mut` argument doesn't overlap any other argument of the same call, since read-only arguments are borrowed, not copied: `f(mut x, x)` would let the callee see its read-only parameter change, as would `swap(mut a, mut a)` and a part with its whole (`f(mut xs, xs[0])`, `g(mut r.lo, r)`). **Overlap is refused by the checker** (user's choice; rejected: allowing it and holding the overlapping argument once more, so the callee's write copies first), with a `help:` naming the copy to write (`y := x; f(mut x, y)`). Overlap means the same variable, or one path a prefix of another (`r` and `r.lo`; `xs[i]` and `xs[j]` count as overlapping unless the indices are different constants, or later proven different by `verify`). The same rule covers the open nested-block case: an argument block that assigns a variable used by another argument (`f(x, { x = g(); 1 })`) is overlap too, and can be refused the same way instead of held (`operands`). A field (`shift(mut r.lo)`) or an element is passed as a pointer into the record or list once it is made unique (copied first if its count is above 1). The reference makes the *variable* shared with the callee; the *value* in it is still updated in place only when its count is 1, and copied first otherwise (`ys := xs; f(mut xs)`): in-place mutation needs both this and reuse (step 3 of "Memory: reference counting with reuse"). An `extern c` `mut` parameter is already an out-pointer, so FFI is unchanged. Tasks keep this safe: a `mut` can't cross a `spawn`, and a `mut` reference on a task's stack is reached by that task only, even while it blocks (see "Concurrency: structured tasks without coloring").
- **Unproven checks are reported by default** (with the runtime check kept); a project policy can require `proven` for chosen modules. For the SMT work: an assignment to a refined variable is one more obligation (e.g. `x = f(x) - 3` with `x: Positive` needs `f`'s contract to imply it).

### Lambda syntax (done)

- `->` is never an operator inside expressions, so there is no ambiguity; `=>` stays reserved for `match` arms.
- **No shorthand lambdas** (no `$`, `_` or implicit parameter) and **no separate anonymous-`fn` form**.
- **Refinements keep `it`** for "the value" (`where it > 0`).

### Bindings and assignment (decided with the user 2026-11-21, built)
- `:=` declares and infers the type: `n := 0`, `(w, k) := pair()`, `mut x := 0`. With a type, the colon is already written, so the sign is `=`: `let x: Int = 5`, `mut x: Int = 0`. `let` only appears with a type; `let x = e` is a parse error pointing at `x := e`.
- `=` only reassigns a variable or field. `+=`, `-=`, `*=`, `/=`, `%=` parse to `x = x op e` (no new node), and the printer writes `x = x op e` back as `x op= e`.
- A function returning `()` leaves out `-> ()` (it was already optional when parsing; the printer now omits it). Function *types* keep it: `(A) -> ()`.
- A call's `(` must be written against the name: `f(x)` is a call, `f (x)` is `f` followed by `(x)`. So without `let`, `f() (a, b) := …` on one line is still a call then a binding (the printer puts them on separate lines anyway). Decided with the user 2026-11-21; the rendering is meant to be customizable per reader later (e.g. `let` everywhere, sums expanded or compressed), since the tree is the language.

### A type's own methods, and shared method names (decided 2026-11-20, built)
- **`impl Item { ... }`** gives a type methods of its own, with no trait. A method with `self` is called on a value; one without `self` is called on the type (`Item.new(...)`), and is resolved into the function `Item.new` right after module resolution.
- **Traits as parameter types** are shorthand for a type parameter with that bound (`mut queue: Queue[P, E]` = `[Q: Queue[P, E]](mut queue: Q)`). Name the parameter only to tie types together.
- **Method names may be shared between traits**, each implementation with its own body (revised 2026-11-20 by the user). A call through a trait (`d: Describe`, `T: Describe`) runs that trait's implementation. On a known type, the type's own method wins, else the one trait of the type that declares the name. Anything else is a compile error: a type with two such traits and no own method; a receiver known only as `A | B` or `T: A + B` (even if the actual type has its own method: that doesn't say which trait's meaning the call wants).
- **Elaboration** (`types::check_and_elaborate`, done with the check): the checker records each such decision by call node, and the program that runs (compiled code, verify, SMT, termination) has it written in: `x.Describe::describe()` for a call through a trait, a direct call of the function `Item.describe` for a type's own method. A type's own methods are registered as functions (`Item.new`, `Item.describe`).
- **Trait methods without `self`** (built 2026-11-20): called on a named type (`Money.empty()`, `T.empty()`, `Self.empty()` in default methods and laws), elaborated to `Trait::empty(type, ..)`. The signature must mention `Self`. Generic functions whose type parameters are bounded by such a trait get hidden parameters `type:T` (of type `$Type[T]`, the type's name at runtime); each call passes the inferred type or forwards the caller's. The fuzzer generates them from its chosen instance. Since `runtime-types` (#122), types are passed whole at run time, which also covers methods with `self`.

## Git, diffs and review (decided)

- **Editing the standard library** (fixed, branch `std-edit`): `std/` is a package whose modules are `std.*`. `strata edit io` inside it names the module `std.io` (it named it `io`) and logs nothing (it started a `strata.log`; std's history is git's); `strata --file std edit` edits it as that package, checked like any package edit (it stored a definition that `check` then refused). `--file` on another folder or a file still stores what parses, checked afterwards.
- **Git stays the base** (built). A package's module files and its `strata.log` are committed; `.strata/` is only the local verification cache. `edit` / `add` / `rename` rewrite the files and append an entry (id, message, changes with each definition's text before and after, `rename`). The log merges by union. `strata init` writes `strata.toml` and an empty `strata.log`, so the log is tracked from the start (`git commit -am` would otherwise leave it behind).
- **Structural diff** between two git revisions: load both snapshots, pair definitions, compare trees. The log entries present at HEAD but not at the base are the atomic steps in between (for stepping through, renames, messages). A PR = merge-base..HEAD.
- **Change kinds**: added/removed; renamed/moved (one line, "N references updated", folded); signature change marked in place, with contract stronger/weaker; body change shown in place with unchanged statements folded, **falling back to a line diff of the canonical text when most of the body changed**; type field/variant changes (with "N matches must handle it"); trait changes; doc comments as a word diff; verification before → after. Ordered types → interfaces → implementations → tests.
- **`strata rename old new`**: done (`resolve::rename`). It reuses the resolver's scoping, so locals shadow and `use` imports work as the checker sees them, and it refuses a rename that would change what any other name refers to. Functions, types, traits, **variants, trait methods** (the trait, every impl's method and the calls) and **fields** (`strata rename Line.qty quantity`: declaration, accesses, record literals, updates, patterns). Variants and methods go through the resolver like definitions (`resolve::member` / `owner` / `defined`; an impl's methods are named in the trait's module, which rename mode used to get wrong). Field accesses are told apart by type, not by name: when another record (or the prelude, or `.value` of distinct types) has a field of that name, `resolve::rename_field` tags each access in a copy (`qty·d3k0`), and the checker (`types::field_owners`, a thread-local probe in `infer` for tagged `Expr::Field`) records the record type(s) of each receiver; only the owner's accesses are renamed, and an access on a union of the owner and another record is refused. Literals, updates and patterns are matched by their constructor. It rewrites the serialized tree in one fixed-order walk (tags and renames line up), and the command type-checks the result.
- **`strata move <name> <module>`** (`resolve::move_def`): a function, type or trait (with its variants or methods) changes module, keeping its short name. The resolver's write-back has a move mode (`run_with(.., moves)`): qualified references get the new module (`orders.charge(o)` → `billing.charge(o)`), short ones stay short and their module gets `use billing.{charge}`, `use` items that named it go (emptied lists are removed), and the moved definition's own short references get imports where it goes. Refused when something private would be out of reach (a private dependency, or a private definition used from its old module), or when any name would resolve differently (the same check as rename). Logged as `"renames": [{.., "kind": "move"}]`; diffs say "moved from `orders`"; `sync` follows moves (`resolve::follow_move`, compared by name since imports change the definitions' positions). Docs and comments aren't rewritten (the command lists the ones that mention the old name). Several renames are one step (`strata rename A.tag label B.tag label`, `resolve::rename_all`): fields are renamed together by `rename_fields` (an access on a union is renamed when every record it reads from is renamed to the same name), then the rest one after the other; one type-check, one log entry. The log entry has `"renames": [{"from", "to", "kind"}], "references"` (`store::renames_of` reads it; `strata move` writes `kind: "move"`). It works on the package's files and logs the rename.
- **Merge driver**: `strata merge-file %O %A %B %P` per definition, then type-check. GitHub won't run it, so: `strata sync main` merges main into the branch locally, and `strata ci` (all packages check, all modules canonical) was run before pushing, until it went (user, 2026-11-22: code is stored only in binary and a saved file checks by construction, so canonical-form and repository-wide checks were pointless; `strata upgrade` keeps the re-encoding, exports and `[verify]` rules are checked when a package loads). **No CI for now** (user, 2026-11-22): the compiler changes all the time and every agent runs the tests locally, so CI (installing LLVM and building strata on every run) only slowed merges; `cargo test` left CI in #185, then the workflow and the required checks went. To bring back once most of Strata is written in Strata and the compiler changes rarely; then cache the built `strata` (keyed by `src/`, `std/`, the Cargo files) so a change to `.strata` files alone doesn't rebuild it.
- **jj**: compatible (runs on git) but not a dependency.
- The tour is later. The user wants to settle the look first: offer a static mockup of the *Changes* view.

Order: ~~`strata rename`~~ → ~~diff core~~ → ~~`strata diff`~~ → ~~*Changes* view~~ → ~~merge driver~~.

**Merge driver (built):** `src/merge.rs` and `strata merge-file` / `setup-git` / `sync` / `upgrade`, plus packages (`src/package.rs`, see below). `package::discover` finds every package (folder with a `strata.toml`) and script (a `.strata` file outside every package) with `git ls-files`; `sync` checks each one after a merge, and `strata upgrade` rewrites each in canonical form. (`strata ci` did both, plus `exports`, until 2026-11-22.)
How the driver works: definitions are paired by qualified name, and one-sided changes win. Two-sided changes go through `git merge-file` on the definition's canonical text, and the result is kept only if it parses back into that one definition; otherwise there are diff3 markers around it. Renames are detected without the log: a definition gone, and an added one with the same kind and module whose text is ≥60% similar to the base's after `resolve::rename`. The rename is applied to the base and to the other side. After the merge, the file is type-checked inside its package, with the package's other files read from disk (ours, because merge-ort runs drivers before it writes the worktree). Only errors that neither side has alone fail the merge. The whole-program check after all files are merged is `sync`'s check of every package and script.
`sync` passes the driver with `-c merge.strata.driver=...` and a temporary `core.attributesFile`, so it works without `setup-git`. It merges `origin/BRANCH` when there is a remote, commits only if everything checks, and otherwise leaves the merge staged.
CI: there is none for now (#186, see above): the workflow and the required checks are gone, and `strata ci` was run before every push (until it went, 2026-11-22). The repository is private.
**Renames across a merge (built):** `sync` runs the driver with `STRATA_MERGE_BASE` / `STRATA_MERGE_THEIRS`; then the driver skips its per-file type check (while git merges, the other files are still ours). After git is done, `merge::follow_renames` reads the renames both sides logged since the merge base and applies each to the merged package (`resolve::follow`): the renamed definition is put back under its old name (and `use` items naming the new name name the old one), every reference to the old name is renamed, and each definition must resolve as before (what the rename touched, with old → new) or exactly as merged (everything else), so a local that would capture the new name makes it refuse. The fix is a logged change (`"follows"`), staged into the merge commit; then `sync` checks everything.
Not yet: following renames under a plain `git merge` (only `sync` does it); a refused follow leaves every reference to the old name for `sync`'s check to report; moving several definitions at once (move a private helper with its user: make it `pub`, or move it first); a rename+edit is recognised only when it is ≥60% similar *and* callers switched to the new name (tiny functions look alike, so similarity alone gave false renames).

Diff: a renamed variant, method or field shows on its type or trait as "variant `Circle` renamed to `Round`" ("only a name changed · N references updated"), and code that only follows it is folded; other changes to the owner are computed against the old owner with the rename applied. `sync` follows member renames too (`resolve::set_member_name` puts the member back under its old name first). Diff, not yet: "N matches must handle the new variant"; moves between modules. Closure hashes (verification cache keys) now ignore docs and comments, and interface hashes ignore docs.

## Packages, modules and dependencies (decided)

- **A package is a folder with a `strata.toml`**: `name` (required; `strata init` writes the folder's name, and it stays when the folder moves, e.g. in a worktree), `exports` (optional, modules or single definitions, the equivalent of `pub use`; default every `pub`), `[deps]`, `[verify]` (verifier policy, e.g. modules that must be `proven`). There is **no `lib.strata`**. **`main.strata`** is the root module and the default entry point. A `.strata` file outside every package is a script. A nested folder with its own `strata.toml` is a separate package.
  **Built:** `name`, `exports` (checked when the package loads), discovery, nested packages, `init`, `[verify]` (verify's policies), `[native]` (C for `extern c`), `[json]`, `[run]`, `[ui]`. `[deps]` is parsed but not fetched.
- **A file is a module; `module m { }` blocks are gone** (built). The parser has no `module` form, `printer::program` is one file's text, and `render` prints one module (`render MODULE`, `main` for the root) or `--split DIR`; on several modules without either it says so. A view across modules labels each group with a `// ── module m` comment line. Where a definition sits inside a file doesn't matter, and the standard rendering is one file per module. Folders organise modules freely; there are no submodules with special access. A module's name is its path inside the package (`shop/orders.strata` → `shop.orders`; confirmed by the user 2026-11-19), so names don't collide and moving a file is a module rename.
- **Dependencies from any git URL** (Go-like, not only GitHub), declared in `[deps]` (`json = "https://…"`, or `{ path = "../x" }` in the same repo), used as `use json.parse`. To be fetched into a global cache and run directly, with no install step (not built: `[deps]` is parsed, nothing is fetched). A generated `strata.lock` pins each dep to a commit + content hash (confirmed by the user 2026-11-19, not built), with `strata update`. Semver tags (explained to the user) can come later; Strata could compute the right bump from interface hashes and contract diffs. Capabilities-as-values mean a dependency can't do I/O unless handed a capability, which makes URL imports much safer than npm/Go.

## Standard library: I/O first (built)

The user asked for a standard library usable from any program, starting with I/O (print, exit codes), then strings, regex, a NumPy-like math library (later, bigger), and web UI. Built so far:
- **`std/` is a Strata package** (`name = "std"`), embedded in the binary (`src/stdlib.rs`), and precompiled into a cached library (#137). A program that has a `use std.…` gets std's definitions appended after its own at resolution (`stdlib::with_std` in `resolve::resolve`), so index `i` of a resolved program is still the program's `i`; code that zips resolved with original decls is unaffected, and `store::graph` truncates to the program's own. Its modules are `std.io`, `std.fs`, `std.process` and the rest (`std.cli`, `std.json`, `std.http`, `std.web`, `std.regex`, `std.unicode`, `std.utf8`, `std.typing`, `std.code`; the compiler in Strata, once `std.ast.*`, is the `compiler/` package now), also when `std/` itself is loaded (`package::program` prefixes a package named `std`; `store::module_path` maps back to files).
- **Capabilities, as decided**: `Console`, `Files`, `Environment` are capability traits. The real implementations (`Terminal`, `Disk`, `Process`) are capabilities (#150): only the runtime makes them, for `main` or a test that names one. Test stand-ins are public: `Recorder`, `MemFiles`, `FakeEnvironment` (plain types; making them `pub mock`s is a step of "Mocks" not built).
- **The native layer** is the `host_*` builtins (`stdlib::HOST`, implemented in `src/llvm/runtime.c`). The resolver rejects them outside `std` modules. `verify` and fuzzing never run code that reaches them (it is reported assumed); a test reaches them only through a capability it names.
- **`strata run [PATH] [-- ARGS]`** runs `main`: parameters are filled by type (Console/Files/Environment only), the return is `()` → 0, `ExitCode`/`Int` → that code, `Result` → `Ok` as before or `Err` printed to stderr (`error: …`) → 1; a fault → 101.
- Examples: `examples/hello`, `examples/wc` (with tests that use the stand-ins).
- Also fixed: the printer now escapes tabs and backslashes in string literals (it used to write a literal tab, and `"\\n"` came back as a newline).

### `std.toml` (asked for by the user 2026-11-22, for `strata.toml` files; built, branch `toml`)

TOML 1.1 (the version the `toml` crate implements) read and written in Strata, as `std.json` is: `parse(text)` gives the root table as `List[(String, TomlValue)]` (keys in the order written, as `JsonValue`'s objects), `TomlValue` = `Text | Integer | Number | Boolean | Moment(DateTime) | Array | Table`; `DateTime` keeps TOML's four kinds as optional `date`, `time`, `offset` (`Utc` for `Z`, `Minutes(n)`); a time without seconds reads as `:00`. The parser works on bytes (`byte_at`, `byte_slice`): all of TOML's syntax is ASCII. Tables are built as a tree of `Node`s (`Leaf` for values, inline tables and arrays, which are closed; `Branch` with how the table came to be: `Implicit`, `Header`, `Dotted`; `Tables` for arrays of tables), the rules as the `toml` crate applies them (a dotted key may extend a table made implicitly by a header path, which makes it dotted). Errors are `line:column: message`. `inf` and `nan` are errors (a `Float` is finite). `stringify` writes a table's values, then its tables as `[sections]` and arrays of tables as `[[sections]]`.
Tested (`tests/toml.rs`) against the `toml` crate on curated documents and, with `STRATA_TOML_CORPUS`, the 711 UTF-8 files of toml-test's 1.1 list: same values, same refusals (all 493 invalid ones), `inf`/`nan` aside.
**`derive Toml`** (asked for by the user 2026-11-22, "like JSON"; built, branch `toml-derive`): `derivable(Record | Union) trait Toml`, `std.json`'s machinery adapted. Decisions: records carry no `type` key (a configuration file, not a message; a record in a union written out, `A | B`, gets one so it can be told apart); `Option` only as a field, `None` left out (TOML has no null); the methods are named for TOML (`to_toml`, `from_toml`, `from_toml_with`, `read_toml`, `write_toml`, derived `to_toml_at` / `from_toml_at`) because a type implementing two traits with the same method can't call it (`Json` and `Toml` together); `UnknownKeys` is `std.json`'s; `[toml] unknown_keys` in `strata.toml`; `Date` / `Time` / `DateTime` impls. Found on the way: derive was minutes slow on nested records (a `DateTime` field: 2+ min to store): `derive.rs` keyed every compile-time `Type` value by its printed, laid-out text, and remade a type's value on each access; keys are now `Debug` text and values are made once per type (4+ min → ~30 s for the test's program, cold).
Not yet: the tools reading `strata.toml` through it (they still use the `toml` crate, `src/package.rs`, until that code is Strata's); a writer that keeps comments and layout (editing `strata.toml` in place).

## Known gaps

- A list holding both an `Option[Int]` and an `Option[Float]` (`[a, b]`) makes LLVM refuse the IR (a `switch` with duplicate cases, seen 2026-11-22). `float_from_bits` gives infinities (only a NaN is `None`), though a `Float` is never infinite.
- A `Bool` option whose default is `true` can't be turned off (no `--no-x`), and `javascript:` URLs in `std.web`'s `href` aren't rejected (both listed where they were decided).
- FFI is C only (`extern c`, see "Foreign functions: `extern LANG`"): `main` can't yet ask for a native module's capability, and there is no std SQLite module yet.
- `strata verify` on the tasks example takes about 30 s of CPU, most of it Z3: two checks of `memory.mem_record` run into the solver's 20 s limit.
- `Files.read` (`host_read_file`) and `Console.read_line` don't check that the bytes are UTF-8: a file that isn't gives a `String` that faults later (`code_points` on it). Found with toml-test's `invalid/encoding` files; it should be an `FsError`.
- `d[k]` on dicts isn't accepted (`at` has no `Dict` version).
- `--json` is missing on `view`, `render`, `interface`, `status`, `done`, `test` and `run`.

Decided against (not gaps):
- **Explicit type arguments at a call** (`f[Money]()`; decided by the user, 2026-11-21): type arguments are inferred from the arguments and the expected type only.
- **Error conversion** (decided by the user, 2026-11-21): `!` only passes an error on when it fits the function's error type (the same type, a variant into its sum, a member into a union). No conversion functions, implicit or declared: errors stay explicit as types.

## Known limitations

- **Proofs cover integers, strings, records, sums, unions and lists (by position).** A loop keeps only the declared types and the invariants inferred or written for it; positions are lost through `filter` and `sort`; floats, dicts and sets are not modelled; trait laws are fuzzed only.
- Length conditions on a list are only decided as "empty" or "not empty" (`where len(it) == 1` with `where len(it) >= 2` needs a `[]` or `_` arm).
- **Verification is slow**: `verify` on `examples/tasks` takes about 30 s of CPU with an empty cache, on all cores. A solver process per query, one solver per run (`STRATA_SOLVER`), results keyed by `closure_hash` (see "Verification fast enough to run with every check" above).
- **Little is cached**: verdicts in `.strata/`, compile-time values and std's termination findings in `~/.cache/strata`, std's compiled library; no check results, and modules are read one at a time.

## Roadmap

1. **SMT verification, continued**: values as SMT datatypes, trait laws, match coverage, and `assumed` for dependencies. (Loop invariants, inferred and written, list contents by position, and `assumed` for capabilities and `extern c` are built.)
2. **Traits with laws**: e.g. `trait Monoid { … law assoc(a, b, c): … }` (built: laws are written in traits and fuzzed for every implementation, `verify::check_law`). Left: proving them with the solver.
3. **Agent-friendly CLI everywhere**: `--json` on every command, trace queries, and scoped workspaces and leases so several agents can work on different slices at once. The CLI *is* the agent API; no server is needed.
4. **Concurrency and iterators**: built (tasks, channels, `select`, `race` and cancellation, a `Clock` and timer arms; iterators with `FiniteIterator`). Left: a deterministic scheduler for tests, deadlock detection, cancelling blocking I/O, supervised scopes; `mock record` / `mock replay` for integration tests; deterministic replay debugging.
