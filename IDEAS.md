# Ideas, decisions and open questions

Everything that keeps track of where Strata is going: open questions, ideas, what has been decided (and whether it is built), known gaps and the roadmap. The [README](README.md) and [docs](docs/) describe what is built.

## Open questions (to discuss before building)

- **A field as a `mut` argument** (decided with the user 2026-11-21: allowed, as now). `shift(mut r.lo)` is the same as `mut t := r.lo; shift(mut t); r.lo = t`, and the record's own invariant is checked the same way after the call as after that assignment, so forbidding it would protect nothing. The check after a `mut` call is left out where the checker proves the parameter's type fits the variable's; undecided cases could become proof obligations for `verify`, with the runtime check kept only for what isn't proven.
- **Generating code from a type's shape** (decided 2026-11-21): see the decision "Derived traits, `comptime` and special methods" below.
- **Marking a `mut self` call** (built 2026-11-20, see docs/language.md "Mutation"). `mut queue.claim(2)`, as Hylo's `&x.append(1)`: required when the method takes `mut self`, an error otherwise. The tree is `Expr::Mut(Method(..))`; a `Mut` around anything else is an argument for a `mut` parameter. The parser's `marked` reads a place after `mut`, then marks the first method call on it, and later calls apply to its result (rendered `(mut q.claim(2)).len()`); as an argument the marked call is rendered in parentheses, `call((mut o.pop()), x, y)` (the user's form). Results are not places (user's point): `mut f(x).m()` is a parse error, and a result can't be passed to a `mut` parameter; name it first. Rejected: `(mut queue).claim(2)`, `claim(mut queue, 2)`, and a separate call operator.
- **What iterating a string yields** (decided by the user 2026-11-21; the three units built, see "Iterators and `FiniteIterator`"; `len` / indexing / slicing on units not yet). Nothing implicitly: a `String` is not a list and can't be the subject of a `for` (already an error today: "`for` needs a List, Set or Dict"). The unit is always named: `s.bytes()`, `s.code_points()`, `s.graphemes()` (names to settle), each giving an iterator a `for` can run over. Depends on iterators (roadmap 4); until then `chars` (code points, as a `List[String]`) stays. The same goes for length, indexing and slicing (decided 2026-11-21): `len(s)`, `s[i]` and `s[1..3]` don't work on a `String`; they are written on the unit, `len(s.bytes())`, `s.graphemes()[1..3]`. Today all three count code points. Indexing, slicing and `len` need a `FiniteIterator` iterator (see "Iterators and `FiniteIterator`" below); a string's units are finite, so they can be indexed. To settle when building it: the unit of the other builtins that take or return positions (`index_of`, `slice`, `get`), which the prover models on code points.
- **Iterators and `FiniteIterator`** (user, 2026-11-21; direction, not built). Two traits: `Iterator` (what a `for` runs over, and what `map` / `filter` / `fold` take as receiver) and `FiniteIterator` (it ends). `List`, `Set`, `Dict`, ranges and a string's units implement both; an unbounded generator implements only `Iterator`. `FiniteIterator` is what indexing, slicing and `len` require, and what lets termination checking say a `for` loop ends (today it knows this only for lists: "only `for` loops"); a `for` over an `Iterator` that isn't `FiniteIterator` is treated like a `while`. Named `FiniteIterator` (user, 2026-11-21: clearer than `Finite`, which means nothing apart from an iterator). Decided (user, 2026-11-21): `FiniteIterator` carries its length, known ahead of time (that is what shows it ends); the length may change where the value is mutable (a `mut` list). `map` keeps the length; `filter` keeps finiteness but returns something with a new length (on a list, a new list). Proposed (Claude, following Rust's `trait ExactSizeIterator: Iterator { fn len(&self) -> usize }`): a supertrait, `trait FiniteIterator: Iterator { fn len(self) -> Natural }`, which Strata already has (`trait Summary: Describe + Priced`). A supertrait is a requirement, not inheritance: implementing `FiniteIterator` requires an `Iterator` impl, but nothing is inherited or overridden and there is no subtyping of values. The user's concern: it looks like a kind of iterator, i.e. inheritance. To settle: that, whether a lazy `filter` returns an eager value (exact length) or a lazy one (only a bound: Rust's `size_hint` upper bound, which is enough for termination but not for indexing), and how `verify` uses `len`. **Step 1 built** (branch `iterators`): `trait Iterator[T] { fn next(mut self) -> Option[T] }` in the prelude (the element type is a trait parameter, as Strata has no associated types), and `for` over any value implementing it. The checker accepts the subject when its type satisfies `Iterator[el]` (`satisfies`, which also infers `el`), and then the loop is rewritten as `{ mut $iter_N := xs; loop { match mut $iter_N.next() { Some(p) => body, None => break } } }` (`types::lower_iterator_fors`) and the program checked again, so the compiler, the prover and termination see an ordinary loop; the second check only happens when a program has such a loop. Lists, sets and dicts keep their built-in loops (no `Iterator` impls for them yet), and `verify` says a `for` over an `Iterator` may not end. Decided (user, 2026-11-21): `FiniteIterator` is a supertrait of `Iterator` (`trait FiniteIterator[T]: Iterator[T]`; the inheritance reading is fine). `map` / `filter` are lazy, so a comprehension over an unbounded iterator is itself an iterator (an infinite comprehension). `verify` uses the length for termination first: a `for` over a `FiniteIterator` ends. Invariants over `len` come later. Next: `FiniteIterator` and termination through it, lazy `map` / `filter` / `fold` on any iterator, the built-in collections and ranges as iterators, comprehensions over iterators, a string's units. To settle when building: what a comprehension over a finite iterator gives (a `List`, as today for lists, or a lazy iterator), and where a lazy `filter`'s length comes from (its bound, the source's length, is enough for termination). **Step 2 built** (branch `iterators-2`): `trait FiniteIterator[T]: Iterator[T] { fn len(self) -> Natural }`, and `map` / `filter` / `fold` as default methods of `Iterator` (`map` / `filter` lazy, through the prelude's `Mapped` / `Filtered`). How:
- **The prelude carries code** (`types::PRELUDE_CODE`): definitions with bodies are added to every program when it is resolved (`with_prelude_code`), in the module `std.prelude`, so they are checked and compiled as the program's own and skipped where std is (`verify`, the views, the viewer's type map). Their traits' methods are named `std.prelude.len` and so on, as std's methods are named in their modules, and a program's impls of those traits name their methods the same way: apart from the builtins `len`, `map`, `filter`, `fold`, which lists keep. Calls (`it.len()`) find them through the receiver's traits (`implemented_method`, now for type parameters' bounds and trait-typed values too). Messages show them short (`ListIter.next`, `FiniteIterator::len`).
- **Termination:** a `for` over a `FiniteIterator` holds it in a `$finite_iter_N`; that `loop`, and the `next` call it makes, count as ending. This rests on `len`, which nothing checks yet (with invariants, later).
- **Build tests** (user, 2026-11-21): they no longer compare compiled output with `--interpret`, but with outputs recorded in `tests/data/build/expected` (`STRATA_BLESS=1` records them), recorded from step 1, where both agreed. The trait methods named like builtins had made the interpreter call `Iterator`'s `map` on lists.
**Step 3 built** (branch `iterators-3`; the user's idea: what is passed to `filter` must end, then `filter` and `fold` do):
- `fold` and `to_list` are `FiniteIterator`'s (on an unbounded iterator `fold` never returns: refused, "`fold` needs a `FiniteIterator`"), written as a `for` over `self`, which ends. `Mapped` / `Filtered` are `FiniteIterator`s when their source is (a filtered one's `len` counts, on a copy).
- Lambdas: termination already follows a lambda's calls from the function it is written in, so a call of a function-typed parameter (`f(acc, x)` in `fold`) counts as ending. An impl's call of its own trait method on a field of `self` (`self.inner.len()`) is recursion on a smaller value (values are finite trees), left out of the call graph.
- Comprehensions over iterators: the checker gives `map(it, f)` / `filter` / `fold` on an iterator to its methods, and `set(it)` / `dict(it)` on a finite one to the prelude's `set_of` / `dict_of`. So a comprehension over an iterator is a lazy iterator (finite when its source is), over a list a list as before.
- `verify`'s cross-check: a fault in a function the checked one calls is that function's, not "a bug in the prover".
**Step 4 built** (branch `iterators-4`; user, 2026-11-21: `xs.iter()`, not lists as iterators, which would clash with the list builtins `map` / `filter`): the prelude's `ListIter[T] = { items: List[T], at: Natural }` (an `Iterator` and a `FiniteIterator`), and `trait Iterable[T] { fn iter(self) -> ListIter[T] }` for `List`, `Set` (in order, `to_list`) and `Dict` (entries by key, `items`); ranges are lists. Calls find a built-in type's impls by its receiver too (`implemented_method`). The prelude's code's names (`ListIter`, `Mapped`, ...) are the prelude's: defining one again says so. **A string's units built** (branch `string-units`; user, 2026-11-21: the names `bytes` / `code_points` / `graphemes`, written in Strata over native byte access): `s.bytes()` and `s.code_points()` are the prelude's (`Bytes`, `CodePoints`, trait `TextUnits` for `String`; code points decoded from the UTF-8 bytes, moving past a continuation byte to the next start), over two native builtins, `byte_len(s)` and `byte_at(s, i)` (C runtime and compiler only: the interpreter, frozen, doesn't have them). `s.graphemes()` is `std.unicode`'s (`Graphemes`, trait `GraphemeText`; std is loaded for a program that calls it, as for `matches`): UAX #29's rules GB3 to GB13 with GB9c (Indic_Conjunct_Break, now generated into std.unicode_tables from the UCD's DerivedCoreProperties.txt, `tools/unicode_tables.py`'s second input), its tables decoded at compile time (`comptime`), checked against all 1093 cases of GraphemeBreakTest.txt (`tests/data/grapheme_break_test.st`). Found on the way: precompiling std deadlocked once std had a `comptime` (resolving std ran it, and compiling that waited for the std library being made: `llvm::building_std` now covers the resolve); a lambda's parameters didn't get types from an earlier argument's trait obligation (`it.map(x -> x.m())`: `settle_pending`). Next for strings: `len`, indexing and slicing on a unit (`s.graphemes()[1..3]`, decided above) and the string builtins moved to Strata over these iterators. Not yet: a nested comprehension whose inner source is an iterator (needs a lazy `flat_map`); a user's own `it.next()` loop isn't shown to end (a call of `next` through the trait may reach `Filtered.next`).
- **Regex verification scope** (decided with the user 2026-11-20; not built). By default, regex refinements are proven over ASCII strings only, and the result always says so ("proven for ASCII strings"). Such a proof counts as proven in an ordinary `verify` run. Under a `[verify] proven = [...]` rule it does not, unless the project opts in to accepting ASCII proofs; it is still reported as proven for ASCII either way. Full Unicode proofs are asked for explicitly where they matter (per module in `[verify]`, or per function). The interpreter stays fully Unicode either way. Pairs with "two solvers": ASCII classes are small enough for Z3 to decide exactly; full-Unicode proofs can go to cvc5, which decides the large classes.
- **Two solvers, each for its strengths** (user, 2026-11-20; direction). Z3 and cvc5 are both wired in (`STRATA_SOLVER`). Use both: route a query by what it contains (cvc5 for strings and large Unicode regex classes, which it decides exactly where Z3 times out; Z3 elsewhere), or run both and take the first definite answer.
- **Complexity / cost.** Separate from termination: a function can terminate and still take exponential time (naive `fib`, Ackermann). The user raised it as "another issue"; nothing is designed yet.
- **Transpilation / interop** with Python (Pydantic, JSON as the boundary), TypeScript and Rust. Later.
- **JSON as a boundary format: a derived `Json` trait** (user, 2026-11-21; direction agreed; built so far: see "`std.json`: a derived `Json` trait" under Decisions, which supersedes the details below where they differ). Today every value has one JSON form (`interp::to_json` / `Interp::from_json`; the JIT's `json` helpers): variants externally tagged (`"None"`, `{"Some": 3}`, `{"Queued": {...}}`), records as plain objects, integers beyond 64 bits as strings of digits, untagged unions read by trying each member in written order. That is useful for debugging but not for the main use the user sees: JSON from a web front end read straight into a record. Measured problems: with `Int | String`, `"5"` reads back as the `Int` 5; with `String | Int`, a big integer (written `"9223372036854775808"`) reads back as a `String`. The direction:
  - **a derivable trait** (`derivable(Record)` / `derivable(Sum)`, see "Derived traits" below) whose derive succeeds only for types with an unambiguous JSON form, so being `Json` *means* being serializable. Base types implement it built in. Full round-tripping of every value is not the goal; reading any JSON that fits the type is.
  - **`Option[T]` is the value or `null`** (or a missing key, for a field), not `{"Some": x}`. `Option[Option[T]]` can't tell `None` from `Some(None)`, so it isn't `Json`.
  - **a `"type"` key holding the type's name**, as TypeScript's discriminated unions do (user). Proposed: always on a sum's variants (`{"type": "Queued", "name": "a"}`, a variant without data either that or the bare string `"Queued"`); on a plain record written, but optional on input when the expected type is a single record (web forms won't send it). A variant with positional data needs a key for it (`"value"`?, or only record and no-data variants are `Json`). A field named `type` in a `Json` type is an error (or the tag key is configurable).
  - **records and `Dict`s**: reading is driven by the expected type, so they only need telling apart inside a union, where the `"type"` key does it; a `Dict[String, V]` in such a union could have a `"type"` key itself, so that union isn't `Json`. A `Dict` with non-string keys isn't `Json` either (or keeps the `[[k, v], ...]` form).
  - **unions**: `Json` only when the members' JSON kinds can't overlap (number / string / bool / null / array / object with a distinct `"type"`). `Int | String` qualifies once integers are never strings.
  - **integers**: always JSON numbers; a value beyond 64 bits is a fault when written and an error when read (user: "big integers are banned"). Open: JavaScript's numbers are exact only to 2^53, so a web client silently rounds larger ones. Options weighed with the user: write larger ones as strings (any `Int` works, but the JSON's shape then depends on the value: `number | string` for a TypeScript client), or refuse them (a fault when written, an error when read; the shape stays fixed, and with a `SafeInt` alias and `verify` covering derived code the risk is visible). The user leans towards refusing; Claude agrees.
  - **a JavaScript-like `Number`** (user's suggestion): `Float` is already an IEEE double that is never NaN or infinite (docs/language.md), which is exactly what JSON can hold: JSON has no NaN or Infinity (`JSON.stringify(NaN)` is `"null"`). So a `Number` with NaN/Infinity wouldn't go through JSON any better; reading `3` into a `Float` already works. Open: whether `Number` is still wanted for JS interop beyond JSON.
  - **to decide**: whether the current form stays as the debug/tool format (`strata run` output, verdicts, `data-on-click`, `to_json`) next to `Json`, or `Json` replaces it everywhere and non-`Json` values only get `show`.
  - **`Debug` and `Display`, as Python's `repr` and `str`** (user, 2026-11-21; built, branch `runtime-types`: `Display`'s method is `to_string`, `Debug`'s is `debug`, and an `impl` replaces either; see the `std.json` entry under Decisions). `show` (`interp::show`, used by `print`, `to_string` and f-strings) is today the compact JSON form, except that a top-level string, big integer or variant without data drops the quotes. Decided instead: two derived traits that every type has by default, overridable like any other trait (`impl Display for T { fn to_string ... }`). `Debug` is the value as written in code: a record with its type name (`Queued { name: "a" }`), strings always quoted (`"hi"`), `Some("hi")`, `[Red, Blue]`, `Dict { "a": 1 }`, `(1, "x")`. `Display` is the readable form: by default the `Debug` form; `String`'s is the one built-in difference (the text without quotes). Collections display their elements with `Debug`, as Python does (`["a b"]` vs `["a", "b"]`). `print`, f-strings and `to_string` use `Display`.
- **Changes are git commits** (built, `git_commit` in main.rs, asked for by the user). After a logged change (`record`: edit / rename / move / add) and at `strata done`, the package's files are committed with the change's message (`git add -A -- .` and `git commit -- .` in the package folder, so other staged work stays out). Nothing during a pending change. Off with `auto_commit = false` in strata.toml or `--no-commit`; skipped outside git and during a merge in progress; a failed commit leaves the change made and says why. Tests that commit by hand after strata commands no longer need to; the log-splitting test uses `--no-commit` to keep several entries in one commit.
- **Editing in an editor** (built, `edit_in_editor` in main.rs). `strata edit [MODULE | SELECTOR]` at a terminal with nothing piped in (or with `--editor`) opens, in `$VISUAL` / `$EDITOR` / git's editor / `vi` (through `sh -c`), the whole package with no argument (one file per module, all given to the editor), a module (`shop`, `main`, or its file `shop/orders.strata`, which may be new; a module's name wins over a definition's, and a definition is named with its module: `shop.total`, `main.main` for the root module's `main`), or the definitions a selector picks (one file per module they are in). Piped, `strata edit shop` puts the definitions into `shop`; there is no `--module` for `edit`. What is saved goes through `apply_edit` like a piped edit; definitions deleted from the buffer are removed. If it doesn't parse or check, the editor reopens with the errors on top (`// ✗ ` lines, dropped when read back); saving unchanged gives up. Errors go on top of the file of the definition they are in.
- **Removing or adding variants in a pending change** (built, `fix_matches` in pending.rs). Patterns can't be holes, so `match`es are fixed first: arms of removed variants are dropped (or only their alternative in an `a | b` pattern; nested ones like `Some(Pending)` too), a `match` on the changed type without a catch-all gets an arm `NewVariant => ?pending_N` (`Lost(_)`, `Lost { .. }`), and a `match` with no arm left becomes a hole. The edit prints what was dropped. Then expression holes as before (the expression walk skips patterns). Not yet: `let` / `for` patterns naming a removed variant still reject the edit.
- **Pending changes** (built, `src/pending.rs`). An `edit` whose own definitions check but that breaks other code isn't rejected: each broken use in the erroring definitions (a call, reference, constructor, method call or `is` test naming a definition whose interface changed, outermost first) becomes `?pending_N`, recorded with what it was and why, and the package enters a pending change (`.strata/pending.json`: the files before, the holes, the renames). Edits, renames and moves during it only write files (`record` in main.rs); `strata status` lists the holes; `strata done` logs the whole change as one entry (from the files before to now, with its renames), refusing while its holes are open unless `--keep-holes` (they become `?todo_N`); `strata abort` restores the files. `strata ci` refuses `?pending_*` holes, so half-done work isn't merged. Not yet: one pending change per package; a use the edit broke compatibly in an erroring definition is also turned into a hole.
- **Storage: hash references, and propagation** (discussed 2026-11-20; direction agreed, not built). The user prefers storing definitions by hash with references by hash and names in a separate table (Unison's model: renames become free, merges of new code can't conflict, several agents can add code at once), over a binary encoding of the same files (the encoding itself is now decided: see the next item). On an edit, dependents follow automatically when they still type-check ("option 1"), and otherwise get a to-do. The user's addition: while a to-do is open, the references to the old version are replaced with typed holes, so the agent sees exactly what to fill in. Before building: settle how a hole keeps what it replaced (the old call, for the agent), and that code with holes still checks but can't run. Status (2026-11-21): the propagation half is built as pending changes (`src/pending.rs`: broken uses become `?pending_N`). The storage half is not: module files hold self-contained, hashed definitions, but references are stored by qualified name, not by hash, there is no names table, and no object per hash (renames still rewrite every reference; two agents adding to one module still touch one file).
- **Storage: the tree, in binary** (decided with the user 2026-11-20; built: packages are stored in it, see below). Code is stored as the syntax tree, not as text: the AST is the language, and the current syntax is one front end among possible others (Nim-, Python-, C-, Haskell-like). The encoding is a compact binary format, not JSON (no serialization round-trips; big integers stored exactly). Ideally a module's `.strata` file *is* that binary, and text is rendered only when needed: `strata edit` already opens a module or definitions as text in the editor and parses what is saved, `render` / `view` print it. Rendered text files, if kept at all, are a read-only view that git ignores. Every change then goes through the tools (`edit`, `rename`, `move`), which check it and answer immediately; with a cache, several agents (the user guesses 3–4) could work in one codebase at once. Before building, settle:
  - ~~the format~~ **built**: our own, not a crate such as `postcard`, because Strata should be able to read and write it itself once bootstrapped (user). `src/binary.rs`, specified in `docs/binary-format.md`. LEB128 integers (zigzag for signed), one tag byte per enum variant, fields in order, strings by index into a table; canonical; corrupt input is an error, never a crash; no compatibility across format versions.
  - **Module files with a header** (built, branch `binary-header`, discussed with the user 2026-11-20: "header files from first principles, but inside the file"). One module file per module (now the `.strata` files themselves), or a bundle of them (`strata pack app.strata`). The header lists each definition's name, kind, `pub`, hash, interface hash, code hash, dependencies and size; each definition is self-contained (its own strings) and stores its interface (bodies as `()`) before its bodies. `store`'s hashes are now those of the binary encoding (no more printing to hash). Measured on `examples/tasks`: all headers 14 µs, all interfaces 82 µs, everything 166 µs (with each definition's hash checked), against 735 µs to parse the text. Files are larger than the first single-file format (27 KB vs 14 KB; 20 KB of source): three 32-byte hashes per definition, and strings repeated per definition. Not done yet: the tools don't use the header (they decode everything, then recompute hashes and the graph); see the next steps.
  - **Next steps, agreed with the user:** (5) read module files in parallel; (6) cache derived results (inferred types, check results) in `.strata/` by hash, and check a module against the interfaces of the modules it uses, re-checking dependents only when an interface hash changes; (7) a long-running process that loads once and reloads only files whose hash changed. Also: interned names in the AST (`Symbol(u32)` instead of `String`), only if profiling shows string handling is the cost.
  - **Binary is the format, `.strata` its extension** (user, 2026-11-20; built, branch `binary-main`). Packages and scripts store only binary module files, named `.strata`; nothing reads text as code any more. Text comes in only through edits: `strata edit` (stdin or the editor; outside a package, `strata --file F edit` writes a script or a folder's module without a log; since branch `script-edit-check` it then checks it, decided with the user: what doesn't check is still written, its errors printed, exit code 1) and `add` of a text file; `render` / `view` / the viewer print it, `render --split` writes `.st` text files that are never read back. `ci` checks each file is exactly the bytes strata writes for it. Git: `.gitattributes` marks `*.strata binary diff=strata merge=strata`; `setup-git` sets `strata render --file` as the textconv, so `git diff` shows text; the merge driver decodes the three sides, merges their text definition by definition and writes a module file, and a conflict leaves the file as text with markers until `strata resolve FILE`. The repository's `std/`, `examples/`, test data and the compiled prelude are binary (decided by the user: GitHub shows no diff for them). The log still carries each change's text (it is history, replayed by parsing). Open:
    - **changing the format** (decided by the user 2026-11-21): no backwards compatibility while the format isn't settled. `VERSION` stays `1`; a change to the tree converts every file in the repository in the same change (render with the old strata, read back with the new: docs/binary-format.md). Version numbers, and perhaps reading older versions, start once the format is settled. Each such change still touches every file, and other branches then conflict on binary files;
    - branches that edited text `.strata` files before this landed conflict with the binary files: re-apply the edit with `strata edit` (or render, merge, read back).
  - **Interned names** (built, branch `interned-names`): every identifier in the AST is a `Symbol` (`src/symbol.rs`), a `u32` into one process-wide table of texts; equal names are equal numbers. Reading a symbol's text takes no lock (append-only chunks); interning takes a mutex. The lexer interns identifiers as it reads them, the decoder once per string of a definition's table, the encoder looks names up by number. The resolver's scopes and tables, the checker's types (`Ty::Con`, `Ty::Rigid`), substitutions and `Env` are keyed by symbols; `x.sym()` converts (free on a symbol). Symbols order by their text, so sorted output doesn't change. Measured on `examples/tasks` (`src/bench.rs`, quiet machine): check 1.6 ms → 0.95 ms, resolve 200 → 137 µs, clone 68 → 38 µs, parse 570 → 520 µs; decoding unchanged (about 170 µs: the per-definition string tables, and checking each definition's hash). Not done: runtime values (`interp::Value`, the prover's `Val`) still name records, variants and fields with `String`; `Decl::name()` / `qname()` still return `String` (they are map keys in many places).
  - **Faster decoding, after a fast-lexer article** (user sent https://xnacly.me/posts/2025/fast-lexer-strategies/, 2026-11-20; ideas, not built). Decoding runs at about 160 MB/s today, against that lexer's 580–850 MB/s; the time goes into allocation (a `Box` per node, a `String` copy per name) and checking each definition's hash. What carries over: (a) **interned names** (built, see above): the AST holds `Symbol(u32)` instead of `String`, so decoding a name reads an integer, names compare and hash as integers, and the file's string table maps to symbols once per distinct string (the article's zero-copy string windows and per-atom hashing); (b) **a built-in string table** shared by every file (`Int`, `String`, `List`, `Option`, `self`, `it`, …) with fixed indices, like its prehashed keywords: shorter files, and those names are known without a lookup; (c) **an arena / flat AST** (nodes in arrays, children as `u32` indices): one allocation per module, free in one go (the article: parsing 2.1x faster, freeing 26x); the most invasive change; (d) **mmap** the module files, for large codebases only (ours are kilobytes). Not applicable: jump tables / computed goto (a one-byte tag in a `match` already compiles to one), character classification and SIMD scanning (there is no text to scan).
  - **Resolved references (step 4)** (user decided 2026-11-21: store resolved trees, print short names; built, branch `resolved-trees`). Every reference to a definition is stored by its qualified name; text shows each as short as the module's `use`s allow, so it is normalised (`orders.Line` written where `Line` is imported shows as `Line`). `resolve::stored_form` qualifies on write, `resolve::written_form` shortens on read: the resolver's walk in two new modes, which rewrite names only (not the desugaring or static calls `resolve` does). In memory, every tool still works on the written form. Consequences: a `move` reports every definition whose stored references changed, not only those whose text did; the merge driver merges each side shown alone, so another module's names stay in full in a conflict's text. Not done:
    - ~~the checker still resolves on load~~ (branch `stored-load`): programs are now worked on as stored, and shortened only to be shown (render, view, the viewer, the editor, diffs). Renames and moves can't capture names any more. The checker still runs the resolver over the stored form (about 150 µs on `examples/tasks`, mostly a pass that changes nothing but method names and declared names); a lighter path for stored code is possible, but `strata check` spent far more elsewhere: it resolved and type-checked the program three times (`types::check`, `Env::new`, `verify::static_refinements`). Now once (`types::check_and_elaborate`, branch `check-once`): `full_check` on `examples/tasks` went from 3.8 to 1.3 ms, `strata check` from 8 to 5 ms (2.5 ms of that is starting the process);

    - a module file shown alone (`git diff`) shortens from its own `use` lines; two modules imported with `*` that both define a name can't be told apart without loading them.
  - how it relates to the hash store above: a binary file per module, or one object per definition under its hash plus a names table;
- **Type checker speed** (user asked to look at it, 2026-11-21; first pass built, branch `checker-speed`). Profiled with macOS `sample` on a loop (`src/bench.rs`: `profile_check`; `allocations` counts allocations, which machine load doesn't blur). Done: declarations borrowed from the environment instead of cloned, error labels and hole obligations written only when shown (`Label`, `Lazy`), FxHash for every map (`src/fx.rs`), expression types recorded only for the compiler, and the environment for checking built from signatures. `examples/tasks`: a check 1.35 → 0.70 ms, 28,300 → 17,700 allocations; `strata check` 5.0 → 4.4 ms end to end (2.3 ms of it is starting the process). Left for later (user, 2026-11-21: good enough for now), by size:
  - types (`Ty`) cloned and dropped everywhere (about 20% of a check): sharing them (`Rc`) or interning them (a type is a number into a table, like symbols) would remove most of it;
  - resolution (13%), which also resolves the standard library on every check of a program that uses it: it could be resolved once;
  - the environment still copies every declaration (and the elaborated one, bodies included): it could borrow the program;
  - interning strings during the check (`Symbol::new`, 5%): call sites that turn a symbol into a string and back.
- **Verification fast enough to run with every check** (user, 2026-11-20; direction, not designed). If agents wait on verification it isn't worth having: the goal is a few milliseconds for a short function, so verifying can run alongside type checking. Measured on `examples/tasks` (67 definitions): `check` 10 ms; `verify` 13 s, of which 108 solver runs take 11 s. Two queries take 6.2 s and 2.8 s (they run into the solver's limits); the others take about 15 ms each, mostly starting a `z3` process. Fuzzing and the cross-check are most of the remaining 2 s. Verdicts are already cached by content hash in a package, so an edit only re-verifies what changed and what depends on it. Ways to get there:
  - keep the solver running: one `z3` / `cvc5` process in incremental mode (`push` / `pop`), or link Z3 as a library, instead of a process per query;
  - two tiers: a fast pass next to the type check with a small budget per query, where anything that doesn't finish is reported as still being checked; and a slow pass in the background (full limits, fuzzing, the cross-check);
  - a verification server, like a language server: it keeps the syntax tree, the checker's environment, the call graph and the verdicts in memory, re-verifies on each change, and answers commands, the viewer and agents (through the Strata MCP server). `strata ui` is already a server; this pairs with storing the tree in binary (load once) and the Strata IDE;
  - make the cache as modular as the proofs. A proof of a caller already uses each callee's contract, not its body. But cached results are keyed by `closure_hash`, the code of everything a function reaches, so editing a callee's body throws away every caller's result. Key them instead by the callee's interface, except where the body does matter: helpers the prover sees through (`transparent`), termination results, and the cross-check, which runs the callees;
  - run independent queries in parallel.
  To decide: what an agent sees while the slow pass runs, and whether `edit` waits for the fast pass.
- **Strata IDE**: the viewer as a standalone desktop app (Tauri; the backend is already Rust), speaking ACP (Agent Client Protocol) so agents such as Claude Code or Codex run inside it, with a Strata MCP server giving them structural tools (slices, check, edit, rename). The viewer would show live where each agent is working (log entries tagged with the agent's session). Idea stage.

## Ideas

### Language

#### Ranges, slices and comprehensions (built 2026-11-20)

Built on the binary-format branch (format version 3: `Expr::Range`, `Expr::Slice`, `Expr::Comp`); see docs/language.md. Decided along the way:

- `a..b` excludes `b`, `a..=b` includes it; a range is an eager `List[Int]` (iterators remain their own feature). Both ends are required, except in a slice.
- Slicing uses ranges, not Python's `:` (one syntax for both): `xs[a..b]`, `xs[..b]`, `xs[a..]`, `xs[..=b]`, on lists and strings, clamped as `slice` was. No negative indices: in a range `-3..0` already means the integers from -3, so `xs[..-1]` meaning "all but the last" would read two ways.
- `xs[i]` is the element, not an `Option`: `at(xs, i)` requires `0 <= i < len(xs)`, a runtime fault otherwise, and an obligation for `verify` like division by zero ("index in range"). `get(xs, i)` stays for the `Option`. Not yet: `d[k]` on dicts (the same, with "key present").
- Comprehensions: `[e for p in xs where c for q in ys where d]`, with `where` as in refinements; patterns allowed (`for (a, b) in ps`).
- The tree keeps them as written (they render back as written); `resolve` rewrites them into `range`, `slice`, `map`, `filter` and `fold` (`src/desugar.rs`), so the checker, interpreter, prover and LLVM never see them. Error messages show the builtin calls.

Decided by the user 2026-11-21 (not built):
- The builtins behind the range and slice syntax (`range`, `slice`, the step) become special methods (`@range`, `@slice`, `@step`; see "Derived traits, `comptime` and special methods"): overloadable, implemented through std traits, but not called by name. Code uses the syntax.
- `map`, `filter` and `fold` are not special: they are ordinary methods on any iterator (the receiver), taking a lambda, and stay callable by name; comprehensions keep desugaring to them.
- `take` and `drop` stay ordinary functions (they have no syntax of their own; `xs[..n]` / `xs[n..]` remain the slice forms).
- Steps: `0..n by 2` (and `0..=n by 2`), desugared to `@step`. `by` becomes a keyword.

Still open:
- `xs where it > 0` as a filter on a value (it reads like a refinement type).

#### Other syntax nits (noticed 2026-11-20; not decided)

- **Dict and set literals** (built): `Dict { "a": 1 }`, `Set { 1, 2 }`, `Dict[String, Int] {}`, and comprehensions `Dict { w: len(w) for w in words }`, `Set { x % 3 for x in xs }` (`Expr::Dict`, `Expr::Set`, `Comp` with a `CompKind`; desugared to `dict` / `set`). In a `for` / `if` / `match` header they need parentheses, like record literals.
- **`except` inside a `for` header** reads badly: `for _ in 0..opts.times except { 1 } {`. Proposed: the renderer parenthesizes any header expression (`for`, `while`, `if`, `match`) that ends in a `}`: `for _ in 0..(opts.times except { 1 }) {`. The parser accepts both. Done instead (user's choice, 2026-11-21): `or { … }` / `??` for an `Option` (`Expr::Or`) and `except { … }` / `!!` for a `Result` (`Expr::Except`), each only on its own type, so `Result[Option[T], E]` isn't ambiguous. The short forms are what the renderer writes for a single-value, one-line fallback. So `for _ in 0..opts.times ?? 1 {`.
- **`len(xs)` and `xs.len()`** are both accepted, as for every builtin; the renderer could pick one form (method form for chains, say) so code reads the same everywhere.

#### Default values for record fields (built 2026-11-20)

`field: T = value` in a record (or a variant's record payload); see docs/language.md, "Records and defaults". Decided: any expression with no variables in scope (not the other fields), checked against the field's type where the type is defined, and evaluated each time it is used. It applies in constructors (`desugar::defaults` fills them in after resolution), JSON input (`Interp::from_json`), and the command line (a scalar field with a default is an option, `--times 3`; a `List` field's default is used when no arguments are left). Mocks and fuzzing still generate every field. Not done: defaults for other types (`type Port = Int where … = 8080`), which the user set aside; a flag whose default is `true` can't be turned off from the command line yet (`--no-x`).

### Web UIs (direction agreed with the user 2026-11-20; steps 1-4 built, each step's "Not yet" below)

The second place Strata should be useful, after the command line: UIs in the
browser, written without JavaScript. The direction is the Elm architecture,
run on the server, in the way Phoenix LiveView and htmx work:

```rust
use std.web.{App, Html, div, button, text, on_click}

type Model = { count: Int where 0 <= it }

type Msg = | Increment | Decrement | Reset

impl App[Msg] for Model {
  fn update(mut self, msg: Msg) {
    match msg {
      Increment => self.count += 1
      Decrement => if self.count > 0 { self.count -= 1 }
      Reset     => self.count = 0
    }
  }

  fn view(self) -> Html[Msg] {
    div([], [
      button([on_click(Decrement)], [text("-")]),
      text(f"{self.count}"),
      button([on_click(Increment)], [text("+")]),
    ])
  }
}
```

(The syntax is a sketch; traits with a type parameter like `App[Msg]` may
need work.)

`strata serve` keeps each session's `Model` in memory and renders `view` to
HTML. A small, fixed JS file that ships with the runtime catches clicks and
form submits. `on_click(Increment)` puts the message's JSON in an attribute;
the JS posts it back, and the server reads it against `Msg` (refinements
checked, as for command-line options), runs `update` and `view`, and the JS
swaps the new HTML into the page.

Why it fits: users write no JS; no async is needed in user code; `update` and
`view` are pure, so they can be tested without a browser and the verifier can
prove invariants across every message (`count >= 0`); an unhandled `Msg` is a
non-exhaustive `match`. The interpreter is plain Rust (the solver isn't needed
to run code), so it could later be compiled to wasm and run the same `App` in
the browser, without changing user code.

Steps:
1. `std.web.Html` (**built**, branch `worktree-web-html`): `Html[M]` (element,
   text) and `Attr[M]` (attribute, flag, event), helpers (`div`, `a`,
   `input`, …, `class`, `href`, `on_click`, …), `render` and `document`.
   Text and attribute values are escaped; names are checked where they are
   written (`element(tag: TagName, …)`, `attr(name: AttrName, …)`; `AttrName`
   excludes `on…` so inline scripts can't be written), not in the type:
   `Html[M] = { node: Node[M] }` and `Attr[M]` wrap private sums, so only
   `std.web` makes them and the verifier has nothing to check in views
   (decided with the user: verifying markup is pointless; what matters is
   the Strata values put into it, which JSX will make explicit); events are `data-on-EVENT` attributes holding the message as JSON
   (new builtin `to_json`). Void elements can't have children (`element`'s
   `requires`). CSS goes in `style_sheet(css)` (not escaped, can't close the
   element) or `style_link(url)`. Everything in `std` is proven, and so is
   `examples/page`. While `Html`'s fields were refined, the prover needed two
   changes in `smt.rs`, kept since they help any recursive or generic type:
   `check_type` stops at the third nested level of the same named type (a
   recursive type like `Html` made it re-check every element of every list,
   level after level: minutes for a small page), with one unknown per (type,
   value) so an assumed result and a later check are the same atom; and
   validity is compared on types whose unrefined type arguments are erased
   (`erased`), so a generic helper's result `Html[M]` matches its use as
   `Html[Msg]`. Not yet: `javascript:` URLs in `href` are not rejected.
2. `strata serve` (**built**, branch `worktree-web-serve`): `std.http`
   (`Request`, `Response`, `Method` as a refined `String`, response helpers)
   and `fn handle(req: Request) -> Response`, called once per request with a
   fresh interpreter (`src/serve.rs`, std-only, one request at a time).
   Routes as in Hono (asked for by the user): `Router` with `app.get(pattern,
   handler)` etc., `:name` segments, `req.param(name)` an `Option`, HEAD via
   GET, 404 / 405. As with `Html`, the refinements (`Method`, `Pattern`) are

   so `Router` has nothing to prove (CI's older z3 gave up on regex
   refinements inside a list of routes). Building it fixed three things: a type's own method now
   comes before a function of another module with the same name when called
   as `x.m()` (`app.handle(req)` inside `fn handle`); termination no longer
   takes a local named like a function for a call of it (`let mut app` in
   `fn app`); the prover knows a function value's result is a valid value of
   its result type (`Val::FnOf`), and a lambda passed for a function-typed
   parameter gets valid arguments. Not yet: reading bodies and forms into

   reading a form straight into a typed record (`decode[NewTodo](fields)`,

5. Later: capabilities in `update` (database, LLM calls, HTTP client); the

**JSX-like syntax** (user: wanted at some point, for simplicity). Markup
written directly in Strata expressions, compiled to the `Html` helpers, e.g.
`<button on_click={Increment}>-</button>`. Helper functions come first; the
syntax is added on top of them later. The parser checks the static markup (tag and
attribute names, no `on…` attributes, no children in void elements) as
syntax; only the `{…}` insertions are Strata code, and their types do the
rest: a `String` becomes escaped text, an `Html[M]` a child, an `M` an event's
message. The verifier has something to say only where an insertion's type is
refined (e.g. `href={url}` with a `Url` that excludes `javascript:`).

Questions to settle:
- **Async first, or web first?** (user, 2026-11-20; undecided.) Async is still
  planned (roadmap item 4). The web design above doesn't need it in user code:
  the runtime handles concurrency, and each request is a plain call. Where it
  matters is `update` calling something slow (an LLM, an HTTP request): it
  would block the session, and with a sequential server, everything. Elm
  answers this without async: `update` returns *commands* (data describing
  what to do), the runtime performs them and feeds the results back as
  messages. Commands are values, so they're easy to test, mock and verify.
  Claude's view: build the web first, with commands, and design async after;
  the risk is that async later changes how commands are written. If async
  comes first, a command could simply be an async call.
- Can `view` use capabilities? Pure is simpler and checkable.
- Send the whole page on every message, or a diff? The whole page to start.
- Sessions: kept in memory to start; later stored through the ORM.

## Design principles (decided)

- **No effects.** Capabilities (database, queue, console, clock) are traits; code takes an implementation as a parameter or holds it in a field. `mock T` generates an implementation that respects the trait's contracts. Async and iterators will be designed later as their own language features, **not** as effects.
- **Immutable by default, mutable when declared**: `let mut`, field assignment, `mut` parameters and `mut self` with write-back to the caller's variable. Procedural code is normal, and there are no shared references.
- **Refinements are structural**; `type X = Y` with no `where` is an error, so use `distinct type` for a nominal type.
- **Modules meet only through their public (`pub`) contracts.** A folder of `.strata` files loads as modules, and `render --split` writes them back.
- **No backward compatibility.** Breaking changes are expected: never add shims so that older stored trees (`.strata/` objects) or old syntax keep working. Re-import from source instead.
- **Rendered code wraps at about 80 columns** by breaking lines, not soft-wrapping.
- **Viewer**: two levels (interface/source), the code view sliced around the selection, a type map as a separate view, and no Flow view.

## Decisions

### Verification: automatic theorem prover (SMT), with layered results
- Use an SMT solver (Z3 or cvc5) as the main verifier. Contracts (refinements, `requires` / `ensures`, trait laws) become proof obligations.
- Report one of four **layered results** per obligation:
  - `proven` (the solver proved it);
  - `fuzzed` (not proven, but no counterexample found);
  - `failed` (with the solver's or fuzzer's counterexample);
  - `assumed` (trusted: outside libraries, I/O).
  A project policy can require `proven` for chosen modules.
- **Loop invariants**: infer them where possible (e.g. bounds and accumulators). Explicit `invariant …` annotations only where they really help; agents may write them and the solver checks them.
- Callers are checked against a callee's **contract**, not its body, which fits modules meeting through contracts. Cache results by content hash, as `verify` already does.
- Suggested order:
  1. integer, length and string-format refinements;
  2. `requires` / `ensures` across calls;
  3. loop invariants;
  4. trait laws.
  Fuzzing remains the fallback for whatever the solver can't decide.
- Interactive proofs (Lean/Coq-style) come later, as a bigger separate project.

**Built (step 1 and most of 2)**: `src/smt.rs` and `verify::check_fn`. See docs/verification.md. Results: `Proven { checks }`, `Fuzzed { cases, discarded, proven, unproven }` (each unproven check with its reason), `Counterexample { .., found_by: solver|fuzzer }` (a solver model is replayed in the interpreter first, and counts only if it really fails), `Incomplete`. Z3 through SMT-LIB text over a pipe (`z3 -in`, `rlimit` for determinism, solver version in the cache key); `verify --smt` prints the queries (termination ones too), `--checks` lists proven checks. Cross-check: proven functions that terminate are fuzzed a little (`--cross-check`, step budget per run; past it, a run proves nothing); a failure there is reported as a prover bug. Policies: `[verify]` in `strata.toml` (`proven`, `terminates`, `no_recursion`, each a list of modules) and `--require`. Calls already use the callee's contract (requires checked, ensures assumed), and the same call with the same arguments gets the same result (memo), so refinements re-evaluated in assumptions and goals line up. Impl methods are proven against their trait's contract; laws are still fuzzed only. Solvers: `smt::solver()` returns a `Solver { bin, version, kind }`. `kind` is `Cvc5` when `--version` mentions cvc5, else `Z3` (so a fake solver in the tests is run like Z3). `Solver::args` is `-in -T:20 rlimit=20000000` for Z3 and `--lang smt2 --produce-models --rlimit-per=5000000 --tlimit-per=20000` for cvc5. 5M cvc5 units is about 4 to 10 s of hard nonlinear arithmetic; typical queries use thousands. cvc5 1.4.2 needs no `--strings-exp` for `str.replace_all` / `str.to_int`. Its model is one line, with negatives as `(- 6)` and a backslash as `\u{5c}`. `parse_values` / `parse_str` read both formats (unit test `values`). The whole suite passes with `STRATA_SOLVER=cvc5`, and no test had to change. The examples get the same verdicts with both solvers; cvc5 is about 2x slower on `examples/tasks`. There is no portfolio yet (both solvers in parallel, first answer wins). cvc5 decides large Unicode regex classes exactly and quickly, where Z3 times out, so with cvc5 those classes need not be approximated (see the Unicode-regex change).
Unions (`Val::Union`): a tag plus one slot per member *shape* (`val_key` / `type_key`: `Int`, `rec:Square`, `sum:Shape`, …; members of the same shape share a slot, e.g. `Positive | Negative` or two variants of one sum, whose inner tag is then constrained). Since shapes are disjoint the tag is a function of the value, as in the interpreter where a union value is just the member's value. Validity is `in_type` (= the interpreter's `value_in`: `shape_test` and `check_type`); merging values of different shapes makes a union; a `match` arm whose pattern can only match one slot rebinds the matched variable to that slot (exact under the arm's guard); a union used as an `Int`/`String`/`Bool` is `ite(tag = slot, member, fresh)`. Assigning a field of a sum or union value now makes it unknown (and the check unprovable) instead of keeping the old value. String builtins with an exact SMT-LIB counterpart are modelled (`slice` as `str.substr` with clamped bounds, `get`/`index_of` as `Option`s, `replace` as `str.replace_all` plus a not-empty-pattern check, `to_string` with a `-` for negatives, `ends_with`, `chars`, `is_digit`; `parse_int` exactly only for `-?[0-9]+` and digit-free strings, with the lemma `str.to_int x >= 0 <=> x in [0-9]+` that Z3 needs). `slice`, `get`, `take` and `drop` now accept big integers (saturated, so clamping is exact) instead of faulting. Z3 often gives up on `str.replace_all` with symbolic strings (those checks are fuzzed). Builtins that fault on some arguments are checks (`builtin_faults`, found 2026-11-21: before, an unmodelled builtin was a fresh value with no check, so `chr(n)` was "proven" and the cross-check caught `chr: -624 is not a character`): `chr` of a code point that is a character (its result `str.from_code` up to U+2FFFF), `ord` of one character (`str.to_code`), `split` with a separator that isn't empty, `repeat` with a count that isn't negative (its 100,000,000-character cap is gone from the runtime: a string too large is out of memory, as when built any other way), `float` of an Int below 10^308; `sqrt`, `floor`/`ceil`/`round` and float arithmetic (`+ - * / %`, faulting on a result that isn't finite) are checks never proven, floats not being modelled. So the prover can tell Ints from floats in lambdas, the checker records each lambda's type and writes concrete parameter types into the checked program (`annotate_lambdas`); `chars(s)`'s elements are one character each, and a list slice is a sublist (clamped). std needed: `max_code`'s value as its contract, `chr` guards in `class_of` and `parse_hex` and `json.read_string`, and `Float`'s decoder returns an error for an integer past 10^308 instead of faulting. Left unknown on purpose: `to_upper`/`to_lower`/`is_alpha` (Unicode tables), `trim` (Unicode whitespace at both ends), `split`, `lines`, `repeat`, `reverse`. Regexes (decided with the user: Strata regexes are modern Unicode regexes): `regex_model` is `std.regex.smt_model` (the tree translated in Strata, run as compile-time code; before, `regex-syntax`'s HIR in Rust); look-arounds only as `^`/`$` certain to be at the start/end; anything else is `None` (unknown). Z3 times out on unions of more than ~50-100 `re.range`s (cvc5 does not), so a class of more than `MAX_RANGES` (24) ranges makes `matches` a fresh bool between an under- and an over-approximation (`RegexModel::Between`); `regex_relations` adds exact inclusion/disjointness facts between patterns matched on the same string term, from `std.regex.relations`, a product of the two patterns' DFAs (bounded search; undecided means no fact). SMT strings stop at U+2FFFF (`MAX_CHAR`): classes are clipped there, and literals past it are unknown. Before, `str_lit` wrote them as `\u{e0041}`, which Z3 reads as 9 ASCII characters, so `len("\u{E0041}") == 9` was "proven" (the cross-check caught it). Proofs about strings hold for strings up to U+2FFFF; the cross-check is the backstop. The compiled fuzzer's strings for a pattern come from `std.regex.samples` (Unicode classes and word boundaries included); the interpreter's generator, frozen, still uses `rand_regex`.
Not yet: `assumed` (no outside code exists yet); loop invariants (loops forget what they change); list contents are "every element satisfies P" facts (`Val::List { len, id }`; `Vc::lists[id]` has a `Gen`, how an element is made, and guarded preds; `every` proves a property of an arbitrary generated element with the quantifier on the skolem side, `all_of` / `know_all` give `all(xs, p)` both directions; elements are made under their existence condition, so an empty literal can't make a path contradictory). Not modelled: positions and order (`xs[0]`, sortedness, permutations), relations between elements (uniqueness: `unique_ids`), `any`, `zip` / `enumerate`, dict and set contents; sequences (SMT `Seq`) could be added later for positions; floats, dicts, sets; `sum` is modelled only as "≥ 0 for non-negative elements, 0 when empty", `all`/`any` only when empty; generic callees lose precision (a result `MemQueue[P, E]` doesn't satisfy a `MemQueue[Int, String]` check, because element types are compared syntactically); unions whose members can't be told apart by shape (`List[Int] | List[String]`, `Box[Int] | Box[String]`, a type parameter, a trait, `Float`, `Dict`/`Set`, a refined sub-union) are unknowns.

### Termination and helpers (decided with the user, session 3; built)
- Termination is reported for every function: terminates (with how) / may not terminate (with why) / assumed (`terminates` marker, after the contract). See docs/verification.md. The viewer shows "may not terminate" in orange; diffs show it in the verification word.
- **No `decreases` clauses** for now (user: a `for` loop covers the case where you can name the bound). Instead the bound is inferred. For `while a < b`, the solver tries `b - a` (and the other comparisons). For recursion, a smaller piece of a parameter is detected first. Otherwise candidate measures are tried (`termination::candidate_measures`): integer parameters, `len` of list or string parameters, both differences of each comparison of parameters in the body, then pairs compared in order (Ackermann). Not covered: mutual recursion, measures built from more than a difference (`n * n - k`), recursion through a lambda.
- **Helpers are seen through in contracts** when they terminate and cannot fail (`termination::analyze` → `transparent`): no `requires`, no refined parameters, no `mut`, no division by a non-literal, no `assert`, no hole, no refined constructors, and only such helpers or total builtins called. A helper whose termination is only assumed is still seen through, and the proof lists it. In function bodies, calls are still checked against contracts only.
- Policies: `--require terminates` accepts an explicit `terminates`; `--require no-recursion` rejects any recursion, even structural.

### Integers and floats (decided, user, session 3)
- **`Int` is a big integer that is a machine integer while it fits** (like Python). Built: `Value::Int(i64)`, and `Value::Big(BigInt)` only for a value that doesn't fit (so equal numbers are equal values); arithmetic switches over on overflow, and a literal too large for 64 bits is `Expr::BigInt(digits)`. Integers beyond 64 bits are written to JSON as strings of digits (serde_json can't write larger numbers without `arbitrary_precision`, which breaks deserialising the internally tagged verdicts); they are read from a number up to 2^64 - 1 or a string. An integer pattern must fit in 64 bits.
- **Sized types live in the standard library as refinements of `Int`**: built in the prelude, `I8` … `I64`, `U8` … `U64`. They are verified like any refinement, and LLVM compiles each to its own width.
- **`Float` is `F64`**; `F32`, `BF16` and similar exist alongside, with their own LLVM representations. (Floats are not modelled by the prover yet; SMT-LIB has a floating-point theory for when they are.)

### Compilation before transpilation
1. **Native compilation through LLVM** to machine code, with a garbage-collected runtime (no borrow checker in Strata). This comes before transpiling.
   - **Step 1 (built, branch `llvm-backend`)**: `strata build` (`src/llvm.rs`) writes LLVM IR as text from the elaborated program and compiles it with `clang` and a C runtime (`src/llvm/runtime.c`); no LLVM library is linked into `strata`. Scalars (`Int` as `i64`, `Float`, `Bool`, `String`, `()`), functions, control flow, `match` on literals / conditions / refinement types, f-strings, a few built-ins; contracts checked at run time with the interpreter's messages. `tests/build.rs` runs each program both ways and compares. See docs/tools.md.
   - **Parity with the interpreter, so the JIT can replace it** (user, 2026-11-21; one stacked PR per item): (1) the small refusals; (2) unions beyond records and variants (`Int | String`), and branches whose values are laid out differently; (3) trait-value methods that mention `Self`, have type parameters of their own or a `mut` parameter, generic supertraits, returning a trait-typed value; (4) regexes (`matches`); (5) big integers; (6) `mock`; (7) `strata test` on the JIT (faults that return instead of exiting, captured output, compiled `test` blocks); (8) `strata verify` on the JIT (calling any compiled function with values, through JSON; a step budget). Later: `serve` (needs an FFI and a network library), `derive`'s compile-time evaluation (the same JSON bridge plus a step budget; the specialization is Rust already), a cache of compiled code (the JIT's `-O2` costs ~0.3 s on a medium program).
     - **(1) built** (branch `compile-small-gaps`): a field of a union of records at different places in each member (by the variant; one without it faults as the interpreter does), assigning a field of a union or a tuple (`pair.0 = …`, also added to the interpreter, which faulted `cannot assign`), any pattern in a `for` over a range, `==` on trait values (an equality entry in the table: the same implementation's, else unequal), the `stack:` line of a fault (`strata_enter` / `strata_leave` around the program's functions, not the compiled prelude's or lambdas, as the interpreter's), and running out of stack is `fault (Limit): stack overflow (recursion too deep)` instead of a crash.
     - **(2) built** (branch `compile-unions`): a union with members other than records and variants is a pointer: records' and variants' blocks as they are, any other member in a box `{ tag, value }` with a tag per member type, unique in the program (so a smaller union's values are a larger one's unchanged). Values are boxed where they flow into a union (`coerce`) and unboxed where the checker narrowed them (an arm's matched variable: `expr` reads the node's type). Type patterns and `is`, literal / list / tuple patterns (the member first), `==`, printing, dropping, refinement checks of a union-typed value (`-1 is not a `Positive | String``), and trait methods on a union (by the member; not a `mut self` one, which would write a member back where the union goes). Found in the checker, then fixed (branch `checker-union-fixes`): a declared type is the variable's, not its first value's (`mut u: Int | String = 3` made `u` an `Int`, so `u = "text"` was refused), and `List[Int]` is a type pattern (`CtorPat::Type`, the arguments in brackets, also what `match comptime` writes as `Option[x]`; it was parsed as a constructor's arguments and printed `List(Int)`).
     - **(3) built** (branch `compile-dyn-methods`): methods called on trait values that take or return `Self` as a whole type (the table's wrapper unwraps a `Self` argument, which must be of the same implementation, and wraps a `Self` result into a trait value), that take a `mut` parameter besides `self` (a slot through the table, written back), or that have type parameters of their own (a dispatcher per call's type arguments, switching on the pair's table among every table of the trait; dispatchers are made once the queue is empty, and again while new tables appear); methods of a generic supertrait (`super_sub` reads its arguments from `supers`); functions returning a trait-typed value. Still refused: `Self` inside another type (`List[Self]`, `Option[Self]`), and type parameters together with `Self` or `mut`. A `Self` argument on a trait value is refused by the checker (decided with the user 2026-11-21, branch `dyn-self-args`): `xs[0].bigger(xs[1])` could pass a `Ci` to `Sq`'s `bigger`, so it is an error with a `help:` (declare the parameter as the trait, `other: Shape`, to take any implementation; that is how the two meanings are told apart: `Self` is the receiver's own type, the trait's name any). Allowed: the receiver variable itself, or what methods returning `Self` make of it (`s.bigger(s.scaled(2))`). The table's check at run time stays (a `mock`).
     - **(4) built** (branch `compile-regex`): `matches(s, re)` with a literal pattern is compiled to a DFA when the program is: `regex-automata` (the engine under the interpreter's `regex`) builds `^(?:re)$`, and its states reachable from the start become tables (each byte's class, the next state of each (state, class), dead states, states that match at the end) that `strata_dfa_match` runs; Unicode classes work as in the interpreter. A bad pattern faults with the interpreter's message. Refused: a pattern built at run time (it would need a regex engine in the runtime; with a Rust runtime, `regex` itself), and a pattern whose DFA gives up (Unicode word boundaries) or passes 4M cells. Also: functions shown as values (`"<closure (x) -> …>"`, `"<fn twice>"`, as the interpreter), so `examples/page` compiles.
     - **(5) built** (branch `compile-bigint`): an `Int` in [-2^62, 2^62) is a machine integer as before; any other is a big integer, a pointer kept in the 64-bit values outside that range (above it for positive ones, below for negative ones), so indices, lengths and counts are unchanged, a big index is simply out of range, and comparing a small with a big integer needs no call. `+`, `-`, `*` stay inline when both operands and the result are small (their two top bits equal), else call the runtime; comparisons and `==` call it only for two big integers; `/` and `%` (Euclidean, as the interpreter's), printing, `float` (rounded to nearest, ties even; too large faults as the interpreter does), `floor` / `ceil` / `round` (exact), `parse_int`, literals and `Int` patterns handle big integers. The runtime's arithmetic (32-bit digits, schoolbook multiplication, bit-by-bit division) was checked against Python on 3,000 random cases. Big integers are counted and freed as any other object (decided with the user 2026-11-21, branch `free-bigints`): `counted` is true for `Int`, and each dup / drop of one is `@strata.int_dup` / `@strata.int_drop`, an inline test (`v + 2^62 < 0`) before calling the runtime, so a small one costs a compare and a branch (a loop of small arithmetic: about 3% slower). New `Int`s (arithmetic, `/`, `%`, big literals, `parse_int`, `floor`, generated ones) are temporaries; lists of `Int` copy their big elements as objects (`dup_slots` kind 2); a big integer's block comes from `strata_alloc`. A number literal is a constant (never counted).
     - **(6) built** (branch `compile-mock`): `mock T` is a trait value whose table's methods generate their results, as the interpreter's `mock_call`: `requires` checked (its fault is the interpreter's), then a value of the result's type generated until `ensures` holds (200 tries). A generator per written type and hints (`gen_fn`), as src/generate.rs: integers from the intervals the refinements allow (often their ends, or 0), lengths likewise, strings matching a refinement's regex (32 samples made when compiling, one picked at run time), unions by a member, variants by choice (the one with fewest fields past depth 3), trait types as mocks, and rejection until the refinement holds (300 tries). A mock's table is among its trait's tables, so dispatchers cover it. To decide: the random numbers are the runtime's (splitmix64 from 7), so a mock's values are not the interpreter's; a program that prints them differs, one that checks what they satisfy (as tests do) doesn't.
     - **(7) built** (branch `jit-tests`): `strata test` compiles the tests with the JIT by default (`--interpret` to not; `--jit` says why when it can't, and they are then interpreted; `--emit-llvm` prints their IR). Each `test` block is a function (`strata.test.N`, no frame on the call stack); `strata_test` runs one with a trap armed, so a fault `longjmp`s back with its kind, message and stack instead of exiting, and what it prints is kept; each starts as the interpreter's (no stack, the generators' numbers from the start). The report is printed by Rust, the same for both. Found and fixed on the way (the `tasks` example had never been compiled, having no `main`): a parameter of a generic trait type (`mut queue: Queue[P, E]`) wasn't compiled per implementation as a plain trait's is (`is_trait` wanted no arguments), so a `mut` argument went in as the value where the callee wanted a trait value; and a constructor or type pattern on a trait value (`match worker.console { Log { lines } => … }`) compared the table with a tag, so it never matched (it now compares the pair's table with the implementation's, then matches the value). A crash now prints the program's call stack (`crash (signal 11) in:`).
     - **(8) built** (branch `jit-verify`): `strata verify --jit` fuzzes compiled. A driver per function (`compile_fuzz`: free functions, generic ones at `test_instance`, not methods nor what takes a function) generates the arguments with `mock`'s generators, records each as JSON, and calls the function; all drivers are one module, compiled once (`jit::fuzzers`; the engine lives as long as the process), and `fuzz_limited` runs a case through `strata_fuzz` (the test trap, seeded, a step budget) when the function has a driver, under a lock (the runtime's state is global; verify's jobs are threads). The verdicts are `fuzz_limited`'s: an unmet `requires` of the function itself is a discarded case, a generator that can't satisfy a type skips, a hole is incomplete, any other fault a counterexample. Compiled code counts steps only in this mode (each loop iteration and call; 50M without a budget, the cross-check's 200,000 with one). The SMT solver's counterexamples are still replayed by the interpreter (they come as the interpreter's values). Decided with the user (2026-11-21, branch `verify-jit-default`): compiled is the default (`--interpret` to not, `--jit` says why when it can't; the inputs are the runtime's random numbers, which is fine), and a runaway case stays `too many steps`: `verify` runs code on inputs it made up, so a budget is its own rule, unlike running a program.
     - **No limits on loops and recursion** (decided with the user 2026-11-21, branch `no-limits`): neither the interpreter nor compiled code stops a `while` / `loop` or a `range` at a count (the interpreter's 1,000,000) or a recursion at a depth (its 2000). Like Python's `RecursionError`, but where the memory ends rather than at a set depth: a recursion runs until the stack is nearly out, then faults `fault (Limit): stack overflow (recursion too deep)`. The interpreter checks the stack left at each call (`stacker::remaining_stack`, 256 KB kept; on its 1 GB thread about 95,000 calls deep); compiled code catches the guard page (SIGSEGV or SIGBUS, on the running thread's own stack, so the JIT on strata's 1 GB thread goes about 33M deep and a native binary's 8 MB main thread about 260,000), as `strata_fault`, so a test's trap catches it too. The `stack:` line shows a recursion as one entry: `main -> down (95846 times)` (four or more calls in a row; compiled code keeps runs, not frames). `verify` keeps its step budget (`too many steps`): it runs code it generated inputs for, not the program. Found on the way: the interpreter copied a variant's fields on every read (a chain of 8,000 links took 32 s to build; fields are now shared, `Rc`), and checked a declared variable's whole value on each assignment even when its type has no refinement anywhere (now skipped, `plain`). Lists are still copied when read. Open: a native binary could run its `main` on a larger stack, as the JIT does, so the depth doesn't depend on how the program is run.
   - **Retiring the interpreter** (decided with the user 2026-11-21): LLVM is linked into strata statically, so compiled code can run anything the interpreter runs, compile-time code included; the interpreter goes, rather than being kept (or rewritten in Strata) for compile time. In order: (1) compile-time code without the interpreter (branches `comptime-data`, `comptime-jit`, built); (2) `verify` without it (literal refinements, the solver's counterexamples replayed, laws, fuzzing methods); (3) `run` / `test` without it, the JIT required; (4) `serve` (after the FFI), then `interp.rs` deleted (`Value` kept as the host's values). Rules so a future compiler (self-hosted, or another backend) isn't tied to how it's done now: compile-time code is pure (no capabilities), deterministic and bounded by a step budget, so any engine gives the same result; its results must not depend on the machine compiling (sized types, when they come, computed at the target's widths); the code generator's output stays text IR, only the JIT needs LLVM's libraries (a self-hosted compiler would bind its C API, `llvm-c`, statically linked as now).
     - **Compile-time code, built**: most of it is data (all 161 evaluations of a six-field `derive CommandLine`: a description written out, a known name, a field of one), read directly (`Expander::data`). The rest (`comptime $Self.fields.map(f -> shout(f.name))`, a kind's refinement, a trait's `requires`) becomes a function `{ known values bound; _ := e; () }`, checked with the program as it is before its derived `impl`s (compile-time code can't use them), compiled (`Entry::Comptime`: its result type the checker's, steps counted), run on the JIT under the test trap with the budget (5M steps), and its value read back from memory by its shape (`llvm::Shape`, `llvm/native.rs`: what the FFI will use too). A fault or the budget's end is the `derive`'s error, showing the code as written. Without the JIT feature, still interpreted (until the JIT is required). Found on the way: compiled `is` on a refined alias of a record (`x is Choice`) looked for the alias's own constructors and was always false.
     - **`verify` without the interpreter, built** (branch `verify-compiled`): literal refinement checks are probes (`let _: T = <literal>`, all in one module); the solver's counterexamples are replayed by a probe binding the values to the parameters' types (an invalid one discards it, as before) and calling the function; trait methods and laws are fuzzed through wrapper functions added to the program (`verify::wrappers`, `strata_verify_N_…`, their frames hidden from stacks; a law's wrapper ensures it holds), so `fuzz_limited` only ever runs compiled drivers, and what can't be compiled is skipped with the reason. Fuzzers are compiled from the elaborated program (checking it again needed one fix: a trait method named by an elaborated call, `Monoid::empty`). Probes and compile-time code are compiled unoptimized (O2 made `check` on `examples/page` 0.7 s; unoptimized, 0.04 s as before).
     - **`run` / `test` without the interpreter, built** (branch `run-compiled`): no fallback; what can't be compiled is an error naming it (`run`), or that test's failure (`test`, the others run). `run f [JSON-ARGS]` is compiled (a function binding the arguments, read from JSON against the types, then calling `f`; its result read back, a fault as `{"fault": ..}`, an argument breaking a refinement `invalid input: n: ..` from `f`'s own check), and `--trace` too (each function of the program calls `strata_trace_call` / `strata_trace_return` with its values as JSON: the interpreter's lines). Patterns built at run time match through Rust's `regex`, which strata gives the runtime as a function pointer (`strata_set_regex_engine`; a built program has none, and says so). `--interpret` stays, only to compare with in the build tests, until `interp.rs` is deleted with `serve` (after the FFI). **No changes to `--interpret` from now on** (user, 2026-11-21) for anything compiled code (the JIT) already handles: a gap only the interpreter has is left as is, not fixed. Found on the way: compiling a resolved program resolved it again, which in a package qualifies an implementation's methods twice (`core.core.enqueue`, the method's code empty: invalid IR) — the interpreted fallback had hidden it; compile-time code, probes and fuzzers now compile the resolved program as it is (`Checked::compiled`, `elaborate_resolved`), only the compiler's prelude resolved. Fuzzers are compiled only for what `verify` checks, unoptimized (faster on every example than O2 or the interpreter).
     - **Compile-time code and std at speed** (decided with the user 2026-11-21; std's own compile-time work, a regex library's for one, will be heavy): (1) **cache compile-time values** (built, branch `comptime-cache`): pure and deterministic, so a value is keyed by `closure_hash` of its function (the code and all it reaches) and the strata binary, kept as code in a cache shared by every program (`~/.cache/strata/comptime`, `STRATA_CACHE`; a two-type `derive Json` checks in 0.04 s warm, 0.11 s cold), read back as data (an entry that doesn't read is a miss); then batch a derive's evaluations into one module. (2) **stable constructor tags** (and box tags) (built, branch `stable-tags`): from the qualified name (40 bits of its SHA-256; a union box's from its member type's, above 2^40), not the program's numbering, so code compiled once reads values the same in every program (the FFI needs it too); a collision in one program is an error naming both; a match-heavy loop runs as fast as with dense tags. (3) **precompile std's non-generic code** (built, branch `std-precompiled`: the functions that aren't generic, take no trait value and don't read a package's setting (`setting("json.unknown_keys")` is written in per program, so they and their callers stay per program; 63 today), built the first time it is needed, about 9 s, with clang -O2 into `~/.cache/strata/std/<hash>/`; a program declares them instead of compiling them; under the JIT `dlopen` loads the shared library and the calls map to it, its own calls into the runtime resolving to strata's, exported; `strata build` links `std.o`; everything else the library compiles is internal to it. Not counted in steps (a runaway loop inside std isn't stopped by a budget); `--trace` compiles std with the program, so its calls are traced; `STRATA_NO_STD_LIBRARY` turns it off) at O2 into a library cached by strata's version and std's hash (generic code and copies made for a program's types stay per program; shared helpers `linkonce_odr`): under the JIT it is **dynamically linked** (loaded into the process, the program's calls mapped to it as the runtime's are), and an executable from `strata build` always links it **statically**.
   - **Next, roughly in order**: memory management (reference counting with reuse, decided below); `mut` parameters (by reference, in place); `main`'s capabilities (`Console`, `Files`, `Environment`) and options; compiled `test` blocks; skipping the runtime check of a contract `verify` proved; sized types (`I32`, `U8`, ...) in their own widths.
   - **Both text IR and the LLVM libraries** (decided with the user 2026-11-20). The code generator writes IR as text, which a Strata compiler can do too (it won't have LLVM's libraries unless they are bound); the libraries are used to run that IR fast. **Step 2 (built, branch `llvm-jit`)**: `strata run --jit` (cargo feature `jit`, inkwell on LLVM 23) parses the IR, runs LLVM's O2 pipeline and runs it with MCJIT, calling the C runtime compiled into strata. The goal is a fast interpreter, as Python feels: the JIT should become the default for `run` (and `test`) once big integers compile, and later compile per function, interpreting what doesn't compile yet instead of the whole program.
   - **Step 3 (built, branch `compile-data`)**: the compiler works from the checker's types (`types::elaborate_typed`: each expression's type, by node), not its own guesses. Records, variants, tuples and `distinct` types (blocks of 8-byte slots behind a tag unique per constructor; a `distinct` value is its underlying one), generics by monomorphization, own methods, every pattern but lists, `!` / `?` / `except`, generated equality and printing per type. Refinements of a record's fields are checked when it is built; afterwards only fields of a type argument's type are (`Option[Positive]`).
   - **Step 4 (built, branch `compile-lists`)**: lists (a header of length, shared buffer and offset: `drop` and `[x, ..rest]` share the buffer, and `push` writes in place past the end when no other list has used that slot, so `out = push(out, x)` is amortized O(1) while values never change), list patterns, `for` over lists, closures (a block: the function's address, then the captured values, by value), named functions as values. The list built-ins are Strata (`src/llvm/prelude.strata`, compiled with the program as the module `strata.compiled`) over a few native ones (`len`, `get`, `push`, `take`, `drop`, `range`, `+`); `sort` is a stable merge sort given the interpreter's order, generated per type. `examples/math.strata` compiles whole; list-heavy code runs 15-20x faster than interpreted.
   - **Step 5 (built, branch `compile-traits`)**: traits, by static dispatch: every receiver's type is known once generics are monomorphized, so a call goes straight to one compiled instance per (trait, method, receiver type), with `Self`, the impl's and the trait's parameters filled in; default methods are compiled per type; a variant with an implementation of its own is chosen by its tag; static methods take their type from the call (the hidden type parameter `elaborate` adds carries nothing). `examples/traits.strata` compiles (but for the regex in `Sku`). Not yet: values whose type is a trait (`db: Db`): they need a type's methods at run time, a table per implementation; that comes with capabilities.
   - **Step 6 (built, branch `compile-capabilities`)**: `mut` parameters by reference: the callee gets the caller's slot (a field passed `mut` gets a slot of its own, written back after the call), then the variable's declared type is checked, as the interpreter's write-back does. Capabilities: `main`'s `Console`, `Files` and `Environment` are made natively (`Terminal`, `Disk` from `.`, `Process`), and std's `host_*` operations are in the C runtime with the interpreter's results and error messages (Rust's `io::Error` text). A trait-typed parameter is compiled per implementation passed (the language's own meaning of `db: Db`), so its calls still dispatch statically. Not yet: options from the command line (`CommandLine`: the interpreter parses them in Rust, `cli.rs`; in Strata it needs a record's fields at run time), and a trait as a field's or a list element's type (a table of methods per implementation).
   - **Step 6b (built, branch `compile-dyn`)**: values of a trait type held anywhere but a parameter (a field `console: Console`, `List[Shape]`, a `let` with the trait as its type): a pair of the implementation's table (show as JSON, show, then each method of the trait and its supertraits, as small wrappers over the compiled instance) and the value. A concrete value is wrapped where it flows into such a place (a field, a list element, `push`, a `let`, an assignment, a branch, a return). A `mut self` call copies the pair, lets the method change the copy and stores it back, so values stay values. Not through a table yet: methods that mention `Self` beyond `self`, have type parameters of their own, or a `mut` parameter besides `self`; `==` on such values. Also: the write-back check after a `mut` call is left out when the checker proved the parameter's type fits the variable's (`types::refinement_within`).
   - **Step 7 (built, branch `compile-collections`)**: the string built-ins, dictionaries and sets, `xs[i]` / slices, format specs. A `Set` is a list kept sorted in the interpreter's order (`compare`, the generated `cmp`) without duplicates, a `Dict` a list of `(key, value)` pairs sorted by key (a design choice to review: lookups are binary searches, but `insert` and `remove` copy the list, O(n), where a balanced tree or a hash table would be O(log n) / O(1); the interpreter copies too). So equal collections are equal lists (`==` is the list's), `for` and `items` are the list's, and the built-ins are Strata over lists in the prelude (`set_from`, `dict_insert`, `set_union`, ... given the element type's order as a closure). The order follows `interp::compare` exactly: floats by `total_cmp` (-0.0 before 0.0), and a `distinct` value by its JSON (so `UserId(10)` sorts before `UserId(9)`, as in the interpreter: worth revisiting in the interpreter itself). Strings: native in the C runtime (by code point; `lines` is Strata over `split`); what needs Unicode's tables (`to_upper` / `to_lower`, `is_alpha`) gets tables the compiler makes from Rust's own (`char::to_uppercase`, `is_alphabetic`), emitted only when used, so both agree. Known differences, all rare: `to_lower`'s final sigma looks only at the neighbouring characters (Rust skips case-ignorable ones such as apostrophes and combining marks); a number `parse_int` reads that doesn't fit in 64 bits is an overflow fault (the interpreter makes a big integer); `ord`'s message escapes only ASCII control characters as Rust's `{:?}` would; `-0.0` and `0.0` are equal to the interpreter's `==` but not to its order, and a set's `insert` / `contains` / a dictionary's lookups search by the order, where the interpreter's `contains` / `get` use `==`. Not yet: regexes (`matches`): the interpreter uses Rust's `regex` crate, and matching it exactly natively means either linking a regex engine with the same syntax and semantics into the runtime or compiling patterns (usually literals in refinements, such as `Sku`'s) to code with the compiler: compile constant patterns to DFAs in Rust (the `regex-automata` crate can build a dense DFA) and emit the tables, which keeps the runtime small; to decide.

### Foreign functions: `extern LANG` (decided with the user 2026-11-21; not built)
One declaration form for every foreign language, `extern LANG fn ...`, with two mechanisms behind it:
- **`extern c`**: an in-process call through the C ABI. First, because the rest builds on it (SQLite, then the ORM).
- **`extern python` / `extern ts` / `extern rust`**: calls whose values cross as JSON, through the derived `Json` trait (PR #100, branch `json-trait`), not today's tagged debug form. That trait's mapping is what those ecosystems already produce: `Option` as the value or `null` (Pydantic `Optional`, TS `T | null`, serde `Option`), a sum's variants tagged with a `"type"` key (TS discriminated unions, Pydantic `Field(discriminator="type")`, serde `#[serde(tag = "type")]`), records as plain objects. So types and codecs on the other side can be generated (Pydantic models, TS types or zod, serde structs) and match exactly. A type crosses only if it is `Json`, as only FFI-safe types cross `extern c`: the derive is the check. Results are decoded against the declared type, refinements included, so a foreign function that breaks its contract is a fault at the boundary (a NaN from Python is a decode error, as `Float` is never NaN). `extern rust` can be a generated serde shim exported with the C ABI, i.e. `extern c` underneath. Python and TS run first as a subprocess speaking JSON lines (isolated, works without the JIT); embedding libpython / a JS engine later if speed asks for it. Open: large data (a NumPy array copied as JSON is slow): opaque handles to foreign objects (`extern python type Model`), or a binary path later; integers beyond 2^53 for TS (see the `Json` entry).

`extern c`:
- **Declarations, one at a time**: `extern c fn sqlite3_open(path: String, mut db: Sqlite3) -> I32`, `extern c type Sqlite3` (an opaque handle, only passed back). Each is its own definition (hashed, rendered, diffed like any other). Libraries are named in `strata.toml` (`[native] libs = ["sqlite3"]`, perhaps C files of the package to compile in as shims).
- **Types that cross**: the sized integers (`I8` … `U64`, as C's `int8_t` … `uint64_t`; plain `Int` doesn't, its size isn't fixed), `Float` (`double`), `Bool`, `String` (a NUL-terminated copy each way; a NUL inside is a fault), `()` (`void`), `extern c type` handles. A `mut` parameter is an out-pointer (`mut db: Sqlite3` is a `sqlite3**`), which is what `mut` already means: copy in, copy out. Not at first: structs by value, callbacks, buffers.
- **Contracts are assumed**: `requires` is checked before the call, the result's type and `ensures` after it (at run time: foreign code can lie). Never proven, never fuzzed: a function that reaches an extern is reported like one that reaches `host_*` ("it talks to the real system").
- **Capabilities (option b, user's choice)**: externs are called only from inside their own module, a module of extern declarations; that module turns them into a capability (a trait and its real implementation, as `std.fs` does with `Files` over `host_*`), and everything else works through the capability, so a signature still shows what code can touch. How a program gets the real implementation: see "Capabilities given to `main`" (revised with the user 2026-11-21).
- **Capabilities given to `main`** (decided with the user 2026-11-21; step 1 built, branch `capabilities`: `capability trait`, `capability Name { ... }` (expanded by `resolve` into a type with no constructor and an `impl` whose functions get an implicit `self`), `main` and tests asking for them (compiled: a null pointer, never counted; interpreted: an empty record), `verify` reporting their code and what takes one as assumed, the viewer's colour. Step 2 built, branch `capabilities-std`: std's `Console`, `Files`, `Environment` are capability traits and `Terminal`, `Disk`, `Process` capabilities; `main` (and `handle`, `init`, `update`) names `Disk` / `Process` and gets `Console` (the terminal) from the environment; the Rust table and `HOST_TYPES` are gone; a trait's method is found on a value of a type implementing it without the trait imported (`disk.read(path)` with only `Disk` imported). The interpreter (frozen) doesn't give a test the terminal). Replaces the "private constructor" idea above.
  - **`capability trait`**: an interface to the outside world (`Console`, `Files`, `Database`). Anything may implement one (fakes for tests do); the marker says what it is for.
  - **A capability** (proposed syntax `pub capability Sqlite { pub fn open(path: String) -> Result[SqliteDb, SqlError] { ... } }`): a named set of functions that reach the outside world, with no data. Only the runtime makes one, only for an entry point; no constructor, no JSON, no `mock`. Its functions are called on the value (`sqlite.open(path)`), never on the name, so holding the value is the permission. It may implement capability traits (`pub capability Disk {}` with `impl Files for Disk`), which covers std's `Terminal`, `Disk`, `Process` and removes the table hard-coded in Rust (`capability()` in src/cmd/run.rs, the compiler's entry).

The program's signature lists everything it can touch, used or not.
  - **Only `Console` is chosen by the environment**: `fn main(mut console: Console)` gets the terminal under `strata run`, a fixture in tests, a recorder under `--trace`. The run mode is an implicit parameter of `main`, not visible by default; a flag in `strata.toml` (name to settle) lets `main` ask for it to see or override the choice. No `default` implementations otherwise. `Files` and `Environment` are named concretely by `main` (breaking `examples/wc`, `tasks`, ...).
  - **Syntax** (decided with the user 2026-11-21): capabilities are ordinary parameters (`sqlite: Sqlite`), in `main` as anywhere; no effect lists and no separate `with` clause for entry points. The declaration has its own keyword (`capability Sqlite { ... }`), and the viewer colours capability names (and capability traits) differently from types, wherever they appear.
  - **Libraries**: a capability is only *made* at an entry point; a library with no `main` defines capabilities and code that takes them as parameters (`pub fn migrate(sqlite: Sqlite, ...)`), and the program passes its own on. A library's `[native]` C is linked into every program that depends on it (once `[deps]` are fetched). Tests may ask for real capabilities like `main` (decided with the user 2026-11-21): `test "opens a file" (sqlite: Sqlite) { ... }`, for a library's integration tests; a test that doesn't ask uses fakes through capability traits.
- **Only compiled code calls them** (user's choice: no libffi). `strata build` declares them in the IR and links the libraries; the JIT loads the libraries and resolves the symbols. The interpreter (`run --interpret`, or a `main` the JIT can't compile) refuses a program that reaches an extern, saying so.
- **In the tree**: `DeclKind::Extern` added as the last tag, so existing files stay readable (no re-encoding).
- **Later**: the `host_*` layer as `extern c` declarations over `runtime.c`, instead of four hand-written cases per builtin (`stdlib.rs`, `interp.rs`, `llvm.rs`, `jit.rs`).
- **Order**: (1) syntax, tree, binary format, checks (FFI-safe types, externs not `pub`, callers in the module only); **built** (branch `ffi`): `DeclKind::Extern`, the checks, the interpreter's refusal, and `verify` reporting anything that reaches a native module as assumed (step 3 done early, since generating a handle crashed the fuzzer); (2) compiled calls, `build` and the JIT, libraries from `strata.toml`: **built** (branch `ffi-calls`): `[native] sources / libs`, conversions in `llvm.rs` (`foreign_call`), the JIT compiling the sources into a library with clang and loading it, `Option` of a handle for NULL (needed for out-pointers: a `mut` argument must start as something), `examples/fuzzy`; (3) `verify` and the interpreter's refusal; (4) `std` SQLite behind a `Database` capability; (5) `extern python` over JSON, then TS, then Rust.

### Mocks: fakes for tests (decided with the user 2026-11-21; step 1 built, branch `mocks`: `mock Name = { ... }` (a `mock` flag on `TypeDecl`, files re-encoded), test-only (the resolver), left-out methods generated (`resolve::mock_methods`: each answered by a generated `mock` of the trait), `verify` assumes them, hidden in `view` / the viewer. ### Derived traits, `comptime` and special methods (decided with the user 2026-11-21; steps 1-2 built)
Command-line options need code made from a record's fields; so will JSON codecs for compiled programs and the ORM. Instead of a hidden Rust generator (`src/cli.rs` today) or general metaprogramming over syntax trees, a trait can say how each of its methods is derived, as ordinary Strata code specialized per type at compile time (as Zig's `comptime` does). A derive returns a real function, never a syntax tree.

```rust
use std.typing.{Record, Field}

/// A record whose fields are a program's command-line options.
pub derivable(t: Record) trait CommandLine
  requires all(t.fields, f -> is_option_type(f.type)) {

  derived fn from_args(args: List[String]) -> Result[Self, CliError] {
    given := parse(comptime t.fields.map(spec), args)!
    t.try_make(f -> read(f, given))
  }

  derived fn help(program: String) -> String {
    help_text(program, comptime t.doc, comptime t.fields.map(spec))
  }
}

fn read(comptime f: Field, given: Given) -> Result[f.type, CliError] {
  match comptime f.type {
    Bool => Ok(given.has(f.name)),
    Int => parse_number(given.text(f.name)),
    ...
  }
}
```

- **`derivable(t: Kind)`**: parentheses, not brackets: `t` is an argument, a compile-time value describing the type derived for (`Self` is that type, `t` describes it). Its type is a kind from `std.typing` (`Record`, `Sum`, `Choice`: a sum whose variants carry nothing); deriving for another kind of type fails at the `derive` line. `requires` states finer conditions as a contract checked at compile time, naming the offending field.
- **`derived fn`**: a method with an ordinary body, specialized for each type it is derived for. A method without `derived` is a default method, or one the user must write.
- **Using it**: `derive CommandLine for Options`, or `derive CommandLine for Options { fn help(program: String) -> String { ... } }` to write some methods by hand (as overriding a default method). After specialization it is exactly an `impl` with those bodies: no inheritance, no relationship at run time. `impl CommandLine for Options { ... }` with every method written also works: it is an ordinary trait.
- **`std.typing`**: ordinary types describing types, imported when writing a derivable trait (like Python's `typing`): `Record` (`name`, `doc`, `fields`), `Sum` / `Choice` (`variants`), `Field` (`name`, `type`, `doc`, `default`), `Variant`. `t.make(f -> ...)` builds a `Self` from a function giving each field's value (applied once per field, at compile time; each result must have that field's type); `t.try_make(f -> ...)` does it with a `Result`, stopping at the first `Err`. The syntax tree is only read through these descriptions. Self-hosting (user, 2026-11-21): `std.typing` should be the type-declaration part of the eventual syntax-tree module (`std.ast`) the compiler in Strata needs, not a separate model, so the self-hosted frontend reuses `Record`, `Sum`, `Field`, `Variant` and a derive reads the same structures the compiler does.
- **`comptime`**: on expressions (`comptime t.fields.map(spec)`: evaluated at build time, the result put in the program), functions, and parameters (`comptime f: Field`: the function is compiled once per value, so `f.type` is a real type in each copy). `match comptime f.type { ... }` keeps only the matching branch. Compile-time code can't take capabilities (so it is deterministic, which the type system already shows) and must terminate (proven by `verify`, or within a step budget, else the build fails saying so). Not for generics: type parameters already do that.
- **Checking**: a derived body depends on the type, so it is checked when it is specialized, at each `derive ... for T` (as Zig and C++ templates are); errors point at that line and the field. The kind and `requires` catch most mistakes first. Less powerful than generating trees (a derive can't change a signature or add top-level definitions), which keeps derives tame.
- **Special methods, marked `@`**: value-level specials are methods with a reserved `@` name, declared in std traits and implemented like any trait method: `trait Add[Rhs, Out] { fn @add(self, other: Rhs) -> Out  law associative(...) }`, then `a + b` on such a type. Also `@mul`, `@neg`, `@index`, `@call`, `@iter`, ... For a numpy-like library: generic numeric code (`T: Add[T, T] + Mul[T, T]`) and laws `verify` checks. In the tree a special method is a function with a kind (an enum), not a magic name: the checker enforces each kind's shape, `a + b` and a call of `@add` are the same node, and the text is only one rendering of it.
- **Order of work**: (1) the syntax (parser, printer, binary format) and the checks; (2) the specialization: `std.typing`, `comptime` (run by the interpreter during checking), producing ordinary `impl`s that everything after it (checker, interpreter, compiler) sees unchanged; (3) `CommandLine` written this way in `std/cli.strata`, `main` calling `from_args`, and `src/cli.rs` removed (its messages and `--help` text kept exactly; tests compare the old and new on the same arguments). Then options compile. Special methods and operator overloading after.
- **Revised (decided with the user 2026-11-21; built, branch `comptime-for`)**, replacing what above differs:
  - `derivable(Record) trait X requires ...`: no argument; `$X` is a type's description (`$Self`, `$f.type`: `f.type` is a type, `$f.type` its description). `std.typing` only defines the description types (`Record`, `Sum`, `Choice`, `Field`, `Variant`, `Type`), to name them in signatures and kinds.
  - Descriptions are read with ordinary list functions. Building or taking apart a value needs its variant known at compile time (binding-time analysis: literals, `$X`, the variable of a `comptime for` or of a match comprehension, `comptime` parameters and `comptime e` are known, and what is made only of them). `make` is not a real method: on a description not known at compile time it is an error saying to use `comptime for`. Rejected: dispatching at run time on a description (a `Variant[T]` with an index), as implicit. Possible later: `match found { v => Some(v.make()) for v in $Self.variants, _ => None }`.
  - `comptime for v in $Self.variants { ... }`: the loop runs while compiling, its body written out once per element (Zig's `inline for`).
  - Match comprehensions, compile time only, arm first as list comprehensions: `match self { v => kebab(v.name) for v in $Self.variants }`; the point is the exhaustiveness check (at run time a loop does it). A general language feature, not only for derives.
  - `$Self.make(f -> e)` / `try_make` for records; `v.make()` (no fields) or `v.make(f -> e)` for a variant. `select` is gone. Still to add: `$T.check(x)` (a refinement checked into a `Result` with the interpreter's message).
- **Types as compile-time values (decided with the user 2026-11-21; replaces the description types above; building, branch `typing-defs`)**. The old `std.typing` had two models of a type that didn't meet: descriptions of declarations (`Record`, `Sum`, and `Variant`, a copy of `Record`; a variant without fields was a `Variant` with no fields) and `Type`, a type as written (`Named`, `Refined`, `Function`, `Nothing`, `Union`), linked by `$`. Working back from what `std.cli` and `std.json` read, nothing needs a definition written out as data: every read starts at a type and goes one step (`.fields`, `f.type`, `.variants`), and code tells shapes apart with type patterns (`Option[x] =>`, `Choice =>`), not by matching the data. So:
  - **One `Type`**, a type known while compiling (as Zig's `type`), opaque: the compiler answers its properties when asked, so a recursive type (`Tree`) is no problem. No `$`: `f.type.fields`. A declaration only gives a type a name and a doc; the line is named vs. unnamed, not declaration vs. use (`Option[String]` is named `Option` with `args`; `Int where it > 0`, `A | B`, `(Int) -> Bool` have no name).
  - **Every type has** `name: Option[String]`, `doc: List[String]`, `args: List[Type]`, `written: String` (as written, for messages), `condition: Option[String]` (a refinement's, as written: text until `std.ast` has an `Expr`, then that; `check` evaluates it), and `t.check(x)`. Refinements and `distinct` are not a shape: a refined record still has fields.
  - **Its shape**, what code switches on (with the type patterns `Record`, `Tuple`, `Sum`, `Choice`, `Union`, `Atom`, `Int`, `Option[x]`, `Distinct[y]`, `Param`, ...): a record has `fields: List[Field]`; a tuple (`(Int, String)`, or a variant `Circle(Float, Float)`) has `elements: List[Type]` (user: a positional element isn't a field; not `items`, a dictionary function); a sum has `variants: List[Type]` (each a record, tuple or atom: variants are types); a union has `members: List[Type]`; a function type has `params` and `result`; a type with one value is `Unit` (`()`, was `Nothing`) or an atom (a variant without fields, a named unit, only defined in a sum); a built-in (`Int`, `String`, `List[x]`, ...) is told apart by name and `args`; a type parameter (`T`) is `Param`. (Later, with "Sums and unions are one thing": no `Sum` kind and no `variants`; a sum is a `Union` with `members`.)
  - **`Field`** stays a record: `name`, `doc`, `type: Type`, `default: Option[String]`, with `f.default_value` and `f.of(x)`; its `written` is `f.type.written`.
  - **Building**: `t.make(f -> e)` / `try_make` for a record or a variant with fields; `t.make((i, e) -> x)` for a tuple (index and element type); `v.make()` for an atom. A tuple's element is read with `x.0`.
  - Gone: `$`, `Definition` vs `Type`, `Variant`, `Named` / `Refined` / `Function` / `Nothing` as data, `Field.written`. Kinds in `derivable(Record | Sum)` are the shape patterns. Variants can't carry a `///` doc yet (the tree has none), so a variant's `doc` is empty.
  - **Built** (branch `typing-defs`): `Type` is a record (`name`, `doc`, `kind: Kind`, `args`, `written`, `condition`, `fields`, `elements`, `variants`, `members`, `params`, `result`), the lists a kind doesn't have empty; `Kind` is `Record | Tuple | Sum | Union | Function | Atom | Unit | Builtin | Param`, and `Choice` is `Type where it.kind is Sum && all(it.variants, v -> v.kind is Atom)`. `Self` is the type derived for, as a value (`Self.fields`, `match comptime Self`); `x.0` in a match comprehension's arm reads a tuple-shaped variant's element. Opaque in effect, not in the language: a named type's lists are written out except inside itself (a recursive type) or four named types deep, where they are empty; reading them from a type known while compiling (`f.type.fields`, `Self.variants`) always writes them out in full, so only compiled compile-time code walking deeper than that sees the empty lists. A refined type is named as its base (`Int where it > 0` is `Int`, with its `condition`); an alias or `distinct` type has its own name and the shape of what it stands for. `$` (`Expr::Describe`) is gone from the tree. Also fixed: the printer wrote `comptime (a ?? b)` as `comptime a ?? b`. Not yet: reading the `i`th element when `i` is only known while compiling (`x.0` must be written); `name` being an `Option` makes code write `v.name ?? ""` for variants, which always have one. (Later, with "Sums and unions are one thing": no `Sum` kind and no `variants`; a sum is a `Union` with `members`.)
- **Step 3 (built, branch `cli-derive`)**: `CommandLine` is a derivable trait written in Strata (`std/cli.strata`): `from_args(program, args)` gives the options, `ShowHelp` or `BadArgs`; `strata run` calls it, and `src/cli.rs` only says which types are options. Its messages and `--help` are the old `cli.rs`'s (compared on `examples/hello` and `examples/wc`). New for it: `$T.check(x)`, `comptime t: Type` parameters, `f.default_value`, `Option[x]` type patterns, kind patterns (`Choice`, `Sum`, `Record`) in `match comptime`, `std.typing.compile_error` and `Field.written`. Options in a compiled program: built (branch `compiled-options`): `main`'s entry calls the derived `from_args` with the program's name (argv[0] without its folder) and arguments, then prints the help (exit 0) or `error: <message>` (exit 2) as `strata run` does; `strata run --jit` too (the JIT now refuses IR that calls a runtime function its table lacks, instead of jumping to address 0). Not yet: "more than one `List` field" isn't reported; a record-level refinement on the options faults instead of a message; the printer writes `Option[x]` patterns as `Option(x)`.
- **Step 1 (built, branch `derive-syntax`)**: The syntax is parsed, printed and stored (`derivable(t: Kind) trait ... requires ...`, `derived fn`, `derive Trait for Type` with or without a block, `comptime fn`, `comptime` parameters and expressions, a field named `type` after a dot); `derive`, `derived` and `derivable` are keywords only at the start of an item, so they stay ordinary names elsewhere; `comptime` is reserved. The checker refuses derivable traits, `derive` and `comptime` functions with a message saying they come next; a `comptime` expression is evaluated as written until then.
- **Step 2 (built, branch `derive-expand`)**: `src/derive.rs`, run right after resolution (and desugaring): each `derive X for T` becomes an ordinary `impl`. `T` is described as a value of `std.typing` (`Record` or `Sum`), checked against the kind (a refinement too: `Choice` is `Sum where ...`) and `requires` in the interpreter; each `derived fn` is specialized (`t` and `comptime` values written in, `comptime e` evaluated, `make` / `try_make` turned into the record's construction, a call of a function with `comptime` parameters turned into a call of a copy made for those values, with `f.type` and the types `match comptime` binds written in). The checker checks the results, not the generic bodies. Known limits: only a lambda's parameters hide a known name (not a `let`); functions with `comptime` parameters are specialized only from derived code; a failed `requires` names the condition, not the field; compile-time code taking a capability isn't refused yet (it can't get one: only `t` and `comptime` values are in scope); the budget is 5 million interpreter steps.
- **Sums** (built, branch `variant-names`): `t.select(v -> test, v -> value)` gives `Some(value)` for the first variant whose test holds (both specialized with `v` known), else `None`; `v.make(f -> e)` / `v.try_make(f -> e)` build the variant `v` (nullary, positional or record fields).


### Long-term goal: self-hosting
The compiler should eventually be written in Strata. Gaps to close first:
- **Native compilation** (built: `strata build` through LLVM, and the JIT for `run`, `test` and `verify`'s fuzzing): the interpreter is too slow to run a compiler.
- **Efficient mutation of collections**: in-place updates when a value has a single owner (as in Swift / Koka), instead of copying. Reference counting is built; reuse (Perceus) is not yet.
- **String and byte primitives**: characters, slicing and indexing (built, on code points; to become explicit units, `s.bytes()` and the like) (see "What iterating a string yields").
- **Early `return`, and `!` / `?`** to propagate errors (built).
- **A small native runtime**: GC (reference counting, built), I/O (the `host_*` layer, built), and binding to the SMT solver (not built: the solver is still a process per query).

Bootstrap plan: write the frontend (lexer, parser, printer) in Strata and test it against the Rust one, then the checker, then compile the Strata compiler with itself and check that its output stops changing (a fixed point).

**`std.ast`: the syntax tree in Strata, read and run by Strata code** (asked by the user 2026-11-21; step 1 built, branch `std-ast`). So parts of the compiler can move to Strata now: code in Strata reads `.strata` files, walks and builds trees, and runs them.
- **The tree**: `std.ast` mirrors `src/ast.rs` node for node, fields in the same order, variants in the order of their binary tags. Names differ where Strata needs it: variants are unique per module and don't reuse a type's name (`IntLit`, `StrLit`, `Var`; `VarDecl` for the statement; `IntPat`; `Equal`, `Less` for the operators; `Fallback` for `x ?? v`), and fields aren't keywords (`pre` / `post` for `requires` / `ensures`, `compile_time`, `terminating`, `mocked`, `conditions` for a derivable's `requires`). With unions-are-sums (merged), `Payload.MemberType` (tag 3) is a union member defined elsewhere; `Describe` went with `$` (the `std.typing` redesign).
- **One representation for values** (user, 2026-11-21, with the host-values work): values the host makes or reads (compile-time results, `run f ARGS`, verify's counterexamples, the Codebase snapshot) become Strata syntax, i.e. `std.ast` literals: what `Debug` prints, what `comptime e` writes back, what a compiler in Strata works on. `src/ast_value.rs` (Rust tree → the `std.ast` value, as `debug` writes it; `strata header FILE --tree`) is the first piece: the Codebase snapshot can be built with it. `std.typing` stays the checked description of types (what a derive reads); `std.ast.TypeDecl` is how a type is written.
- **Step 1 (built)**: `std.ast` (the types); `std.ast.binary`: `read` (module files and bundles), `read_header`, `decode_module`, `decode_definition`, `encode_definition`, `take_bodies` / `put_bodies`, refusing what `binary.rs` refuses (truncation, lengths past the end, non-canonical integers, unknown tags, nesting past 10,000, non-UTF-8 strings, a NaN); `std.utf8` (`encode`, `decode`, `decode_range`); `Files.read_bytes` (a default: the bytes of `read`; `Disk` reads them with `host_read_bytes`); built-ins `float_bits` / `float_from_bits` (compiled only). Tested (`tests/ast.rs`) against Rust on every module file in the repository, a program with every node, and a bundle: the same trees (`debug` vs `header --tree`), each definition re-encoded to the file's bytes, every prefix of a file refused. Reading all 39 module files (std included) and re-encoding them takes about a second. Found on the way: the verifier treated any type nesting more than 8 levels as refined (`refined_in`'s depth cut-off), so every `std.ast` value had validity checks it couldn't prove; it now visits each reachable type once instead.
- **Not yet in step 1**: the SHA-256 hashes (reading doesn't check them, so a flipped byte inside a definition can still decode; only definitions are written, not module files), and the header's names of `impl`s (they need the type printer). SHA-256 needs bit operations on integers: **decided** (user, 2026-11-21): operators `&`, `|`, `^`, `<<`, `>>` on `Int` (**built**, branch `bit-ops`): Python's meaning (two's complement infinitely sign-extended, `>>` rounding down, a negative shift a fault), Rust's precedence (tighter than comparisons: `|` < `^` < `&` < shifts < `+`), binary tags 14-18 (added at the end: old files read unchanged); `|` ends a refinement or a `where` pattern (the parser's `no_pipe`), so a bit-or is parenthesized there; the printer shows a bit operation compared in parentheses (`(x & 255) == x`, as the user wrote it, since C reads `x & 255 == x` the other way), which covers those places; compiled inline when both operands are small, in the runtime for big ones; the verifier models a shift by a literal and `x & (2^k - 1)` exactly (`*` / `div` / `mod` by 2^k), other uses as bounds only (one constant per operation and operands, so a refinement assumed and checked again is about one value). Not in the interpreter (it refuses them). With them, **step 1b (built, branch `ast-hashes`)**: SHA-256 in Strata, **private to `std.ast.binary`** (user, 2026-11-21: nobody should use it thinking it is a vetted, safe hash; it isn't constant-time and hasn't been reviewed as cryptography, so std gets a public hash only once one has been). Checked for what it does: FIPS 180's examples, the million `a`s included (a test in the module, run by `strata --file std test`); every length from 0 to 200 bytes, longer ones up to 20,000 bytes (from 8,192 bytes the length in bits takes three bytes, as in the million-`a` example, which doesn't fit on a command line) and constant inputs against the `sha2` crate (224 inputs); and all three hashes of every definition in the repository; about 100 KB hashes in well under a second. **A project tests only its own code** (user, 2026-11-22): `strata test` runs the tests of the project's own files (the package's, or the script's), not those of what it imports (std; dependencies, once fetched), which are compiled, verified and tested on their own: std's run when std itself is the program (`strata --file std test`). `strata test --with-deps` runs them too. (The program's own definitions come first in the resolved program, so the compiler takes the tests among those.) Seen on the way: `strata run f ARGS` took quadratic time in a list argument (50,000 elements 2.6 s), because compiling a list literal asked, for each element, whether a later one may assign (`Func::operands`); fixed separately (branch `operands-linear`: 200,000 elements in 0.2 s). `without_notes` in `std.ast`, `hash` / `interface_hash` / `code_hash` in `std.ast.binary`, and `decode_module` checking each definition's hash, so a flipped byte never reads as another tree; `tests/ast.rs` checks all three hashes of every definition in the repository against the headers. Still not written by Strata: whole module files, whose entries list each definition's dependencies (that takes resolving names: the front end's resolver). Seen on the way (not changed): `verify` reports a fault inside a callee (`main` calling `d(0)`, `d` dividing by its argument) as "a bug in the prover" from the cross-check, although the callee itself is reported.
- **Step 2: running a tree in Strata** (`std.ast.eval`, not started): **the start of the self-hosted front end** (user, 2026-11-21), not a second interpreter for running programs (the JIT does that). So it is built the way the front end will be: over stored trees, with its own name resolution (references to definitions are stored qualified; method calls and locals as written, so it finds a method from the receiver's type and the `impl`s, as `resolve.rs` does), values as `std.ast` literals (`IntLit`, `CtorExpr`, `ListExpr`, a closure as its lambda and environment), tested against the compiled programs' recorded outputs (tests/data/build/expected). Front-end pieces next to it, each tested against the Rust one: the printer (tree to text), then the lexer and parser.
- **Step 3: LLVM from Strata** through `extern c` and `llvm-c`: code generation stays text IR (a string, see the LLVM toolchain decision), so only the JIT needs the C API: `LLVMParseIRInContext`, the ORC `LLJIT` (`LLVMOrcCreateLLJIT`, `LLVMOrcLLJITAddLLVMIRModule`, `LLVMOrcLLJITLookup`). The FFI gaps that blocks: a `char *` that C still owns (an error message freed with `LLVMDisposeMessage`: read as a `String` and given back, not just copied), calling a function pointer (the address the JIT gives; a C shim in `[native] sources` works meanwhile), library paths and flags in `[native]` (LLVM's `-L` / `llvm-config --libs`), and arrays of handles (only for the builder API, which text IR avoids). `extern python` / `ts` / `rust` (FFI step 5) are not built; they're a separate step.

**`std.regex`: our own regex engine, in Strata** (decided with the user 2026-11-21; not built). A self-hosted compiler can't use Rust's regex crates, so regexes get a library written in Strata, used language-wide (programs call it like any std module) and by the compiler. It replaces, one use at a time: `regex` (the interpreter's `matches`), `regex-syntax` (parsing patterns for the prover, the generator and the code generator), `regex-automata` (DFAs for literal patterns in compiled code, and the inclusion / disjointness facts of `regex_relations`) and `rand_regex` (generating matching strings for the fuzzer and `mock`). It also gives compiled code patterns built at run time, refused today because they need an engine in the runtime; the runtime stays small (C), since the engine is ordinary compiled Strata.
- **The engine is the definition of Strata regexes**: interpreter (while it lasts), compiled code, prover and generator all follow it. Rust's crates are only the reference it is tested against (differential fuzzing), then removed.
- **The full dialect stays**, word boundaries and anchors anywhere included (user: the library is for every program, not only for compiling). Parts that can't do a feature say so, as now: the DFA builder refuses Unicode `\b`, the prover leaves it unknown, the Pike VM runs everything.
- **Design**: a parser into a Strata syntax tree with the Unicode semantics (`\d`, `\w`, `\s`, `\p{..}`, `(?i)` folding); a Thompson NFA run by a Pike VM (linear time, no backtracking; captures, `find` and `replace` possible later, which a DFA can't give); a DFA builder (subset construction over character or byte ranges) for literal patterns and for products of two patterns; a generator; the SMT translation reads our tree instead of the HIR.
- **Unicode tables**: a `std.unicode` module generated once from the Unicode Character Database by a script and checked in, also for `to_upper` / `to_lower` / `is_alpha` (made from Rust's `char` today). Compiled programs keep only the tables they use.
- **Speed**: the compiler runs Strata code with the JIT, not the interpreter (user: the interpreter is being retired, the JIT is the interpreter from now on), so building DFAs for large Unicode classes at compile time is compiled code.
- **Step 1 (built, branch `regex-parse`)**: `std.regex.parse` reads a pattern into a `Regex` (`Empty`, `Literal(String)`, `Class(List[(Int, Int)])`, `Look(Assertion)`, `Repeat`, `Capture`, `Concat`, `Alternation`): the syntax first (an AST, as regex-syntax's, so nesting is limited the same way: 250), then its meaning with the flags threaded through (a flag set in a group lasts to its end, across `|`), and the tree built by constructors that simplify as `Hir`'s do (literals joined, `a|b` a class, a common prefix lifted, `a{1}` is `a`), so equal patterns give equal trees. `std.unicode` has sets of code points as ranges (union, intersection, difference and negation stepping over the surrogates as Rust's `char` does, so the ranges are regex-syntax's to the code point), property lookup with UAX #44 loose matching, simple case folding; `std.unicode_tables` (195 KB, Unicode 16.0.0) is generated by `tools/unicode_tables.py` from regex-syntax's tables (made by ucd-generate from the UCD), each set a string of numbers decoded on use. `tests/regex.rs` prints both trees the same way (`show`) and compares them, error or not, on ~280 curated patterns and 1000 random ones (`REGEX_SEED`, `REGEX_CASES`; 40,000 agreed before merging; in the interpreter, as CI runs it, a pattern takes ~50 ms). Not yet / found on the way:
  - speed: with std precompiled (PR #137), `std.regex` and `std.unicode` are in std's cached library, so a program calling `parse` starts in ~0.10 s (1.25 s compiling them with the program, `STRATA_NO_STD_LIBRARY`), and a pattern parses in ~0.4 ms. Literal patterns, nearly all of them, can still be parsed while compiling (`comptime parse(...)`, or the compiler for `matches` with a literal: step 2), their trees then constants;
  - the tables are data, not code: they were `match`es on names (a 1,700-arm `match` became a 9,000-line function, and a program using `property` took 1.2 s to start); they are now sorted constant lists of names and values, searched by halving (0.3 s), and case folding is two constant lists (`folding_keys`, `folding_others`) instead of a string decoded for each `(?i)` literal. For this the compiler makes a list or tuple literal whose elements are all constants a constant itself (see the memory entry);
  - error messages are our own (regex-syntax's show the pattern with a caret); only "error or not" is compared;
  - the Unicode data comes from regex-syntax for now; the script reads the UCD files once the crates go;
  - tooling (fixed by PR #127): `strata --file std edit std.M` accepted definitions that `strata --file std check` then rejects (a parameter named `min` hiding the function); and `strata edit M` run inside `std/` (as a package) names the module `M`, not `std.M`, and starts a `strata.log`, so std's modules must be edited with `--file std` and their `std.` names. Variants can't have `///` doc comments (the parser refuses them), so a sum's variants are documented on the type.
- **`comptime e` in ordinary code (built, branch `comptime-anywhere`)**: evaluated while compiling, as a derive's (on the JIT, values cached), and written in as a literal, so `comptime parse("…")` is a constant tree and the program never calls `parse`. `e` may use definitions only (a variable around it is an error that says so). Functions that are specialized where called (`comptime fn`, `comptime` parameters, derived ones) are left alone. Found on the way, and the cause of a run that took 22 GB: evaluating one resolves the program made for it (the cache key, `closure_hash`), and that program still held the `comptime` being evaluated, so resolving it evaluated it again, without end; the program made for compile-time code now leaves out ordinary code holding a `comptime`, and the pass doesn't run inside itself. Constructors of constants (`Some(1)`, a record, a `Regex`) are constant data too (branch `const-ctors`), so a `comptime parse(...)` tree allocates nothing. Not yet: `strata --file F edit` of a script accepts a `comptime` that `check` refuses.
- **Step 2 (built, branch `regex-pike`)**: `std.regex.compile` makes a Thompson NFA (`Inst`: `Chars(ranges)`, `Split`, `Jump`, `Save`, `Assert`, `Done`; repetitions unrolled, at most 250,000 steps), and `is_full_match` runs it as a Pike VM over the text's code points: the set of states, no backtracking, assertions evaluated between characters as regex-automata's `LookMatcher` does them (word characters `\w`'s, Unicode or ASCII). `full_match(text, pattern)` is what `matches` means. Compiled code matches a pattern built at run time with it (`std.regex.match_code`, then `pattern_error` for the fault), so built executables have them too, and the runtime no longer reaches Rust's `regex` (`strata_regex_match` is gone). `tests/regex.rs` compares it with `regex`'s `^(?:p)$` on curated patterns and texts and on random ones (texts made by `rand_regex` from the pattern, then changed a character); 12,000 random patterns agreed. Difference, on purpose: a pattern is a regex on its own, so `a)|(b`, which Rust's `regex` accepted inside its `^(?:…)$`, is an error. Not yet: captures and `find` (the VM tracks states only, `Save` is a no-op); a pattern is parsed and compiled at every call (10,000 calls of a short one: well under a second); literal patterns still use regex-automata's DFA (step 3), and the interpreter and the prover Rust's crates.
- **Step 3 (built for compiled code, branch `regex-dfa`)**: `std.regex.automaton` builds a DFA from the NFA by subset construction: the code points split into classes at every range's ends (a `\w` pattern has ~1,600), `^` holding at the start only and `$` at the end (what follows it can't read a character); a pattern asserting anything else (lines, word boundaries), or making more than 4,000 states or 2M cells, keeps the Pike VM. `matcher(pattern)` is `Deterministic`, `Pike` or `NotARegex`. Compiled code makes each literal pattern's matcher while compiling (`literal_patterns` in llvm.rs: compile-time evaluation, cached, its value a function `strata.matcher.N` returning it as data) and calls `std.regex.run_matcher`; the program's code is left as written, so messages still show `matches(it, "…")`. regex-automata is gone from the code generator (and `strata_dfa_match` from the runtime); a program calling `matches` now includes std. Found on the way: a trait method named like a builtin (`find`) took the builtin's calls on every type (PR #161), and `STRATA_MEMORY=check` listed what compile-time code had made in the same process as the program's (its list now starts with the program). Not yet: the generator and the SMT translation (step 4).
- **Step 3, the prover (built, branch `regex-relations`)**: `std.regex.relations(a, b)` is `(a <= b, b <= a, disjoint)` on the two patterns' languages, explored on the product of their DFAs (pairs of states reachable on the same text while one side is alive, at most 50,000; classes split wherever either DFA's do); `false` when it doesn't hold or can't be decided (a pattern without a DFA: lines, word boundaries, too many states). The prover's `regex_relations` calls it as compile-time code (cached on disk, and per pair in the process), so regex-automata is out of the compiler: it stays only as a dev-dependency, the reference `tests/regex.rs` compares `relations` with on curated pairs and random ones (each pattern, its union with another, `(?:p)+` within `(?:p)*`); 12,000 random pairs agreed: never a relation regex-automata disproves, and its answer whenever both patterns have a DFA. Less than before: a pattern with line anchors (`(?m)^a$`) gets no facts (regex-automata's DFA did them); the prover asks only when one of the two patterns has a large class, and the cross-check still runs.
- **Step 4, the generator (built, branch `regex-generate`)**: `std.regex.samples(pattern, n, seed)` makes `n` texts from the tree: a class picks printable ASCII three times in four when it has some, an unbounded repetition goes up to 8 past its minimum (as `rand_regex`), an alternation picks a branch, assertions make nothing; each text is kept only if the pattern's matcher accepts it, so word boundaries and lines work too (`a\bb`, which matches nothing, is an error). A linear congruential generator in Strata (the same texts for the same seed). The compiled generator's 32 samples per pattern (`regex_samples` in llvm.rs) come from it, as compile-time code (`stdlib::regex_value`, shared with the prover's relations); before, `rand_regex` read patterns without Unicode, so `\p{L}` couldn't be generated and the function was skipped. `tests/regex.rs` checks every sample against `regex` on curated and random patterns (10,000 random agreed), and that only a pattern matching nothing or asserting more than the text's ends has none. Found on the way: a `matches` in a parameter's own refinement (`s: String where matches(it, "…")`) wasn't seen by `with_std` or `literal_patterns` (they walked bodies, not written types), so fuzzing such a function panicked (`no entry found for key`); both now use `decl_all_exprs_mut`, and calling a function missing from the program is an error, not a panic. Not yet: the SMT translation from our tree (`regex-syntax`); the interpreter's generator keeps `rand_regex` (frozen).
- **Step 4, the SMT translation (built, branch `regex-smt`)**: `std.regex.smt_model(pattern)` is the prover's model, `ExactModel(r)` or `Between(under, over)` for a class past `max_smt_ranges()` (24) ranges, translated from our tree as `hir_to_smt` did from regex-syntax's (anchors only at the text's very start or end, classes clipped at U+2FFFF, `Under` keeping the ranges touching Latin-1 then the widest, `Over` filling the smallest gaps); `smt_exact` for the unit tests. `regex_model` and the tests' `regex_to_smt` call it through `stdlib::regex_value`, so the compiler no longer uses `regex-syntax`, `regex-automata` or `rand_regex`: only the frozen interpreter does (`interp.rs`, `generate.rs`), so the crates go when it does (step 5). `tests/regex.rs` keeps the old Rust translation as the reference: 12,000 random patterns and the curated ones give the same text. A cold verify costs about the same; warm, each pattern's cache lookup adds a little (0.8 s on 14 patterns).

### Error handling, strings and mutation (decided)
- **Done**: `except` blocks (`e except { fallback }`, `e except err { ... }`, the fallback may `return`), `!` / `?` propagation, early `return`, f-strings, and string primitives (`chars`, `get`, `slice`, `index_of`, `replace`, `lines`, `repeat`, `reverse`, case, `is_digit` / `is_alpha` / `is_space`, `ord` / `chr`). Strings are indexed by character. See the README section "Errors".
- **Mutation of a `mut` value happens in place**, with no copying, whenever nothing else holds the value. The hard part is knowing when that's the case: use the absence of shared references plus ownership or reference counting (as in Koka's Perceus) so updates through a mutable binding are real in-place updates.
- **Errors that say what was probably meant** (the user, 2026-11-21: as Rust's): an error names the problem in the program's terms, then `  help:` lines with what to write instead (`other: Shape` for a `Self` argument on a trait value). New errors should do this; older ones could be gone through.
- **Memory: reference counting with reuse, as in Koka's Perceus and Lean 4** (decided with the user, 2026-11-21; was: Boehm to start). Values never change once built and there are no shared references, so an object only points to older ones: the heap has no cycles and counting frees everything, with no cycle collector. The compiler inserts `dup` (one more owner: count + 1) and `drop` (one owner fewer: count - 1, freed with its contents at 0), moving a value at its last use instead of dup-ing it, and leaving read-only parameters borrowed (the caller keeps ownership; no counting in the callee). An update (`x.f = e`, a `mut` parameter, `push`, `insert`) happens in place when the count is 1 and copies first otherwise (copy-on-write), so copy-in/copy-out stays the meaning and in place is only the implementation. Without threads or async, a count of 1 really means nothing else can see the value. Rejected: Boehm (an outside library, and no in-place updates), precise tracing (stack maps from LLVM, and no in-place updates either). Steps: (1, built, branch `gc`) a count word before every object (so layouts are unchanged), constants with a count of 0 that are never freed (string literals, values of constructors without fields, and, since branch `regex-parse`, list and tuple literals and constructors (records, variants, `Some`, `Ok`) whose elements are all constants (a small `Int`, a `Float` or `Bool` literal, a string, another constant): one global each, equal ones shared, so a table of 1,700 strings is data instead of 1,700 stores, which took LLVM 3 to 8 s to compile; a push or an update copies them, as for any value held elsewhere), the runtime's `strata_dup` / `strata_release` / `strata_free` / `strata_unique`, and `STRATA_MEMORY` to report allocations at exit; (2, built, branch `gc-drop`) a drop function per type (`drop_fn`; a closure block carries its own, a trait value's table has drop and dup entries; the last field is dropped as a tail call, so a million-long chain doesn't overflow the stack), and counting in the code generator: functions borrow their arguments and return what they own, reads borrow, a stored value is moved (a temporary) or held once more, and every scope (block, branch, statement, loop iteration) drops its temporaries and variables, `return` / `break` / `continue` what they leave; a failed pattern drops what it bound; a `mut` argument always goes through a slot of its own (copy in, copy out); an assigned variable's old value is dropped at the end of the statement. `STRATA_MEMORY=check` keeps freed memory aside and stops on any use of it, and the build tests check every program frees everything (a loop of 28 million allocations: 1.4 GB before, 33 MB after). An operand that only borrows is held until the statement ends when a later operand may assign a variable (`f(x, { x = g(); 1 })`: `operands`). Known gaps: every `dup` / `drop` is a call into the runtime (about 15% slower than not freeing: inline the count updates in the IR); the interpreter takes 27 s to build a 10,000-long chain of variants in a loop (`c = Link(i, c)`), so it looks quadratic there (seen 2026-11-21, not investigated); (3) reuse when unique, replacing `push`'s in-place write past the end (the `used` trick), which can make a cycle through a recursive type (`Node(xs)` pushed into `xs`); (4) later: iterative drop for long chains, borrow inference, stack allocation of values that don't escape, big integers in `Int` slots, atomic or shared counts once async or threads exist. No `copy` / `clone` built-in (user, 2026-11-21): `ys := xs` already is a copy, so `copy(xs)` would only move when the work happens, and would suggest that plain assignment aliases. The runtime part (alloc, free, inc, dec) is small and native; most of the work is in the compiler, so it moves to Strata with it when self-hosting.
- **Self-hosting is a long-term goal**, after the language matures. The compiler would be written in Strata, target LLVM, and use the LLVM libraries.

### Memory in high-performance code: proven properties, not a second memory model (direction agreed with the user 2026-11-21; not built)
The user asked whether Strata needs manual memory management, an unsafe mode or a borrow checker for industrial / high-performance code, where both speed and proofs about memory matter (no leaks, memory used correctly). Agreed: no.
- **What the model already guarantees.** Values never change once built and there are no shared references, so the heap has no cycles and reference counting frees everything: no leaks, by construction (stronger than Rust, where an `Rc` cycle or `mem::forget` leaks in safe code). No use after free and no aliased mutation either, since a mutable reference exists only as a `mut` parameter (see "A `mut` argument is passed by reference"). A borrow checker protects against what shared mutable references make possible, and Strata has none; adding them would also make programs harder to verify (Rust's verifiers, Prusti and Creusot, lean on borrow information to cope), against the language's point.
- **Rejected**: a general unsafe mode or manual `free` (the escape hatch is `extern c`, with contracts at the boundary), a borrow checker with lifetimes, and V's autofree (incomplete, falling back to a GC).
- **What such code needs is predictability**: no hidden allocation, no counting in hot loops, bounded memory, in-place updates that are guaranteed rather than hoped for. Each becomes a property the checker or `verify` proves, in this order:
  1. **Fully in-place functions**, as Koka's `fip` / `fbip` (Lorenzen, Leijen, Swierstra, "FP²: Fully in-Place Functional Programming", ICFP 2023): a marked function is checked to run without allocating, each constructor reusing the memory of one its input gave up. Comes nearly for free once reuse (step 3 of "Memory: reference counting with reuse") is built. Marker and syntax not decided.
  2. **Allocation as a capability** (on top of the capabilities already built): a function without an `Alloc` capability provably allocates nothing, which is the real-time / MISRA rule "no allocation after initialization", enforced by types. To settle: whether `Alloc` is implied by default (and only refused where asked), how it interacts with copy-on-write (a copy is an allocation, so a no-`Alloc` function may only update values it can prove unique), and how faults that allocate their message are counted.
  3. **Arenas**: `with arena a { ... }` allocates in a region freed at once when the block ends, with no counting inside. The only check needed is that nothing allocated in `a` escapes the block, the same second-class rule as `mut` references, so no lifetime annotations. Syntax not decided.
  4. **Bounds checks removed by proof**: an index whose refinement `verify` proves within the length needs no check at run time (part of "skipping the runtime check of a contract `verify` proved").
- **Self-hosting and the runtime.** Reference counting needs almost no runtime (no collector thread, no stack maps, no pauses: alloc, free, increment, decrement); most of `src/llvm/runtime.c` is printing, strings, faults, random numbers, contract tracing, fuzzing and host I/O, which a borrow checker wouldn't remove. To go without the C runtime, `std` gets a few raw-memory primitives (load, store, pointer offset, size of a type), usable only inside `std` (as Rust's `core`), so the allocator and the counting can be written in Strata over `extern c` `malloc` / `free`, or over `mmap` where there's no libc. Not decided: their names, and how "only inside `std`" is enforced.

### Runtime and standard library (decided)
- **A small native core in Rust** (C is possible for the system-call layer; decide when we get there): the GC, the system-call / OS boundary, and bindings to LLVM and the SMT solver.
- **Most of the standard library in Strata itself**: collections, strings, the ORM, HTTP / web views, CLI helpers, and agent tooling. Only the thin OS / runtime layer is native.

### Sums and unions are one thing (decided with the user 2026-11-21; built, branch `unions-are-sums`)
A sum already is a union of the types its variants declare (`ShapeError` is `Empty | TooBig`), and matching, narrowing and coverage are the union machinery; what was left apart (where members are declared, which can have `impl`s) confused more than it helped. So there is one construct, the union:
- **Members declared inline or named**: `type Shape = Circle | Square { side: Float } | Dot` reuses `Circle` and declares `Square` and `Dot`. Today's sum is the case where every member is inline (`type Option[T] = Some(T) | None`). Declaring a member inline is declaring a type (a record, a tuple-shaped type or an atom), unique in its module as variants are now.
- **Only bare members flatten**: `type S = A | B; type S2 = S | C` is `A | B | C`; `type S3 = D(S) | E` is `D | E`, not `A | B | E`: a constructor wrapping something is a new type, and what it holds stays inside it (`x.0` of a `D` is an `S`).
- **A named union names a set of values, as an alias does**, under the alias rules: a `Circle` fits `Shape` without wrapping; the same set written out (`Circle | Square`) is the same type; a named union can have `impl`s, methods and `derive` (as a sum can today). A union that adds nothing is refused like `type P = List[Int]`: one that normalizes to one type (`type U = Int | Positive`), or a second name in the same module for a set already named (`type Figure = Circle | Square` next to `Shape`): "use `Shape`, or make it `distinct type Figure = ...`". Names are unique per module, not per program: `geo.Shape` and `ui.Figure` may name the same set, told apart by their module (user); which `impl` applies is the static type's (`geo.Shape`'s for a value typed `geo.Shape`); an anonymous union written inline has none of its own.
- **`distinct type Figure = Circle | Square`**: a separate nominal type, as `distinct` is today: built explicitly (`Figure(c)`), `f.value` is the `Circle | Square`, doesn't mix with `Shape` or its members, has its own `impl`s, and is written to JSON as its value.
- **`std.typing`**: `Sum` and `Union` become one kind with `members` (`variants` goes); `Choice` is a union whose members are all atoms. JSON's two paths (sums tagged by `"type"`, unions told apart by their JSON) merge: a member is tagged when it is a record, tuple-shaped or atom type, else told apart by its JSON kind, as unions are now.
- **Refined with the user (2026-11-21)**:
  - *A bare name refers to a type when one exists*, and declares a new one only when nothing has that name; with a payload too: `Some(Int) | None` is the prelude's `Some` (given `Int`) and `None`, i.e. `Option[Int]`, not new types. A member named like an existing type (`Circel` next to `Circle`) is a warning after the `edit` ("did you mean `Circle`?"), not an error: two types may have close names.
  - *Inline and separate are two views of the same thing*: `type Shape = Circle | Square { side: Float } | Dot`, or `type Square = { side: Float }`, `type Dot` and `type Shape = Circle | Square | Dot`, mean the same; `edit` takes either. So an atom can be declared on its own (`type Dot`), and a tuple-shaped type too (`type Moved(Int)`). Which one is shown is a setting of the renderer and viewer; by default a member is shown inline under its union when that is the only union using it, else on its own.
  - *The renderer uses names*: a union written out (`fn f(x: B | C)`) is rendered as its name (`x: A`) when the set has one in scope (the module's own first), and named subsets too when one name alone covers them (`B | C | D` with `A = B | C` is `A | D`); a `distinct` type is never used so. The checker agrees: a union equal to a named set in scope is that type (its `impl`s apply).
  - *The prelude is part of every module* (it is in scope unprefixed): `type Answer = Some(Int) | None` names a set the prelude already names (`Option[Int]`), so it is refused as adding nothing ("use `Option[Int]`, or make it `distinct`"). A module imported with a prefix (`std.json`, `geo`) is another module: naming the same set there is fine.
  - *A `distinct` union* is built and read as any `distinct` type: `distinct type Answer = Option[Int]` (or `= Some(Int) | None`), `Answer(Some(3))`, `Answer(None)`, `a.value` the `Option[Int]`.
  - *Later (viewer)*: holding a key shows hints: a type expanded into its members, the parameters' names at a call, and the like.
- **Built** (branch `unions-are-sums`, stacked on `typing-defs`):
  - *Stored form*: a union whose members are all defined elsewhere is an alias of their union; one declaring some is a `TypeBody::Sum` whose other members are `Payload::Type` (binary tag 3). The parser reads `A | B { .. } | C(Int)` and the bar-first form the same; whether a bare name is an existing type is decided when the code is stored (`resolve::union_members`: the module's types, earlier unions' declared members, the root module, the prelude and built-ins, what it imports; a second version of the same definition, as an edit has, doesn't count), so the decision is in the tree. A member with fields named like a prelude type (`Some(Int)`) is that type. One bare name with no bar is an alias (`type Port = Int where ..`); a union of one atom is `type X = | Dot`, an atom on its own `type Dot`. `Tuple` and `Unit` aren't built-in names for this (`(A, B)` and `()` are written so), which leaves `std.typing.Kind` its `Tuple` and `Unit`.
  - *Checking and running*: before checking, a union with members of both kinds becomes a sum of its own members (`Shape$own`) and the union of that with the others (`desugar::mixed_unions`), so the checker and backends see only sums and unions. A named union isn't nominal: a union type is found by its set (`Checker::union_name`, `Module::union_name`, a sum counting as its variants), and the named union's `impl`s and own methods apply to it, in `satisfies`, method calls, static calls (`Shape.decode_at(..)`, passed by name) and the compiled dispatch (before each member's own). Coherence across modules naming the same set isn't checked yet: the first name found (by name order) is used.
  - *Rules*: `Checker::union_adds_nothing` (one type once normalized; the same set as an earlier union or sum of the module, the root module or the prelude; the members a union declares, named apart, are fine); `distinct` on a union that only declares members adds nothing; `resolve::near_misses` warns after an edit (one change in a name of up to five letters, two beyond, or case).
  - *Rendering*: `written_form` names a union written out when its module (or the root module) names the set, and named subsets when they don't overlap, keeping the members' order (`resolve::named_unions`; not `distinct`, not generic). `render --members separate | inline` (`resolve::members_view`).
  - *`std.typing`*: `Kind` has no `Sum`, `Type` no `variants`; a union's `members` are as written, a named union one member, except the members a union declares itself, listed each. A named union can derive (`derivable(Record | Union)`); as a field it needs its own `derive`, as a record does. `std.json`: one path for unions, a record, atom or tuple-shaped member tagged by `"type"`, any other told apart by its JSON; messages for a union of tagged members as before.
  - *Default view (user, 2026-11-21)*: a type with a doc is shown on its own, else inside the one union listing it (`render` folds it unless it has a doc, an `impl` or `derive`, or type parameters); `--members separate` shows every member on its own.
  - *Type parameters are wrapped (user, 2026-11-21)*: a generic union's parameter is inside a member it declares (`Some(T)`) or inside a type (`List[T]`), never a member on its own (`T`), and no two members are alike when a parameter is in them (`List[A] | List[B]`): those couldn't be told apart. No `Either[A, B]`: `A | B` is written where it is used. (A bare parameter name in a union is that parameter, not a new atom.) So a union's set, its members paired by what they are and the arguments read off (`Checker::same_set`, `bind_targs` for unions), names one union: a generic one has `impl`s of its own, `Ints = List[Int] | Problem` next to `Many[T] = List[T] | Problem` adds nothing, and `List[Int] | Problem` renders as `Many[Int]` (whole unions only; a parameter only inside a declared member, `Value(T)`, can't be read off a written union). Also fixed: a bare `List =>` arm on a union member compiled to no match.
  - *Two modules naming one set (user, 2026-11-21)*: allowed, but not both implementing a trait (or having a method of one name) for it: `Checker::union_conflicts`, on the later one.
  - *Viewer*: `strata ui` has the setting (*union members: inline (switch)*, kept in the browser): each card carries its code in the other view, and a type the inline view folds has no card there.
### Unions, variants as types, and match patterns (decided 2026-11-19, built)
- **`Option` and `Result` stay as they are**, and so do `!` / `?` propagation. No `T?` / `T ! E` syntax.
- **Unions are sets of values**: `A | B` holds any value of `A` or of `B`. Unions normalize: `Int | Positive` is `Int`; `(Int where p) | (Int where q)` is `Int where p || q`; different bases stay a union. `A` fits `A | B`; `A | B` fits `C` when both do. Type parameters can be members (`T | E` with bounds); if they end up the same type, it collapses, harmlessly.
- **Variants are types.** `type ShapeError = | NonEmptyErr | TooBig { max: Int }` declares the types `NonEmptyErr` and `TooBig`, and `ShapeError` is `NonEmptyErr | TooBig`. So `Result[Circle, NonEmptyErr]` or a parameter of type `TooBig` are allowed.
- **Names are unique in their module** (changed with the user 2026-11-21; was: across the project): no variant may share its name with a type, a trait or another variant of its module. Another module's of the same name is told apart by its module (`geo.Circle`).
- **No automatic wrapping**: always write `Ok(…)`, `Err(…)`, `Some(…)` (`Result[Int, Int]` would be ambiguous otherwise).
- **Patterns are sets of values**: a type name (`Positive =>`, `Square =>`), a variant as today, a literal, a condition (`where 3 <= it && it <= 5 =>`, base type = the scrutinee's), `_`. An arm takes what no earlier arm took. Exhaustive = the scrutinee's (normalized) type is covered by the arms; an arm already covered by earlier ones is an error (unreachable).
- **Narrowing, no new name**: `match x { Positive => { x … } }` narrows `x` itself in the arm. For an expression: `match f(y) as x { … }`. Field paths (`o.status`) narrow too. Narrowing of a `let mut` lasts until it is assigned.
- **Coverage**: integer (and `len(it)`) comparisons with constants, combined with `&&` / `||`, are decided exactly as interval sets. Anything else waits for the SMT solver; until then such an arm needs a later `_`. This also lets a match on `NonEmpty` skip the `[]` arm.
- **Built** (branch `unions`): `Ty::Union` normalized by `Checker::union_of`; subsumption in `fits` (used by `expect`: union members, variants into their sum; type arguments stay invariant); `infer_at` passes the expected type through `if` / `match` / blocks / lists / constructors; `pattern` returns the narrowed type and a value set `P`; exhaustiveness and unreachable arms use atoms (`atoms`, `covers`, `missing`, `useful`) with integer intervals in `types::ints`. Interpreter: `value_in` / `shape_fits` for type patterns and `is`, unions in `check_type` and JSON input, impls on variants. Since then (decided with the user): or-patterns; unions inferred for alternatives when no expected type decides; type arguments fit member-wise (values are never shared) except for arguments to `mut` parameters, which must be exact; `!` passes errors into wider error types; length (`len(it)`) and `Float` conditions are decided (`types::reals` tests one point per region); the matched value's written refinement counts (`Coverage.excluded`), taken from variables' declared types (mutable ones too: the interpreter checks every assignment and write-back against the declared type, `Frame::declared`), their fields and function results (`Checker::written`). Narrowing in an arm is skipped for a `mut` variable the arm assigns (`Checker::assigns_to`), so loops stay sound. A `mut` argument's declared refinement must contain the parameter's (`refinement_within`); assignments of literals are checked at compile time (`literal_outside`). Not yet: list lengths other than empty / not empty; conditions beyond constant comparisons (the SMT branch has the pieces, see below).

### Match coverage with the SMT solver (assessed 2026-11-19, not started)
The `smt-verification` worktree (uncommitted, on old main) already has: symbolic values for parameters with their refinements as facts (`havoc`), `Vc::pattern` turning a pattern into an SMT condition on the matched value, per-arm path conditions in `Expr::Match`, obligations solved with Z3. To decide coverage of undecidable conditions it still needs: (1) an obligation per `match` that some arm holds (the `or` of the arm conditions, under the facts), and one per arm that it can hold (unreachable when proven impossible); (2) the new pattern forms in `Vc::pattern`: type names, `where`, or-patterns, and `Match`'s `as` name (it predates the `unions` branch, so merge first); (3) a policy between `check` and `verify`: `check` would report such a `match` as "needs proof" instead of an error, and `verify` proves it, reports a counterexample, or leaves it runtime-checked (a `no match arm` fault). Floats are not modelled there; the checker's own `reals` covers them.

### Mutation at the call site, references, and unproven checks (decided 2026-11-19)
- **`mut` at the call site (done)**: an argument to a `mut` parameter is written `f(mut x)`; missing it, or writing it for a parameter that is not `mut` (or a builtin, or a closure), is an error. A `mut self` method's call is marked too, `mut queue.claim(2)` (since 2026-11-20; it was unmarked, as in Swift). `Expr::Mut`, checked in `check_mut_args`.
- **References**: immutable values can always be shared (no copying in the compiled form); a mutable reference only exists as a `mut` parameter. References stay second-class (never stored or returned), like Swift `inout` / Hylo, since first-class ones would need a borrow checker; a possible local form is `mut l := mut order.lines[0]`.
- **A `mut` argument is passed by reference, and may not overlap another argument** (decided with the user 2026-11-21; not built: today every `mut` argument goes through a slot of its own, copied in and out). Without threads or async, a `mut` parameter is the only way to the caller's variable while the call runs, and it can't outlive the call, so passing a pointer to the variable is safe with no borrow checker (Swift's "law of exclusivity"). Copy-in/copy-out stays the meaning, which is what the checker and the prover reason with; with a single reference the two can't be told apart. That holds only if the `mut` argument doesn't overlap any other argument of the same call, since read-only arguments are borrowed, not copied: `f(mut x, x)` would let the callee see its read-only parameter change, as would `swap(mut a, mut a)` and a part with its whole (`f(mut xs, xs[0])`, `g(mut r.lo, r)`). **Overlap is refused by the checker** (user's choice; rejected: allowing it and holding the overlapping argument once more, so the callee's write copies first), with a `help:` naming the copy to write (`y := x; f(mut x, y)`). Overlap means the same variable, or one path a prefix of another (`r` and `r.lo`; `xs[i]` and `xs[j]` count as overlapping unless the indices are different constants, or later proven different by `verify`). The same rule covers the open nested-block case: an argument block that assigns a variable used by another argument (`f(x, { x = g(); 1 })`) is overlap too, and can be refused the same way instead of held (`operands`). A field (`shift(mut r.lo)`) or an element is passed as a pointer into the record or list once it is made unique (copied first if its count is above 1). The reference makes the *variable* shared with the callee; the *value* in it is still updated in place only when its count is 1, and copied first otherwise (`ys := xs; f(mut xs)`): in-place mutation needs both this and reuse (step 3 of "Memory: reference counting with reuse"). An `extern c` `mut` parameter is already an out-pointer, so FFI is unchanged. Threads or async, when they come, would need copy-in/copy-out again (or exclusivity across tasks) where a `mut` argument crosses a suspension point.
- **Unproven checks are reported by default** (with the runtime check kept); a project policy can require `proven` for chosen modules. For the SMT work: an assignment to a refined variable is one more obligation (e.g. `x = f(x) - 3` with `x: Positive` needs `f`'s contract to imply it).

### Lambda syntax (done)
- Replace the Rust-style `|x| body` with a **bare arrow**: `x -> body` and `(a, b) -> body`, with optional parameter types such as `(s: String) -> …`. For a longer body, use a block: `x -> { ... }`.
- `->` is never an operator inside expressions, so there is no ambiguity; `=>` stays reserved for `match` arms.
- **No shorthand lambdas** (no `$`, `_` or implicit parameter) and **no separate anonymous-`fn` form**.
- **Refinements keep `it`** for "the value" (`where it > 0`).
- When implementing, update the parser, printer, examples, README and tests; `render` must still round-trip.

### Bindings and assignment (decided with the user 2026-11-21, built)
- `:=` declares and infers the type: `n := 0`, `(w, k) := pair()`, `mut x := 0`. With a type, the colon is already written, so the sign is `=`: `let x: Int = 5`, `mut x: Int = 0`. `let` only appears with a type; `let x = e` is a parse error pointing at `x := e`.
- `=` only reassigns a variable or field. `+=`, `-=`, `*=`, `/=`, `%=` parse to `x = x op e` (no new node), and the printer writes `x = x op e` back as `x op= e`.
- A function returning `()` leaves out `-> ()` (it was already optional when parsing; the printer now omits it). Function *types* keep it: `(A) -> ()`.
- A call's `(` must be written against the name: `f(x)` is a call, `f (x)` is `f` followed by `(x)`. So without `let`, `f() (a, b) := …` on one line is still a call then a binding (the printer puts them on separate lines anyway). Decided with the user 2026-11-21; the rendering is meant to be customizable per reader later (e.g. `let` everywhere, sums expanded or compressed), since the tree is the language.

### A type's own methods, and shared method names (decided 2026-11-20, built)
- **`impl Item { ... }`** gives a type methods of its own, with no trait. A method with `self` is called on a value; one without `self` is called on the type (`Item.new(...)`), and is resolved into the function `Item.new` right after module resolution.
- **Traits as parameter types** are shorthand for a type parameter with that bound (`mut queue: Queue[P, E]` = `[Q: Queue[P, E]](mut queue: Q)`). Name the parameter only to tie types together.
- **Method names may be shared between traits**, each implementation with its own body (revised 2026-11-20 by the user). A call through a trait (`d: Describe`, `T: Describe`) runs that trait's implementation. On a known type, the type's own method wins, else the one trait of the type that declares the name. Anything else is a compile error: a type with two such traits and no own method; a receiver known only as `A | B` or `T: A + B` (even if the actual type has its own method: that doesn't say which trait's meaning the call wants).
- **Elaboration** (`types::check_and_elaborate`, done with the check): the checker records each such decision by call node, and the program that runs (interpreter, verify, SMT, termination) has it written in: `x.Describe::describe()` for a call through a trait, a direct call of the function `Item.describe` for a type's own method. A type's own methods are registered as functions (`Item.new`, `Item.describe`).
- **Trait methods without `self`** (built 2026-11-20): called on a named type (`Money.empty()`, `T.empty()`, `Self.empty()` in default methods and laws), elaborated to `Trait::empty(type, ..)`. The signature must mention `Self`. Generic functions whose type parameters are bounded by such a trait get hidden parameters `type:T` (of type `$Type[T]`, the type's name at runtime); each call passes the inferred type or forwards the caller's. The fuzzer generates them from its chosen instance; laws and trait methods know `Self` from the interpreter's `self_types` stack.

## Git, diffs and review (decided)

- **Editing the standard library** (fixed, branch `std-edit`): `std/` is a package whose modules are `std.*`. `strata edit io` inside it names the module `std.io` (it named it `io`) and logs nothing (it started a `strata.log`; std's history is git's); `strata --file std edit` edits it as that package, checked like any package edit (it stored a definition that `check` then refused). `--file` on another folder or a file still stores what parses, checked afterwards.
- **Git stays the base** (built). A package's module files and its `strata.log` are committed; `.strata/` is only the local verification cache. `edit` / `add` / `rename` rewrite the files and append an entry (id, message, changes with each definition's text before and after, `rename`). The log merges by union. `strata init` writes `strata.toml` and an empty `strata.log`, so the log is tracked from the start (`git commit -am` would otherwise leave it behind).
- **Structural diff** between two git revisions: load both snapshots, pair definitions, compare trees. The log entries present at HEAD but not at the base are the atomic steps in between (for stepping through, renames, messages). A PR = merge-base..HEAD.
- **Change kinds**: added/removed; renamed/moved (one line, "N references updated", folded); signature change marked in place, with contract stronger/weaker; body change shown in place with unchanged statements folded, **falling back to a line diff of the canonical text when most of the body changed**; type field/variant changes (with "N matches must handle it"); trait changes; doc comments as a word diff; verification before → after. Ordered types → interfaces → implementations → tests.
- **`strata rename old new`**: done (`resolve::rename`). It reuses the resolver's scoping, so locals shadow and `use` imports work as the checker sees them, and it refuses a rename that would change what any other name refers to. Functions, types, traits, **variants, trait methods** (the trait, every impl's method and the calls) and **fields** (`strata rename Line.qty quantity`: declaration, accesses, record literals, updates, patterns). Variants and methods go through the resolver like definitions (`resolve::member` / `owner` / `defined`; an impl's methods are named in the trait's module, which rename mode used to get wrong). Field accesses are told apart by type, not by name: when another record (or the prelude, or `.value` of distinct types) has a field of that name, `resolve::rename_field` tags each access in a copy (`qty·d3k0`), and the checker (`types::field_owners`, a thread-local probe in `infer` for tagged `Expr::Field`) records the record type(s) of each receiver; only the owner's accesses are renamed, and an access on a union of the owner and another record is refused. Literals, updates and patterns are matched by their constructor. It rewrites the serialized tree in one fixed-order walk (tags and renames line up), and the command type-checks the result.
- **`strata move <name> <module>`** (`resolve::move_def`): a function, type or trait (with its variants or methods) changes module, keeping its short name. The resolver's write-back has a move mode (`run_with(.., moves)`): qualified references get the new module (`orders.charge(o)` → `billing.charge(o)`), short ones stay short and their module gets `use billing.{charge}`, `use` items that named it go (emptied lists are removed), and the moved definition's own short references get imports where it goes. Refused when something private would be out of reach (a private dependency, or a private definition used from its old module), or when any name would resolve differently (the same check as rename). Logged as `"renames": [{.., "kind": "move"}]`; diffs say "moved from `orders`"; `sync` follows moves (`resolve::follow_move`, compared by name since imports change the definitions' positions). Docs and comments aren't rewritten (the command lists the ones that mention the old name). Several renames are one step (`strata rename A.tag label B.tag label`, `resolve::rename_all`): fields are renamed together by `rename_fields` (an access on a union is renamed when every record it reads from is renamed to the same name), then the rest one after the other; one type-check, one log entry. The log entry has `"renames": [{"from", "to", "kind"}], "references"` (`store::renames_of` reads it; `strata move` writes `kind: "move"`). It works on the package's files and logs the rename.
- **Merge driver**: `strata merge-file %O %A %B %P` per definition, then type-check. GitHub won't run it, so: `strata sync main` merges main into the branch locally, branch protection requires branches to be up to date, and a required CI check runs `strata check` + canonical-format check on GitHub's merge ref.
- **jj**: compatible (runs on git) but not a dependency.
- The tour is later. The user wants to settle the look first: offer a static mockup of the *Changes* view.

Order: ~~`strata rename`~~ → ~~diff core~~ → ~~`strata diff`~~ → ~~*Changes* view~~ → ~~merge driver~~.

**Built:** `src/diff.rs` (pairing through renames, words per change, line diff with in-place marks and folds that keep enclosing headers, line-diff fallback at ≥60% changed, contract notes, rename references, verification before/after), `src/history.rs` (a package's log replayed with `Codebase::states`, backwards from the files so hand-written code before the first entry is the start, one step per patch; or git: `BASE..HEAD` commits plus the working tree, each commit split into the log entries it added, replayed forwards with `store::apply`, plus a step "edits outside strata" for what the log doesn't explain), `strata diff [--from N] [--to N] [--step K] [--json]` / `strata --file DIR diff [BASE]`, `/api/changes` and the viewer's *Changes* tab. The mockup is still in `design/changes-mockup.html`.
**Merge driver (built):** `src/merge.rs` and `strata merge-file` / `setup-git` / `sync` / `ci`, plus packages (`src/package.rs`, see below). `strata ci` finds every package (folder with a `strata.toml`) and script (a `.strata` file outside every package) with `git ls-files`. It checks each one and validates `exports`, and it requires canonical format: `printer::program` of each file parsed alone. The examples were rewritten into canonical form for it (`strata ci --fix`).
How the driver works: definitions are paired by qualified name, and one-sided changes win. Two-sided changes go through `git merge-file` on the definition's canonical text, and the result is kept only if it parses back into that one definition; otherwise there are diff3 markers around it. Renames are detected without the log: a definition gone, and an added one with the same kind and module whose text is ≥60% similar to the base's after `resolve::rename`. The rename is applied to the base and to the other side. After the merge, the file is type-checked inside its package, with the package's other files read from disk (ours, because merge-ort runs drivers before it writes the worktree). Only errors that neither side has alone fail the merge. The whole-program check after all files are merged is `sync`'s `ci` run.
`sync` passes the driver with `-c merge.strata.driver=...` and a temporary `core.attributesFile`, so it works without `setup-git`. It merges `origin/BRANCH` when there is a remote, commits only if `ci` passes, and otherwise leaves the merge staged.
CI: `.github/workflows/strata.yml` (`strata ci` on the PR merge ref, plus `cargo test`). The repository is public, and `main` is protected: `strata ci` and `cargo test` are required checks and branches must be up to date (`strict`). Admins are not enforced, so the owner can still push to `main` directly; everyone else goes through a PR.
**Renames across a merge (built):** `sync` runs the driver with `STRATA_MERGE_BASE` / `STRATA_MERGE_THEIRS`; then the driver skips its per-file type check (while git merges, the other files are still ours). After git is done, `merge::follow_renames` reads the renames both sides logged since the merge base and applies each to the merged package (`resolve::follow`): the renamed definition is put back under its old name (and `use` items naming the new name name the old one), every reference to the old name is renamed, and each definition must resolve as before (what the rename touched, with old → new) or exactly as merged (everything else), so a local that would capture the new name makes it refuse. The fix is a logged change (`"follows"`), staged into the merge commit; then `ci` checks everything.
Not yet: following renames under a plain `git merge` (only `sync` does it); a refused follow leaves every reference to the old name for `ci` to report; moving several definitions at once (move a private helper with its user: make it `pub`, or move it first); a rename+edit is recognised only when it is ≥60% similar *and* callers switched to the new name (tiny functions look alike, so similarity alone gave false renames).

Diff: a renamed variant, method or field shows on its type or trait as "variant `Circle` renamed to `Round`" ("only a name changed · N references updated"), and code that only follows it is folded; other changes to the owner are computed against the old owner with the rename applied. `sync` follows member renames too (`resolve::set_member_name` puts the member back under its old name first). Diff, not yet: "N matches must handle the new variant"; moves between modules. Closure hashes (verification cache keys) now ignore docs and comments, and interface hashes ignore docs.

## Packages, modules and dependencies (decided)

- **A package is a folder with a `strata.toml`**: `name` (required; `strata init` writes the folder's name, and it stays when the folder moves, e.g. in a worktree), `exports` (optional, modules or single definitions, the equivalent of `pub use`; default every `pub`), `[deps]`, `[verify]` (verifier policy, e.g. modules that must be `proven`). There is **no `lib.strata`**. **`main.strata`** is the root module and the default entry point. A `.strata` file outside every package is a script. A nested folder with its own `strata.toml` is a separate package.
  **Built:** `name`, `exports` (checked by `ci`), discovery, nested packages, `init`. `[deps]` and `[verify]` are parsed but unused.
- **A file is a module; `module m { }` blocks are gone** (built). The parser has no `module` form, `printer::program` is one file's text, and `render` prints one module (`render MODULE`, `main` for the root) or `--split DIR`; on several modules without either it says so. A view across modules labels each group with a `// ── module m` comment line. Where a definition sits inside a file doesn't matter, and the standard rendering is one file per module. Folders organise modules freely; there are no submodules with special access. Still to confirm: whether a module's name is its path inside the package (`shop/orders.strata` → `shop.orders`, as today; recommended, so names don't collide and moving a file is a module rename) or the file name alone.
- **Dependencies from any git URL** (Go-like, not only GitHub), declared in `[deps]` (`json = "https://…"`, or `{ path = "../x" }` in the same repo), used as `use json.parse`. Fetched into a global cache and run directly, with no install step. Proposed, not yet confirmed: a generated `strata.lock` pinning each dep to a commit + content hash, and `strata update`. ## Known gaps

- The interpreter (`--interpret`) doesn't know an impl's type parameters in a `mut self` method reached through a generic function (`T.zero()` in `impl[T: Zero] Iterator[T] for Padded[T]`, called from `collect[T, I: Iterator[T]]`: "the type `T` is not known here"). Compiled code handles it; per the rule under "Retiring the interpreter", the interpreter isn't fixed. (Methods on a generic impl's type parameters, `T.empty()` / `T.decode(j)`, work since #126.)
- FFI is C only, and only from compiled code (`extern c`, see "Foreign functions: `extern LANG`"): `main` can't yet ask for a native module's capability, and there is no std SQLite module yet.
- `strata verify --force` on the tasks example takes a few seconds (proven functions are not fuzzed); the slowest part is still generating `MemQueue` values that satisfy its invariants.
- `d[k]` on dicts isn't accepted (`at` has no `Dict` version).
- `--json` is missing on `view`, `render`, `interface`, `status`, `done`, `test`, `run` and `ci`.

Decided against (not gaps):
- **Explicit type arguments at a call** (`f[Money]()`; decided by the user, 2026-11-21): type arguments are inferred from the arguments and the expected type only.
- **Error conversion** (decided by the user, 2026-11-21): `!` only passes an error on when it fits the function's error type (the same type, a variant into its sum, a member into a union). No conversion functions, implicit or declared: errors stay explicit as types.

## Known limitations

- **Proofs cover integers, strings, records, sums, unions and list lengths.** Loops forget what they change (no invariants yet), list elements are tracked only when the whole list is known to be valid, floats, dicts and sets are not modelled, and trait laws are fuzzed only.
- Length conditions on a list are only decided as "empty" or "not empty" (`where len(it) == 1` with `where len(it) >= 2` needs a `[]` or `_` arm).
- **Verification is slow and sequential**: `verify` on `examples/tasks` takes about 16 s with an empty cache (0.1 s cached). A solver process per query, one query at a time, one solver per run (`STRATA_SOLVER`), results keyed by `closure_hash` (see "Verification fast enough to run with every check" above).
- **Only verdicts are cached**: nothing else is cached by hash in `.strata/` (no check results), and modules are read one at a time.
