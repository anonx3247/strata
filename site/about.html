How I built the Strata prototype with Claude Code

26 November 2026

On 19 November 2026 I wrote the first prompt. Five and a half days later, on 24 November, I released v0.1: a self-hosting compiler written in Strata, built and installed with no Rust at all. The language was fully working at v0.1 and I was very happy with it. The two days after that were fast iterations on top of it, up to v0.3.4. Claude Code wrote the code. I did the design, set the direction and checked the behaviour, across about 80 sessions, often five to ten at once. I never looked at the code: I worked only in the chat.

I went into this expecting a prototype: a way to find out what the language should be, and whether agents could build it. I didn't know yet how much of it I would keep. I've now decided to rebuild it from scratch, and this time to look at it in much more detail.

The approach: working at the level of contracts

The most important part of this project was contract-based development. When I work with agents, I try to stay at the level of how things compose: the traits, the contracts, the relationships between them, the flows, the invariants, what must be true or false in each situation. I think about a program as a state machine, and leave to the agents the details of how it gets from one state to the next. I only go down into the implementation when I need to, for optimization or for something that needs more detail.

This is what Strata is meant to make possible. Code is stored as a tree, so it can be shown at whatever level of detail you need: interfaces and contracts by default, bodies only on request. Contracts and refinement types are checked by a verifier, so you can trust an implementation you haven't read. That is progressive complexity: you see only the complexity you need at a given level.

For the prototype I went further than that and stayed in the chat entirely, for three reasons:

  • I wanted to move fast.
  • Much of the code was likely to be replaced. The plan was a first compiler in Rust, then a rewrite in Strata, so what I cared about was that the language behaved correctly and the rewrite had a correct reference.
  • I wanted to test the premise on Strata itself: improve the tools until agents can use them on a large project, this one included.

How I worked

Design by conversation

Claude proposed options, explained the background when I needed it (how SMT solvers work, garbage-collection strategies, how Go bootstraps), and I decided. A few examples:

  • Claude's first draft had algebraic effects. I asked what an effect gave me that passing a backend object didn't, and we replaced effects with capabilities: ordinary traits passed as parameters.
  • Code is stored as a binary syntax tree, one file per module, and text exists only when it is rendered. I wanted agents to go through the checked tools instead of editing text files.
  • Claude kept adding ordering to dicts. I refused it each time: a dict is a hash map with no order.

Setting the order of the work

The large decisions were mine: replace the interpreter with a JIT, write the regex engine in Strata because Rust crates wouldn't exist after bootstrapping, start the Strata compiler while the Rust one was still growing, then delete Rust and ship a release that needs nothing else installed.

Proofs over tests

I kept pushing agents to state contracts and have verify prove them, and to write tests only for what touches the outside world. I also wanted contracts at a higher level than bounds on inputs, describing how state changes, which led to old, named outputs and trait-level invariants. When the solver hit its limits, I brought in the idea of agents writing proofs themselves, which became lemma, assert … by and calc.

Running the sessions

One worktree and PR per change. I told each session what the others had merged and passed context between them with handoffs. When CI became slower than the work, I dropped it for a rule: test and verify only what changed.

Catching mistakes

Most of my corrections came from asking one more question about what Claude reported. When it said factorial was proven to terminate, I asked whether Strata's verifier had proven it or Claude had just reasoned it out. When a verify used 3 GB for one function, I said that couldn't be normal, and it wasn't.

Testing as a user

I built a small calculator by hand, and had agents build an order book and a SQL engine in Rust and in each Strata release, graded by hidden fuzz suites.

What Claude did

Claude wrote essentially everything: the Rust prototype, its replacement in Strata, the C runtime, the standard library, the editor support, the site and the docs. It also profiled and fixed its own slow paths, for example verifying std going from over 20 minutes to 24 seconds, and ran fleets of subagents for the release.

It also made mistakes I had to work around. With several sessions merging into main and no CI, bad merges reverted other PRs four times. For a week, verify could count a check as proven from a script Z3 had partly rejected. It sometimes stated causes it hadn't checked, or did work I hadn't asked for.

What came out of it

To measure it, I gave agents (Claude Opus) two tasks from the same written spec: an order book (a matching engine for buy and sell orders) and a small SQL engine. Each task was built once in Rust and once in each Strata release. Every version was graded by hidden fuzz tests against a reference (a Python model for the order book, SQLite for SQL) and read by a review agent.

By 0.3.4, the Strata versions were as correct as the Rust ones, and slightly better: no Strata version had a confirmed bug, while the Rust SQL engine had one (it accepted an ON clause with no JOIN). The Strata agents proved every function they wrote. A Strata agent building the SQL engine from contracts alone, with zero tests, passed the same hidden fuzz tests in the same time as one writing tests.

Strata is still slower to work in. The Strata order book took 1.8 times as long to build as the Rust one, down from about 3 times with v0.2. Early releases lost most agent time to compiler crashes, not to the language. Verification is still slow on large packages.

Working only in the chat had a cost. I could see behaviour and decisions, but not the system's traits, contracts and how they fit together, which is the level I want to work at. The prototype grew to about 40 commands and 25 language features in a week, with leftovers from every direction I tried, and no view of it that I could follow.

Why I'm starting again

The prototype convinced me that Strata is a long-term project, and that I want to do it properly.

The main reason to start again is to understand all of it. I have a good understanding of the system at a high level: the language, the design decisions, how the pieces fit together. My understanding of the details is shallow: how the parser works and what could be optimized there, how the verifier encodes a program, and many other parts. To work on Strata for the long term I need that depth. Getting it means going slower, doing things properly and reading code, which I didn't do here because I was going for speed.

This repository becomes strata-lab, where ideas are tried and measured first. The new Strata is written in Strata, in small layers: a minimal compiler, then verification as early as possible, then self-hosting. The plan is a draft in REBUILD.md.

The way I work changes. In the prototype I stayed in the chat and saw only behaviour and decisions. In the rebuild I look at every layer in much more detail as it is built: the traits, the contracts, the relationships between them, the flows and the invariants, and the code itself, through Strata's own tools. Contract-based development is still the goal, with agents writing the code and proofs checking it, but now I follow and understand the system as it grows, and go into the implementation wherever I need to.
