How I built the Strata prototype with Claude Code

26 November 2026

On 19 November 2026 I wrote the first prompt. Five and a half days later, on 24 November, I released v0.1: a self-hosting compiler written in Strata, built and installed with no Rust at all. The language was fully working at v0.1 and I was very happy with it. The two days after that were fast iterations on top of it, up to v0.3.4. Claude Code wrote the code. I did the design, set the direction and checked the behaviour, across about 80 sessions, often five to ten at once. I never looked at the code: I worked only in the chat.

I went into this expecting a prototype: a way to find out what the language should be, and whether agents could build it. I didn't know yet how much of it I would keep. I've now decided to rebuild it from scratch, and this time to look at it in much more detail.

The approach: working at the level of contracts

The most important part of this project was contract-based development. When I work with agents, I try to stay at the level of how things compose: the traits, the contracts, the relationships between them, the flows, the invariants, what I want to make sure is true or false in different situations. I think about my programs as state machines, and I let the agents worry about the nitty-gritty of how you get from one state to the other. I only go down into the implementation when I really need it, for optimization or for things that need more detail.

This is a lot of what Strata is supposed to achieve. Code is stored as a tree, so it can be shown at whatever level of detail you need: interfaces and contracts by default, bodies only when you ask. Contracts and refinement types are checked by a verifier, so you can trust an implementation you haven't read. That's progressive complexity: you only see the complexity you need at the level you're working at.

For the prototype I went further than that and stayed in the chat entirely, for three reasons:

  • I wanted to move fast.
  • A lot of the code was likely to be replaced. The plan was a first compiler in Rust, then a rewrite in Strata, so what I cared about was that the language behaved correctly and the rewrite had a correct reference.
  • I wanted to test the premise on Strata itself: improve the tools until agents can use them on a large project, this one included.

Test-driven and proof-driven development

Since I wasn't looking at the code, what was important to me was the functionality: that it does what it's supposed to do. With test-driven development you'd write tests for that. Here I wanted proof-driven development: state what must be true, and have the built-in proof system prove it for every input, with the built-in fuzzer covering what it can't prove. Then you don't need all sorts of tests. As I put it to one of the agents:

Ideally we don't actually use tests and we just have verifications and constraints within the Strata code. Tests should only be there for things that depend on the outside or cannot be proven, which should be a very small number of things.

In practice it looks like this. A refinement type and two small functions:

/// A decimal digit.
type Digit = Int
  where 0 <= it && it <= 9

fn next_digit(d: Digit) -> Digit {
  d + 1
}

fn isqrt(n: Natural) -> Natural
  ensures it * it <= n {
  mut r: Natural = 0
  while (r + 1) * (r + 1) <= n {
    r += 1
  }
  r
}

There are no tests for either, and strata verify reports:

✓ isqrt                    proven (6 checks)
✗ next_digit               Refinement violation (found by the solver)
    input:   9
    result of `next_digit`: 10 does not satisfy `Digit` (where 0 <= it && it <= 9) (stack: next_digit)

isqrt is proven for every natural number, loop included. next_digit has a bug, and the solver found the one input that shows it.

The more of the language we had, and the faster it ran, the more the agents could work correctly without me looking at the code, and the fewer bugs came up along the way. That's what makes me comfortable starting on the next steps.

How I worked

Design by conversation

Claude proposed options and explained the background when I needed it (how SMT solvers work, garbage-collection strategies, how Go bootstraps its compiler), and I made the decisions. A lot of the language came out of exchanges like these, lightly trimmed.

On the first morning, Claude's draft had algebraic effects:

Me: Is there really a difficulty in just passing things through? Couldn't we just pass a backend object and have different implementations of said backend? I'm guessing here it's just about not having to mention it everywhere, but that feels more like a syntactical detail than something really fundamental about effects.

Claude: You're not missing anything. For a database or any backend, passing an object is equivalent, and an effect adds nothing fundamental. … Capabilities are ordinary values of trait types, passed explicitly.

Effects went, and capabilities became ordinary traits passed as parameters. Then mutability:

Me: I never said that all values needed to be immutable. I think it can be completely fine to have procedural code with steps and state changes. Immutable by default, and you set mutable variables when you need them. It's easier for both agents and humans to read, because they're more used to procedural code.

Claude: Understood. Immutability was my over-reach. The direction is now immutable by default, mutable when you say so. … To keep the guarantees, mutation stays visible.

Unions, the same evening:

Me: What exactly is the issue with Int | Positive? It's not ambiguous. If Positive is Int with more restrictions, you take the one that's the least restrictive. And if it's a union of two refinements, it becomes an or of the clauses.

Claude: You're right. I was treating unions as tagged. … Strata's refinements are already sets of values, so a union should be the union of those sets. Int | Positive is just Int.

Which method runs when a type has its own method and a trait's:

Me: If we're in a context where all we know is that the object is a Describe, it should use the Describe method. The only place where there's ambiguity is when you know the type of the object. Otherwise its own method should never take precedence.

Claude: You're right, and PR #13 gets this wrong. I shouldn't merge it as it stands.

Test doubles:

Me: I see that we've been making fake implementations of a bunch of traits for tests. Wasn't the point of mock to not have to make these, because they get created automatically?

That one led to mock becoming the way to write test doubles, with no hand-written fakes. And dictionaries, which Claude kept giving an order:

Me: It's a dict. People shouldn't think that a dict is sorted or has a particular order. Nothing should assume that a dict has a constant order. It should be a simple hash map.

Other decisions came the same way: strings aren't iterable (you ask for bytes(), code_points() or graphemes()), errors are values and never faults, sized integers are real machine types that wrap, spawn/await with channels, old(x) in contracts, and code stored as a binary syntax tree so agents go through the checked tools instead of editing text.

Setting the order of the work

The large decisions were mine: replace the interpreter with a JIT, write the regex engine in Strata because Rust crates wouldn't exist after bootstrapping, start the Strata compiler while the Rust one was still growing, then delete Rust and ship a release that needs nothing else installed.

Running the sessions

One worktree and PR per change. I told each session what the others had merged and passed context between them with handoffs. When CI became slower than the work, I dropped it for a rule: test and verify only what changed.

Catching mistakes

Most of my corrections came from asking one more question about what Claude reported. When it said factorial was proven to terminate, I asked whether Strata's verifier had proven it or Claude had just reasoned it out. When a verify used 3 GB for one function: "Don't you find it a bit bizarre? There's probably an issue with the verify command." There was.

Testing as a user

I built a small calculator by hand, and had agents build the same programs in Rust and in each Strata release to compare them (below).

What Claude did

Claude wrote essentially everything: the Rust prototype, its replacement in Strata, the C runtime, the standard library, the editor support, the site and the docs. It also profiled and fixed its own slow paths, for example verifying std going from over 20 minutes to 24 seconds, and ran fleets of subagents for the release.

It also made mistakes I had to work around. With several sessions merging into main and no CI, bad merges reverted other PRs four times. For a week, verify could count a check as proven from a script Z3 had partly rejected. It sometimes stated causes it hadn't checked, or did work I hadn't asked for.

What came out of it

To measure it, I gave agents (Claude Opus) two tasks from the same written spec: an order book (a matching engine for buy and sell orders) and a small SQL engine. Each task was built once in Rust and once in each Strata release. Every version was graded by hidden fuzz tests against a reference (a Python model for the order book, SQLite for SQL) and read by a review agent.

By 0.3.4, the Strata versions were as correct as the Rust ones, and slightly better: no Strata version had a confirmed bug, while the Rust SQL engine had one (it accepted an ON clause with no JOIN). The Strata agents proved every function they wrote. A Strata agent building the SQL engine from contracts alone, with zero tests, passed the same hidden fuzz tests in the same time as one writing tests.

Strata is still slower to work in. The Strata order book took 1.8 times as long to build as the Rust one, down from about 3 times with v0.2. Early releases lost most agent time to compiler crashes, not to the language. Verification is still slow on large packages.

Working only in the chat had a cost. I could see behaviour and decisions, but not the system's traits, contracts and how they fit together, which is the level I want to work at. The prototype grew to about 40 commands and 25 language features in a week, with leftovers from every direction I tried, and no view of it that I could follow.

Why I'm starting again

The prototype convinced me that Strata is a long-term project, and that I want to do it properly.

The main reason to start again is to understand all of it. I have a very good understanding of a lot of things at a high level. But the details, how the parser works and the optimizations I could do there, or the verifier, or a bunch of other parts, I have limited depth in. To work on it long term I want more depth, and that means going slower, doing things properly and actually looking at code, which I wasn't doing here because I was trying to go fast.

That doesn't mean reading everything. I want detail in some sections and not in others:

  • I want to know the main contracts and how the parser is built up, but the details of how desugaring is done aren't particularly interesting to me.
  • I want the core built-ins, the standard library and the collections implemented the way I want them, or at least with the shapes I want. How the regex engine is built, I don't mind: I don't know much about Pike VMs, and as long as it works, it works.
  • When the web side comes, I want the Elm architecture done well. How comptime and derive were done isn't something I need to see.

I care about implementation details when I want to optimize something. The rest of the time I want to know each section well enough, especially its contracts, to navigate the codebase and find those details with the agents when I need them.

There are two more reasons. I've learned a lot, and I'd rather build it right from the start than refactor huge sections of the prototype and bring in new bugs. And now I have the base language: the rebuild can be written with verification and proofs from day one, so it's safer and needs much less testing. I'm in a much better place to start this now that I have the language I wanted for this kind of project.

This repository becomes strata-lab, where ideas are tried and measured first. The new Strata is written in Strata, in small layers: a minimal compiler, then verification as early as possible, then self-hosting. I look at every layer as it's built, through Strata's own tools: the traits, the contracts, the relationships between them, the flows, and the code itself where I want the detail. The plan is a draft in REBUILD.md.
