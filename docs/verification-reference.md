# Verification reference

What `strata verify` reports, and how to tune it: the fine print of [verification](verification.md).

`strata verify` turns every contract into proof obligations and gives each function one of these results:

- **proven** (`✓`): the SMT solver proved every check. `--checks` lists them.
- **fuzzed** (`~`): some checks could not be proven, so the function was run on generated inputs and nothing failed. Each unproven check says why, for example *depends on `fold` is not modelled*.
- **failed** (`✗`): a counterexample. When the solver finds one, it is run (compiled) first, and reported only if it really fails. Otherwise the fuzzer looks for one.
- **incomplete** (`○`): the function still has a hole.
- **assumed** (`≈`): trusted, not checked. These are a capability's own code (`capability ...`: std's `Terminal`, `Disk` and `Process`, and a program's own) and C reached through `extern c`: they call the system. Their contracts are taken as true where they are called, and the code around them is checked as usual: a function that calls C, or takes a capability, is proven from those contracts (compiled code still checks a C function's `ensures` at each call, as nothing proves it). Only running it is different: code taking a capability isn't fuzzed (only `strata run` gives one), and what the solver doesn't prove of it is reported as skipped, saying why.

Derived code is checked as well: `derive Json for Signup` makes `Signup.to_json` and the rest, and also copies of `std.json`'s helpers made for `Signup`'s fields (`std.json.encode_as.for.Signup.4`), which are listed and checked with it, so a fault that only some field types can cause is reported there (with `integers = "proven"` under `[json]`, an `Int` field that may be beyond what JSON holds exactly).

The checks are exactly the ones compiled code makes when it runs: a callee's parameter refinements and `requires`, the refinements of constructed values and assigned fields, annotated bindings, `assert`, division by zero, and the function's own result type and `ensures`. Calls are checked against the callee's contract, never its body, which is how modules meet. A function passed by name (`lines.map(line_total)`) is checked against one arbitrary element of the list.

**`old` in `ensures`.** `old e` is `e` where the function started, for `mut` parameters and `mut self` (elsewhere in the clause they are their values at the exit). `verify` proves the clause at each way out (the end and every early `return`, each with the parameters' values there) with `old` read over the values on entry; at a call seen through the callee's contract, the `mut` arguments come back as new values of their types, the `ensures` relating them to the values before the call, and those are written back. A method only known by its contract (a trait's, called on a type parameter's value) gives the same result on the same arguments, so `c.total()` before and after `mut c.incr()` are related by `incr`'s contract. Compiled, an unproven `ensures` with `old` evaluates each `old e` on entry (`codegen.keep_olds`), holds it until the check at the exit, and shows it in the fault with the value at the end (`(before: len(xs) = 1, after: len(xs) = 1)`). Stored as `Old(Expr)`, the expression tag 40.

**Refinements and contracts are the same checks.** A parameter's refinement is checked where `requires` is (at each call, assumed in the body), a result's where `ensures` is. That is why `strata check` asks for a fact about one value as a refinement and keeps contracts for relations (a `requires` naming one parameter, an `ensures` naming only `it` or one element of a tuple result, and a refinement naming another parameter are warnings, which `strata fix` rewrites): moving one changes no verdict. Named results (`-> (next: Q, added: Natural)`) are read in `ensures` as the tuple's elements (`next` is `it.0`), and reported so.

How it works (`compiler/smt`): the body is run symbolically, with values as SMT terms. Records, sums, tuples and unions are SMT datatypes (`declare-datatypes`): a parameter's outer level is its fields, and a part that is itself structured is one term of its type's datatype, opened through the datatype's selectors the first time a field is read or a pattern looks inside. So a value of a large recursive type (a syntax tree) costs what the function reads of it, not the size of its type, and the solver knows by itself what datatypes give: equal values have equal parts, two constructors are different values, and a value is never one of its own parts (`t != t.left` is proven). What a type's refinements say of a term is a predicate of the term, defined for each term the code opens; a list inside a datatype value is a term of a list sort with its length and items as functions of it. A list is known by its length and by how its elements are made (a checked type, a literal, `range`, `filter`, `map`, `+`, `push`, a part of another list), position by position where it can be, so `all(xs, p)` is proven on an arbitrary element and, once known, gives `p` to every element the code looks at, a value of a union (`Square | Circle`) is a tag saying which member's shape it has plus a value for each member (a member value passed where the union is expected, or branches returning different members, become one; a `match` arm narrows it to its member), branches are merged with `ite`, and a loop keeps of the variables it changes only their declared types and its invariants, inferred or written (after a `while`, also that its condition is false, unless a `break` left it). Each check becomes the question "can the negation be true under what is known here?", which is sent to the solver (Z3, or cvc5) as SMT-LIB text (`verify --smt` prints the queries, termination ones included; `verify --obligations` prints each obligation with the solver's answer, `proven`, `refuted` or `unknown`, nothing run; `verify --termination` prints each function's termination verdict and whether a contract may see through it; `verify --fuzz` prints the fuzzer's verdict alone, no solver). `unsat` means proven; `sat` comes with a model, which becomes the counterexample. A dict is an SMT array from each key to an `Option` of its value, a set an array from each item to whether it is in, each with its size as a function of the array: `get`, `contains`, `len`, `insert`, `remove`, literals and `union`/`intersection`/`difference` (of sets) are array terms (`select`, `store`, a constant array for `{}`), the size changing by one when an `insert` adds a key that wasn't there or a `remove` takes one that was (facts about each operation, no quantifier), so two dicts are equal when they have the same entries (`b == old b` after a function that put back what it took out), and a `for` over a dict's entries or a set's items gets each in the array. A value read from a dict is valid for the dict's value type (a `Dict[Int, Loc]` whose `Loc` has `price > 0`), as each operation carries the dict's validity to the next. `keys`, `values`, `set(xs)` and `dict(pairs)` of a list that is not a literal are known by their sizes only. A counterexample shows an input dict or set as a literal of its first entries (`Set[String] { "x", "" }`). Anything not modelled (floats, positions after `filter` and `sort`, most higher-order builtins, unions whose members can share a shape such as `List[Int] | List[String]` or include a type parameter) becomes an unknown value. That can only make a proof fail, never make a false proof succeed, and the reason is kept for the report. `Int` is a mathematical integer, as it is when the code runs.
An SMT string is a sequence of code points, so `len(s.code_points())` is its length exactly. A string's positions are byte offsets: `byte_len(s)` is a function of the string known to lie between its number of code points and four times that, and equal to it on an ASCII string; `byte_slice`, `index_of` and a match's position are exact on ASCII strings and bounded elsewhere. So refinements on lengths and positions stay provable. These string builtins are modelled exactly: `+`, `contains`, `starts_with`, `ends_with`, `chars` (its length, each element one character), `replace` with a pattern that isn't empty (an empty one puts the replacement around every character, which SMT's `replace_all` doesn't, so it is unknown), `to_string` of an `Int`, `Bool` or `String`, and `is_digit`. `parse_int` is exact for digits with an optional `-`, and for strings without a digit (`None`). Other forms (whitespace, `+`, `_`) are unknown. `trim` keeps only a length bound. `to_upper`, `to_lower`, `is_alpha`, `split`, `lines`, `repeat` and `reverse` are unknown. `chr` is a check that its argument is a character, and `ord` one that its argument is one character. `matches(s, "regex")` becomes a regular-expression constraint with `std.regex`'s meaning (the prover's model is made by `std.regex.smt_model`). Strata regexes are Unicode regexes: `\d` is any decimal digit, `\w` and `\s` are Unicode classes, `\p{..}` works, `.` is any character but `\n`, and `(?i)` is Unicode case folding. The pattern is parsed by `std.regex`, and translated exactly: literals, classes, groups, alternation, repetition, and `^` / `$` at the very start or end. Word boundaries, multi-line anchors and anchors elsewhere stay unknown. Z3 can't decide classes with hundreds of ranges (`\w`, `\p{L}`, Unicode `\d`), so such a class is bounded from both sides: `matches` is true on a subset of its ranges and false outside a superset of them. When one string is matched against two patterns, how their languages relate (one inside the other, or disjoint) is worked out exactly from the patterns' automata and added as a fact. So `\d{3}` implies `\d+`, and `[a-z]+` implies `\w+`.

**Strings past U+2FFFF.** SMT-LIB strings hold the code points U+0000 to U+2FFFF (Z3 and cvc5 both stop there). Rust strings go up to U+10FFFF. So a proof about strings covers the strings whose characters are all at most U+2FFFF. A string literal with a later character (planes 3 to 16: rare CJK, tags, private use) is an unknown. The cross-check, which runs proven functions on generated inputs, is the backstop.

**Helpers in contracts.** A contract can use an ordinary function, such as `type Digit = Int where small(it)` with `fn small(n: Int) -> Bool { 0 <= n && n < 10 }`. Inside a contract, a helper that terminates and cannot fail is *seen through*: its body is used, not just its contract. So `fn zero() -> Digit { 0 }` is proven and `fn ten() -> Digit { 10 }` is refuted. A helper that may not terminate is never seen through. Unfolding one would let the solver prove false things. A helper marked `terminates` is seen through, and the proof says it relied on that.

**Termination.** `verify` also says whether each function always finishes:

- **terminates**, when shown automatically:
  - no recursion, and only `for` loops;
  - a `while a < b` loop (also `<=`, `>`, `>=`, `!=`) whose bound `b - a` the solver proves goes down on every pass, unless the pass ends the loop. The candidate bounds are those of the condition's comparisons (joined by `&&` or `||`), then those of the comparisons the body tests (`if` and inner `while` conditions over variables known before the loop), at most 4: each alone, then each pair compared in order, so a loop where on each pass one quantity goes down while those before it stay is found (`(n - i, m - j)` for `while i < n { if j < m { j += 1 } else { i += 1; j = 0 } }`, `(len(a) - i, len(b) - j)` for a merge's `while i < len(a) && j < len(b)`);
  - a `while` or `loop` with a `decreases` clause whose measure the solver proves goes down on every pass (below);
  - recursion where some argument is a smaller piece of a parameter, taken apart by a `match` (`[_, ..rest] => 1 + length(rest)`);
  - recursion with a *measure*: an integer expression of the parameters that the solver proves is never negative at each recursive call, and smaller for the call's arguments. The candidates are tried automatically:
    - each integer parameter (`fact(n - 1)`, `gcd(b, a % b)`);
    - the length of each list or string parameter (`total(drop(xs, 1))`);
    - for each comparison in the body, the distance between its sides (`100 - n` in `up(n + 1)` under `n <= 100`, `hi - lo` in a binary search);
    - pairs of these compared in order, like words in a dictionary (`(m, n)` for Ackermann's function).

    A function with a `decreases` clause has that measure as its one candidate.

  It also needs everything the function calls to terminate.
- **may not terminate**, with the reason: a `loop` without a `decreases` clause, other recursion, mutual recursion, a `decreases` measure not shown to go down, or a call to such a function.
- **assumed**: the function is marked `terminates` (after its contract, `fn f(x: Int) -> Int terminates { … }`). Its callers say they terminate *if* it does.

**`decreases` clauses.** Where no candidate is found, the measure can be written: `decreases e` on a `while` or `loop` (on its own line between the header and the body, as `invariant`), or on a recursive function (beside `requires` and `ensures`). `e` is an `Int` expression, or a tuple of them compared in order (`decreases (left, len(book.orders))`: each pass either lowers `left`, or keeps it and lowers the other). The part that decides must be at least 0 before the pass or call, and lower after it; the parts before it the same. At most one clause per loop or function; a `for` loop takes none (it ends on its own). It is a check like any other: `verify` proves it where each pass ends (`decreases `(a, b)` after a pass of `while …``, at each `continue` too, unless the loop is over) and at each recursive call (`decreases `(m, n)` at a call of `ack``), over the parameters as the function got them and the call's arguments; and the termination verdict uses it as the one candidate (`terminates: `while …` ends: its `decreases (a, b)` measure goes down on every pass`). Not proven, it is checked when the program runs, like `invariant`: a loop's measure kept from the start of a pass and compared at the next (`decreases failed: `k` did not go down in a pass of `while i > 0` (before: 3, after: 3)`), a recursive function's computed on entry and compared with the arguments' at each call of itself (`compiler/codegen`'s `decreases_start`, `decreases_pass`, `decreases_entry`, `decreases_call`). So a solver's counterexample is run and confirmed, and a loop whose measure is wrong stops with a fault instead of running on. The verdict then says `may not terminate: … its `decreases …` was not shown to go down on every pass (it is checked when the program runs)`. Stored: a loop's clause is a `Decreases` statement among its body's first (with its `invariant`s), a function's is its body's first statement; both are shown where they were written.

`verify NAME` analyses termination only for what the selected functions reach (a function's verdict depends only on what it calls), so checking one function does not pay for the loops of the whole program and std.

**Policies.** A package's `strata.toml` says what `verify` requires, each rule as a list of modules (`"*"` for all of them, `"main"` for the root module; a module covers the modules below it):

```toml
[verify]
proven = ["core"]        # every check proven, not just fuzzed
terminates = ["*"]       # every function shown (or marked) to terminate
no_recursion = ["core"]  # no recursion at all, even recursion that terminates
```

Recursion is allowed unless `no_recursion` says otherwise. A run that breaks a rule fails, listing each violation. `proven` accepts assumed code, and the run lists everything it accepted that way. `verify --require proven,terminates,no-recursion` applies the same rules to everything checked, package or not. Loading the package fails on a rule that names a module it doesn't have.

**Cross-check.** A proven function that terminates is still run on a few generated inputs (`--cross-check N`, 20 by default, 0 turns it off). If one of them fails, the prover was wrong, and `verify` says so: the result is a failure *found by the cross-check*, flagged as a bug in the prover. Each run has a step budget. A run that goes past it, or runs out of stack, proves nothing either way and is set aside: proven code can still be far too costly to run, like Ackermann's function.

**Inputs built by the program.** A strong `requires` throws away most random inputs: of 800 random order books, 12 met `requires book_ok(b)`. So under a `requires`, an argument whose type is one of the program's records or sums is mostly built the way the program builds one: three cases in four, the fuzz driver calls one of the program's functions that return that type without taking one (a *builder*, `empty_book()`), then up to 10 times one of those that change it (a *stepper*: it takes the value `mut`, as `new_order(mut b, c)`, or takes it and returns a new one, as `insert(l, p, o) -> Ladder`), or none, each on generated arguments; the fourth case is generated as before. A step whose `requires` doesn't hold on its arguments is skipped. When some builders (or steppers) have an `ensures`, only those are used: a function that merely hands back a ladder from a random book rarely keeps an invariant. The function being fuzzed, generic ones, `extern c` ones, std's and core's are never used, nor one with a parameter no value can be generated of (a capability). The built value is still checked against the `requires` when the function is called, so a builder or stepper that doesn't keep the invariant only costs a discarded case. A fault while building (a builder's own `requires` unmet, a bug in a stepper) happens in a frame of its own (`strata_fuzz_build`) and discards the case too: the stepper's own verdict reports its bugs. The verdict's count stays honest: "200 cases, 69 discarded by `requires`" counts both. On the order book, the engine's handlers went from 12 cases (788 discarded) to 200 (69 discarded, nearly all of them random ones), the ladder's from 200 (278 discarded) to 200 (36). If the driver can't be compiled with the builders (a stepper that can't be compiled yet), it is compiled without them, as before.

**Inputs from the solver.** Random values rarely meet some types: a list whose elements are consecutive integers, or a record whose indices must stay within its own list. When the fuzzer can't make inputs for one ("could not generate a value", or every input broke the `requires`), the solver makes them. It looks for values that satisfy the parameters' types and the `requires`, with lists of at most 6 elements. Up to 20 of them, each different from the ones before, are run as the fuzzer's cases. A failure is reported as *found by the fuzzer, on inputs from the solver*:

```text
✗ last                     Ensures violation (found by the fuzzer, on inputs from the solver)
    input:   [-1, 0, 1, 2]
```

**The solver and the fuzzer race.** A function's obligations go to the solver and its inputs to the fuzzer at the same time. The fuzzer waits up to 0.3 s first, because most proofs take milliseconds. Until the solver has answered, the fuzzer runs on a cross-check's budget of steps. The first to find a failure stops the other, and the solver's processes are killed. So a query the solver would give up on after 20 s doesn't hold up a bug the fuzzer finds in a millisecond. When the solver proves everything, the fuzzer runs only the cross-check's cases. When it doesn't, the fuzzer runs the full search, and the cases that ran out of the smaller budget are run again first. Which side finishes first depends on timing, so a failure the fuzzer finds before the solver has proven everything is reported as the fuzzer's, not as a bug in the prover. `--no-race` runs the solver first, then the fuzzer: every result is the same from run to run, and the cross-check can tell a bug in the prover.

**Verdicts are kept.** Each check's verdict is kept between runs, for a package, a script or `std/` alike: in the git repository the code is in (`<git common dir>/strata/verdicts`, so every worktree shares them), else in `~/.cache/strata/verdicts` (`STRATA_CACHE`; `STRATA_VERDICTS` names the folder). Each verdict is a file of its own, written whole and renamed into place, so several runs at once share them safely. Its key is the check's name, the hash of its definition with everything it depends on (`store::closure_hash`), the number of cases and of cross-checked cases, the seed, `--no-race`, the solver (path and version) and std built into strata (unless std itself is checked: then its definitions are in the hashes) (not the strata binary: a verdict outlives rebuilds of the compiler). A proof is kept a second way, by what it relies on (`verify-strata/proofs/`): the check's own code, the interface (signature and contract) of each callee the prover sees only by its contract, the code of each it sees through (`transparent`), and everything else it reaches by its code, but not the number of cases: so when a callee's body changes and its contract doesn't, its callers' proofs stay, and only their cross-check runs again (it runs the callees). Termination's findings on each function's loops are kept the same way (`verify-strata/loops/`). Only the definitions with a check to run get fuzz drivers compiled. Each definition's latest verdict is kept too, by its hash: what `strata diff` shows. A changed definition is checked again with what depends on it, and nothing else is: a kept verdict is printed as a fresh one with `(cached)` after it, and `--require` and `[verify]` apply to it the same way. `--no-cache` checks everything again (and keeps the new verdicts). A verdict where the solver gave up is kept too: its resource limit is deterministic, so it would give up again (each query asks the solver why it gave up). One where it ran out of time (the 20-second backstop, which a busy machine may hit), gave no answer or didn't say why isn't kept. Folders of the older layout, one per compiler, unused for two weeks are removed.

**`verify` is written in Strata.** `strata verify` runs the command written in Strata (`compiler verify`, in `compiler/main`) on a script or a package (`--file`, else the package around the current folder). The program is checked first, as `strata check` checks it: its errors are printed and nothing is verified. A selection (`verify NAME`, `prefix*`, `module:m`, `slice:NAME`, a module's name) chooses the definitions checked, and the package's `[verify]` rules apply as Rust's do. The same checks are made (functions, a type's own methods, implementations' methods through wrappers that call them, laws, the copies a `derive` makes), with compiler/smt's proofs and compiler/codegen's fuzz drivers run in the compiler's own JIT, and the report is that of `verify --no-race` (it has no race). It keeps its own verdicts, in `~/.cache/strata/verify-strata/checks` (`STRATA_CACHE`), one file per check, keyed as Rust's are (the check's name, its definition's closure hash, read from the module files' headers, the cases, the cross-check, the seed, the solver's name and std's hashes); `--no-cache` checks again. Each definition's status (its checks' worst verdict) is kept in `verify-strata/status`, by its closure hash, for a viewer (`compiler verdicts FILE` lists them). What it proved is recorded in `verify-strata/proofs/<the path's hash>.txt` (or `--proofs FILE`), each check with its definition's closure hash; a definition not verified in a run keeps its record while its code is unchanged. `compiler proofs FILE` gives what is current, in the form `codegen --proofs` reads, with the entry checks every caller proved (`entry F argument P`, `entry F requires I`): what `build` and `run` leave out. `build` verifies first (`compiler verify --quiet`: one line on stderr for the checks not verified before). `--obligations`, `--termination`, `--fuzz` and `--smt` are `compiler smt`, `termination`, `fuzz` and `smt --queries` (the obligations' queries; the termination analysis's aren't shown). `verify --compare` runs both verifiers and prints the lines only one gives. A call of an `extern c` function is assumed by its contract, as Rust's verifier does. It reads only the std definitions the program reaches, and builds and loads a package's `[native]` C for the code it runs. Not yet: the race and inputs made by the solver.

**Std's termination is kept.** What the solver finds about std's own functions (a loop's bound, a recursion's measure) is kept between runs with the rest of verify's findings, under `verify-strata/` in the own cache (`~/.cache/strata`, `STRATA_CACHE` moves it), keyed by the code involved. Functions made from std for a program (`std.json.encode_as.for.Signup.4`) are the program's, and are analysed every time.

**In parallel.** Functions are checked on all cores (at most one solver process per core), and a function's obligations are solved in one solver script, each between `push` and `pop`. Z3 is kept running, a process per core for the whole run, each script given after `(reset)` with its limits set again, so starting Z3 (longer than most queries take) is paid once per core; a script already answered in the run isn't asked again. A solver that is a script, or doesn't answer a command as it reads it, gets a process per script instead (`STRATA_SOLVER_POOL=0` asks for that too); `STRATA_SOLVER_LOG=FILE` writes a line per script: its time, flags, size, hash and first answer. Termination's loop bounds and recursion measures are found the same way. No string is longer than memory: each query bounds the lengths it uses below 2^64, without which Z3 tries to build a string of 10^308 characters to refute `len(s) < 10^308` (it gave up after 20 s on `float(len(w))`).

**Loop-invariant searches.** Each loop's inference (`smt.while_loop`) records what its search took (`LoopFound`: Z3's resource units, `(get-info :rlimit)` asked after each search query, and its time). Invariants whose search took more than 2M units (`found_by_search`) are written (a value before the loop, `$entry_x`, named in code by `main.entry_forms`: the expression `x` was set to just before the loop when that is made of variables neither the loop nor the statements since change (`value_before`), else a binding `start_x := x` made just before the loop) into the program as `invariant` clauses after the run's verdicts (`main.write_found`): one edit, the changed module files encoded again, each changed definition written, parsed and resolved again and kept only if it is the same tree; logged (`"by":"verify"`) and committed when the package was opened from its folder (`--log`, which `strata verify` and `strata build` pass then). `--no-write` turns it off, `--show-searches` lists every loop's search. Every search query is a job flagged `budget` in c/solver.c: the run's budget (`--search-budget N`, default 2,000M units; `solver_budget`) is charged the units each script actually run used (an answer from the run's memo costs nothing), and once it is used up a search is answered `budget` without running. A function whose encoding met that is reported (`search_notes`), and its verdict, proof and termination findings aren't cached. A loop with written invariants asks its inference questions as `probe`s (0.5M units each), giving up at the first unanswered.

**Solvers.** `z3` is found on the `PATH`. `STRATA_SOLVER` names another solver binary, for example `STRATA_SOLVER=cvc5`. A solver whose `--version` names cvc5 is run with cvc5's flags; any other is run like Z3. Both get the same SMT-LIB queries. Without a solver, everything is fuzzed. Each query has a deterministic resource limit rather than a timeout (`rlimit` for Z3, `--rlimit-per` for cvc5, with a 20-second time limit only as a backstop), so results can be cached by content hash. A proof gets 2M Z3 units, a tenth of what a search for a model gets (inferring loop invariants, making inputs): every proof in std, the examples and the compiler takes under 0.5M, and what ran longer was a search for a counterexample to a check that can't be proven (it is "the solver gave up" now; the fuzzer looks for one too). The solver's version is in the cache key. The test suite passes with either solver. cvc5 has no Homebrew formula; install it with `brew tap cvc5/cvc5 && brew install cvc5`, or from its releases.
