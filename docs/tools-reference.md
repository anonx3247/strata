# Tools reference

The fine print of [the tools](tools.md): each section adds to the section of the same name there.

## What the tools tell you

Outside a package, `strata --file F edit < text` writes a script (or a folder's module) as given, then checks it: what doesn't check is still written, said with `written: F doesn't check (N errors; --file edits are kept as given, unlike a package's edit, which is rejected):` and its errors, and the exit code is 1. (A package's `strata edit` refuses an edit that doesn't check in itself; the uses it breaks elsewhere, a changed return type, parameter list or parameter type, become holes of a pending change instead. A rejected edit's text is kept in the package's `.strata/rejected/edit-N.st`, and the rejection says where, for an edit from standard input and one from the editor that gives up.) One module file of a folder isn't checked alone, since its neighbours may not be written yet.

What an edit checks and writes. An edit that changes nothing (every definition given is as stored) does nothing: nothing is written, checked, logged or committed. Otherwise only the module files whose definitions change are written; in those, each definition the edit leaves alone keeps its stored bytes and header entry, and only what changed is encoded again (`strata upgrade` is the command that encodes every file again). Then only what the edit can affect is checked, as `strata check` would check it, the rest of the package and std in scope: the definitions it changed or added, and when one's interface changed (its signature, contract, fields, variants, methods) or one was removed, the definitions that use it, in any module: those whose header lists it as a dependency, and those written with one of its names (a field read on a value whose type they never name, a method called on one). A body changed alone can't break anything else, so only it is checked. An error elsewhere in the package, which the edit can't have caused, doesn't stop it. `rename`, `move` and `fix` check the same way. An edit prints the warnings on what it wrote (as `strata check` does on everything, on stderr): a contract that is a refinement, a refinement that is a contract (`compiler/lint`); `strata fix [NAME]...` makes the change each one shows, logged as an edit is (`--file F`: a script or folder, outside any log, as `edit --file` writes it). std, core and a package with dependencies are still checked whole. `strata check` checks everything.

## How it is stored

`verify`'s verdicts are kept outside the package, shared by every worktree of its git repository (`.git/strata/verdicts`; outside a repository, `~/.cache/strata/verdicts`), one file per verdict, keyed by the hash of a definition *and everything it depends on*, with the check's name and the run's settings.

The code is stored as its syntax tree, in binary: each `.strata` file is a module file (the format is Strata's own, specified in [binary-format.md](binary-format.md)). Text goes in only through an edit (`strata edit`, `strata add`) and comes out through `view` (`strata view MODULE`: a module as its file is stored, imports first); `strata view --split DIR` writes a package's text, one `.st` file per module, to read rather than to read back; a type one union lists is shown inside it unless it has a doc or an `impl` of its own, and `--members separate` shows every member as a definition of its own (the same program either way). Outside a package's log, `strata --file F edit < text` stores a script (or, with `--file DIR/ edit MODULE`, a module of a folder), created if it is new; only text that doesn't parse is refused. Each module file starts with a header listing its definitions, their hashes and dependencies (`strata header core.strata` prints it), and each definition stores its interface before its bodies. `strata pack app.strata` writes the whole program as one bundle, which `--file`, `strata run` and every view read like the package. The hashes `strata` shows are those of the binary encoding (see the spec).

## Finding code: `find`, `refs`, locations

Builtins and the standard library are read the same way: a name the program doesn't define is looked up in core and std, also outside a package. `strata view Dict` and `strata view insert` show the builtin's doc and signature (every overload of the name), `strata view std.json.parse` (or `view JsonValue`, a public std name core doesn't have) std's definition; `strata find Dict` lists them. A builtin's doc ends with its cost, in one form: `Cost: O(1) amortized, in place when ...; O(n) otherwise (a copy).`, checked against the runtime and measured, so read it rather than benchmark.

A location's path is made of the tree's field names and list positions: a block's statements and then its result by position (an expression statement is its expression), `callee` and `args/N` of a call, `recv` of a method call, `arms/N/pat` and `arms/N/body` of a `match`, `params/N/ty`, `ret`, `pre/N`, `post/N` and `body` of a function, `methods/N/…` of an impl, trait or capability, a record argument or pattern field by its name (`args/attempts`), `value` inside `return`, `assert`, `mut`, `spawn` and the like. The hash is the definition's identity hash (comments included), so a location says when the definition has changed; `view` then shows the same path in it now, or as much of the path as still leads somewhere. `view` reads a location wherever it is among its arguments.

`refs` looks for uses in the definitions whose header lists the target's definition (or a member's type or trait) as a dependency; a name the package doesn't define, given qualified (`std.list.map`), is looked for by name everywhere. A field's reads (`x.attempts`) count when the checker types `x` as the field's record, or when no other record has a field of that name; a type's own method's calls when the checker resolves them to it; a trait's or capability's method's calls by name. A root-module name used where a local of the same name is in scope is the local's.

`strata check` follows each error with `--> LOCATION` and the code after `| `: the place is the first node, outermost first, written as code the message quotes (an expression or pattern before a type); without one, the definition's head. compiler/codegen's "not compiled yet" errors (`build`, `run`, `test`) end with the code they are in (`, in `CODE``) and are followed by its location in the same way. (The checker doesn't track places itself yet; nor do runtime faults, `--trace` and `verify`'s refutations: see IDEAS.md.)

## Packages

**Dependencies.** `[deps]` names other packages, by local path (`json = { path = "../json" }`) or git URL (`json = "https://…"`, or `{ git = "URL", tag = "v1" }`, `rev`, `branch`; pinned to a commit in `strata.lock`, fetched into `$STRATA_CACHE`, else `~/.cache/strata`, and moved by `update`); the key is the dependency's `name`. A dependency's modules are named with its package's name as prefix, as std's are with `std`: its root module (`main.strata`) is `json`, its module `text` is `json.text`, and a module of the package can't be named like one of its dependencies (`` module `json` is named like the dependency `json` ``). Inside the dependency nothing changes (its root module's definitions, union and sum variants included, stay visible short to its other modules); everywhere else it is reached only through `use` (`use json`, `from json use parse`, `use json.text`), and only what its strata.toml `exports` (modules, or single definitions: `exports = ["text", "parse"]`, a root module definition by its name or `main.NAME`, the root module as `main`; default every `pub` definition): using the rest is an error, worded like a private definition's (`` `parse` isn't exported by package `json` ``). A dependency's definitions are read lazily, as the program reaches them: only the module files it reaches are read, and only the definitions it reaches are decoded (a variant or a trait's method brings its own type or trait). There are no cycles between packages: if `a` depends on `b`, `b` may not depend on `a`, directly or through others (`dependency cycle: a -> b -> a`); cycles between the modules of one package are fine. std depends on nothing. A dependency is checked, verified and tested in its own package: the commands report only the package's own definitions, and a dependency's `test` blocks are left out (`strata test --with-deps` runs them; the Strata compiler's `check --with-deps` checks them). So far this is built in the compiler written in Strata (`compiler/deps` and `compiler/main`: its `package [--std DIR] DIR`, `check [--std DIR] [--with-deps] DIR` and `update DIR [NAME...]` commands; it has no `test` or `verify` command yet); the Rust `strata` commands don't load dependencies.

Loading a package (for `check`, `run`, `verify`, …) fails on an export that names nothing, or a definition that isn't `pub`.

**The cache.** A run reads two caches and writes one (`compiler/cache`, `caches_of`): its own, `$STRATA_CACHE`, else `~/.cache/strata`, and a release's shipped cache, read-only, beside the executable (`lib/strata/cache`, `STRATA_SHIPPED_CACHE`). Every key starts with the compiler's identity (the SHA-256 of its executable), so a new compiler never reads an old one's entries, and nothing is evicted: the own cache only grows, until it is cleaned by hand. `strata cache` prints where the own cache is, its size, and each top-level folder's size with what it holds (`verify-strata`: verify's verdicts, proofs and loop findings; `objects` and `ir`: built programs; `std-library` and `core-rt`: std and core.rt compiled; `comptime`, `proofs-lines`, `identity`, `deps`: git dependencies; `build`, `run`, `smt`: the scratch of runs, one folder per process id), a folder nothing reads any more marked as an older compiler's, then the shipped cache's size. `strata cache clean` removes the whole own cache and says how much that freed; it never touches the shipped cache or a std library, nor the verdicts kept in a git repository (`.git/strata/verdicts`). It refuses a folder that isn't a cache of its own (`/`, `$HOME` or above it, a package, a git repository, a folder holding std or the shipped cache), and refuses while another running strata has scratch in it (a `build/PID`, `run/PID` or `smt/PID` whose process is running: `--force` cleans anyway); it is meant for when nothing else runs. `--obsolete` removes only the top-level folders nothing reads any more (an older compiler's layouts, such as `std/`, `compiler/`, `scripts/` or `termination/`) and the scratch of runs that ended without removing it.

## Git

- **`strata merge-file %O %A %B %P`** is a git merge driver. It pairs each side's definitions with the base's. A definition that only one side changed comes from that side, so edits to two functions never conflict, even when they sit on neighbouring lines. When both sides changed the same definition, its canonical text is merged line by line, and the result is kept only if it parses back into that one definition; otherwise conflict markers go around that definition alone, and the file is left as text: fix it, then `strata resolve FILE` stores it as a module file again. A rename on one side (a definition gone, and a new one that is the base's after `strata rename`) is applied to the other side, so new calls to the old name follow it. Then the file is type-checked inside its package: an error that neither side had on its own (ours changed a signature, theirs added a call to the old one) fails the merge. A side that isn't a module file isn't merged: ours stays.

## The REPL: `strata repl`

`strata repl` (or `strata --file F repl`) opens a session on the package around the current folder: every function, type, trait and impl of it, std and core. Each line is an expression (`double(21)` prints `42: Int`: the value as code, as `strata run f` prints a result, and its type), a binding (`x := e`, `mut x := e`, `x = e`, which prints `x: Int = 10`), or a definition (`fn`, `type`, `trait`, `impl`: the session's, not written to the package; one of the same name replaces the earlier one, or the package's own for the rest of the session). Commands: `:type e` (the type only, nothing run), `:view NAME` (a definition, the session's first), `:reload` (the package's files read again; each value kept whose type still checks, the others dropped and said so), `:quit`. With standard input not a terminal each line is read in turn, as if typed, and the exit code is 1 when an input failed, so cases and agents can drive it.

Each line is checked against the program and the session (the earlier values' types known), then compiled by compiler/codegen as a small function of its own (with what it reaches) and run by the JIT in the same process, as `comptime` runs: a fault (`[1, 2][5]`) is reported as an error and the session goes on. The values are kept between lines as the code that writes them (read back from compiled memory, as `run f` reads a result), and bound again from it in the next line's function; a `mut` value a line assigns (`xs = xs + [1]`) is read back after it.

Capabilities are the REPL's own, never the program's real ones: `console` is a `std.io.Recorder` made for each line (what a line prints is shown with its result, written nowhere else; it reads no input); no other capability (`disk`, `process`, …) is given, so a line can't write files or start processes (IDEAS.md: the opt-in planned).
